# atlas-duck — Design Spec

**Date:** 2026-10-07
**Status:** Draft for review (after three adversarial review passes: multi-lens, local security, consistency)
**Author:** Yavuz Ege Özcan (with Claude)

atlas-duck is a cross-platform desktop application that acts as a **human-in-the-loop security proxy** between AI agents and self-hosted Atlassian **Jira Data Center** and **Confluence Data Center**. It holds the user's Personal Access Tokens, executes typed operations on behalf of agents, requires the user's approval before any write is executed and before any read result is released, and records every read and write in an encrypted, tamper-evident audit log retained for at least three months.

---

## 1. Goals, non-goals, success criteria

### 1.1 Requirements (as stated)

| # | Requirement |
|---|---|
| R1 | Multi-platform desktop GUI app (Windows, macOS, Linux). |
| R2 | Connects to Jira and Confluence using user-provided API keys (Data Center/Server only → Personal Access Tokens). |
| R3 | Acts as a security proxy for AI access; agents never receive credentials. |
| R4 | Agents can request operations: create tickets, access spaces/pages, search, etc. |
| R5 | Write request → user is notified and must approve before execution. |
| R6 | Read request → app performs the read; user must approve the result before it is returned to the agent. |
| R7 | Best-effort preview of all data to be returned (and of writes to be executed). |
| R8 | Agents can submit scripts that use read-only commands; scripts read without confirmation; user approves only the final result (with preview). |
| R9 | The app has a CLI that agents use. |
| R10 | All reads and writes are logged and retained for at least 3 months for compliance. |

### 1.2 Decisions made during brainstorming

| Topic | Decision |
|---|---|
| Deployments | Jira DC/Server and Confluence DC/Server only (PAT, `Authorization: Bearer`). Cloud out of scope. |
| Stack | Tauri 2 (Rust core, React + TypeScript UI); Rust CLI; rquickjs sandbox. |
| CLI waiting | Block with timeout; on timeout print the request id and exit 4; `await <id>` resumes. |
| Script language | JavaScript in embedded QuickJS-NG (rquickjs), in a separate sandbox process. |
| Agent auth | None. IPC restricted to the current OS user. Agent name is self-declared and **unverified**; OS peer pid/exe captured for display and audit. |
| Auto-approve | None in v1. Every write and every read result is approved individually. Batch approve/deny of selected queue items is allowed (§5.6); each item is logged individually. |
| Audit depth | Full payloads, encrypted at rest, hash-chained, retained ≥ 92 days (covers any 3 calendar months). |
| Approval UX | Approve / deny with reason / **edit** (writes) / **redact** (reads). |
| Operations | Core + extended reads and writes for both products (§7). |
| Agent front ends | CLI **and** an MCP server (`atlas-duck mcp`, stdio) over the same IPC. |
| Spec scope | One spec covering the full v1; the implementation plan is milestone-ordered (§14). |

### 1.3 Non-goals (v1)

Atlassian Cloud; auto-approve rules/policies; per-agent authentication; auto-update; multi-user/shared/server deployments; agents on other hosts or in containers/VMs (the CLI must run as the same OS user on the same OS instance as the app; WSL on Windows uses the Windows CLI through interop, §12.4); Jira attachment upload; cross-space Confluence page moves; arbitrary HTTP passthrough; delete operations; Markdown-generated mentions (§7.6); idempotency keys (duplicates are flagged instead, §5.6).

### 1.4 Success criteria

1. An agent with only the CLI (or MCP) can search Jira, read an issue, read a Confluence page, run a multi-call read script, and create/update issues and pages — and it receives **no Atlassian-derived bytes** the user did not explicitly release (residual channels are enumerated in §10.2), and **no write** happens that the user did not explicitly approve, byte for byte (§5.1 inv. 3).
2. Every fetched, released, denied, edited, delivered and executed payload is retrievable (decrypted) from the audit log for the retention period, and the log's integrity — including truncation at either end — can be verified.
3. A reviewer can decide on a typical approval in under ~10 s thanks to the preview. Reference scenarios: `jira.issue.get` with default fields, `jira.search` with 50 rows, a ~5,000-word Confluence page, `jira.issue.create`, a small `confluence.page.update` diff, and a 200-row script result. For each, the preview header and first screen render within ~1 s on the CI runners (the 1 s inert window after focus or a candidate change, §5.6, counts against the ~10 s), and nothing needed to decide is more than one click away (§6.1, §13).
4. No PAT ever appears in IPC traffic, diagnostic logs, audit payloads, or the sandbox; in the UI it exists only transiently in the dedicated credential-entry window (§10.3) and is never displayed or returned to any webview afterwards; no Atlassian content ever appears in diagnostic logs.

## 2. Architecture

### 2.1 Processes

| Process | Role | Secrets |
|---|---|---|
| **`atlas-duck-app`** (Tauri 2 tray app) | Trust core: IPC server, request broker & approval state machine, Jira/Confluence HTTP clients, preview generation, audit store, UI windows. | PATs, audit KEK, head and first-retained anchors — in the OS keychain; in passphrase mode (§8.6) PATs are KEK-wrapped in the DB's `vault` table, the KEK is unwrapped from `recovery`, and the head anchor is the MAC'd file `<data>/anchor`. Read only by this process. |
| **`atlas-duck`** (CLI; also hosts `atlas-duck mcp`) | Thin client used by agents. Sends typed requests over IPC, blocks for decisions, prints JSON. Launches the app if it is not running (§4.7). | None. Never touches keychain or DB. Reads only the non-secret `cli.toml`/`paths.toml` and the `endpoint` file (§7.7, §3.1). |
| **`atlas-duck-sandbox`** (one process per script run) | Executes one agent script in QuickJS. All `atlas.*` calls are forwarded to the app via its stdin/stdout. | None. No HTTP client, keychain, or DB code linked. OS resource limits + best-effort OS confinement (§9.4). |

All three binaries ship in the same installer (§12). **Data leaves the app only through IPC envelopes**: the app never inherits a client's stdio, worker stderr is captured by the app (§3.4), and diagnostic logs contain metadata only (§7.7).

### 2.2 Rust workspace layout

```
atlas-duck/
  Cargo.toml                     # workspace
  crates/
    registry/      # pure-data operation specs (§2.3): no fn pointers, no I/O
    core/          # op table (executors/previewers/stale checks), request lifecycle, approval queue, redaction/edit engine
    atlassian/     # Jira DC REST v2 + Agile 1.0 client, Confluence DC REST client, rate limiter
    convert/       # storage→markdown, markdown→wiki, markdown→storage, wiki→preview-html
    preview/       # preview model builders per operation
    audit/         # SQLite store, crypto (envelope), hash chain, anchors, prune log, retention, export
    ipc/           # protocol types (JSON-RPC), framing, per-OS transport, peer identity
    sandbox-host/  # spawns/limits/confines the worker, bridges host calls
    sandbox-worker/# the atlas-duck-sandbox binary (rquickjs)
    cli/           # atlas-duck binary: CLI + MCP server (rmcp)
  app/
    src-tauri/     # Tauri app (tray, windows, commands); [[bin]]s for cli + sandbox thin mains
    ui/            # React + TypeScript + Vite
  docs/
```

Dependency rule: `registry` depends on nothing in the workspace. `core` depends on `registry`, `atlassian`, `convert`, `preview`, `audit`, `ipc` (types). `cli` depends only on `ipc` + `registry`; `app` links `cli` for the AppImage `__cli` dispatch and calls the `audit` crate's export verifier for the `__verify-export` mode (§12.1); the `atlas-duck` CLI reaches that verifier only by running the app binary as a child. `sandbox-worker` depends only on `ipc` (types) + `rquickjs` (it receives the Read op ids in its init frame, §9.1). Nothing but `app` depends on Tauri. `atlassian` receives credentials through an injected `CredentialProvider` (keychain / vault / test double). Every Rust-drawn native confirmation (batch approval §5.6, PAT identity change §7.1, archive-and-start-fresh §8.7, security-weakening settings §10.3, "Prepare for removal" §12.5) goes through one injected `NativeConfirmer` trait in `core` (`confirm(text) -> Ok | Cancel`): the Tauri native dialog in `app`, a scriptable stub in tests (§13).

### 2.3 Operation registry

Every agent-visible capability is an entry in a static registry — never an HTTP passthrough. The registry is split in two:

```rust
// crate `registry`: pure data, no fn pointers, no I/O; shared by `core` and `cli`
struct OperationSpec {
    id: &'static str,                 // "jira.issue.get", "confluence.page.update"
    product: Product,                 // Jira | Confluence
    class: OpClass,                   // Read | Write
    params_schema: JsonSchema,        // validated before anything else happens
    cli: CliBinding,                  // per-param flag names, ≤1 positional, --<name>-file variants
    target_params: &'static [&str],   // params identifying the target (read-only in the edit form)
    target_display: TargetDisplay,    // declarative short-label rule over target_params (below)
    similarity: Similarity,           // "similar request" rule (§5.6): Target | Create | MoveIssues | None; per op in §7.3/§7.4
    field_rules: Option<FieldRules>,  // allowed `fields` / `expand` values (rule-based, §7.3)
    caps: Caps,                       // built-in defaults/hard caps (e.g. `max`, the 50-issue move limit)
    min_version: Option<Version>,     // instance version gate
    paginated: Option<PageSpec>,      // page param names, `items_key` (result array concatenated by atlas.all)
    result_projection: Projection,    // writes: static allowlist of response fields returned to the agent
    success: SuccessShape,            // writes: {statuses, body: Json | Empty}; default {2xx, Json} (§7.2)
    redaction_rules: RedactionRules,  // reads: where copies of a field live, item-level `mirrors` (e.g. renderedFields arrays), and the URL-valued fields (url, _links.*, self, ancestor links) (§5.3)
    result_example: serde_json::Value,        // documented example output (ops describe; dry runs, §9.5)
    result_example_sparse: serde_json::Value, // same shape, nullables null, arrays empty (dry runs)
    result_schema: JsonSchema,        // docs and tests only; never an MCP outputSchema (§4.6)
}

// crate `core`: behaviour attached per op id
struct OpImpl {
    executor: fn(..) -> ..,           // maps params → exact HTTP request list (§5.1 inv. 3)
    previewer: fn(..) -> Preview,     // builds the preview model
    stale_check: Option<fn(..)>,      // per-op rule (§5.4); only Write ops may have one
}
```

- `core` keeps its own table `op id → OpImpl`. A unit test checks that every registry id has exactly one `OpImpl`, that the table has no ids outside the registry, and that only Write ops have a `stale_check`.
- The CLI subcommands, MCP tools and `ops describe` output are all **generated from the `registry` crate** inside the CLI/MCP binary (§4.1), so they work without a running app. The sandbox `atlas.*` functions are generated in the worker from the Read op ids the host sends in its init frame (§9.1 step 3).
- `ops describe <id>` returns `{op_id, class, approval: "release"|"approve", params_schema, cli: {usage, positional, flags, file_variants}, defaults, caps, items_key?, field_rules, min_version, result_example, result_example_sparse, script_limits, examples: {cli, call}}`. Run locally (without `--instance`), `caps` and `script_limits` are the built-in defaults (§7.3, §7.4, §9.4), marked `limits_source: "default"`. With `--instance X` the app answers: `ops list`/`ops describe` add `available: bool` for that instance (never its version, §7.1), and `caps`/`script_limits` become the effective configured values (`limits_source: "effective"`). For every Write op the description states: "Submit human names (project, issue type, transition, user, link type, parent page); the app resolves and validates them (§5.4 step 2). Do not pre-read createmeta, transitions or assignable users; if you need metadata, fetch it in one script." Paginated ops state the §7.5 rule: continue only from `meta.page.next_start`. `atlas-duck call` always accepts the schema param names.
- **`target_display`** is defined once per op from its `target_params` and the submitted params, and is used in the queue list, the native batch-approval dialog and `requests list` (§4.4, §5.6). Keyed ops show the key or id (`ABC-123`, page `12345`). Searches show the first ~80 characters of the JQL/CQL, rendered as a text node. `script.run` shows `script · N lines`. Creates show the project or space key. It is built from agent-supplied params only, never from fetched content. The audit `target` column keeps the hashed form (`jql:<sha256>`, §8.2).
- Scripts can only reach `class == Read` entries; enforced in the app (§9.1).
- **Validation is static**: it depends only on registry data, the params, and the instance's cached version. Nothing fetched from Atlassian content influences whether validation passes or what its error text says.

### 2.4 Trust boundary (stated plainly)

- Any process running as the same OS user can reach the IPC endpoint (per the "no agent auth" decision). OS-level restrictions only exclude other users and remote hosts.
- Agent identity is informational: self-declared name, `cwd_basename`, the OS-derived peer pid/exe and the peer origin chain (§3.1), all shown and logged as **unverified**. PID→exe lookups and ancestor walks are racy and are not an authentication signal.
- **Accountable principal**: for every approved write and released read, the accountable principal is the approving OS user, acting as the owner of the instance PAT (§5.6 approver identity). Agent and peer fields are advisory attribution only. The compliance export manifest states this (§8.10).
- Request ids are **not access control**: any same-user process can enumerate them (`requests list`) and `await` any of them. Ids are random only so they cannot collide or be predicted across restarts. Every delivery is logged with the recipient (§8.3 `DELIVERED`) and multi-recipient deliveries are highlighted in the Audit window.
- **The human approval step is the security control.** DC PATs cannot be scoped; the operation registry is the only least-privilege layer.
- Approval decisions are enforced in Rust. The UI submits `{request_id, decision, candidate_rev, edits?, redactions?, reason?}`; `candidate_rev` = revision counter + hash of the exact candidate, issued by Rust with each preview it delivers. Rust rejects decisions whose `candidate_rev` is not current (`DECISION_STALE`, logged, no state change), rejects approvals/releases of a revision that was not opened or is not **approvable** (a Rust-computed property per revision, delivered with the preview; the UI's disabled Approve only mirrors it; §5.1 inv. 6) and edits that change `target_params` values or the conflict baselines (`DECISION_INVALID`, logged, no state change, §5.4 step 4), and re-validates all other edits and redactions. The "opened in this revision" state (§5.6) is tracked in Rust (Rust records delivery of the preview for a given rev to the approvals window), not in UI state. These rules are tested against the Rust decision API with a scripted approver, not only in UI component tests (§13).
- **The approvals webview is part of the trusted computing base**: code execution in it is equivalent to approval authority for every pending item. Consequently: frontend dependencies are minimal, lockfile with integrity hashes, installed with `--ignore-scripts`, no runtime remote loads; strict rendering rules (§6.4, §10.3). Per-window command grants are enforced by Tauri capability files (§10.3); every command deserializes typed arguments with serde `deny_unknown_fields` and validates bounds in Rust; the Tauri isolation hook is one global defence-in-depth filter (known command names, payload size caps) with no window context, and its iframe origin is allowed in `frame-src` of every window's CSP (§6.4, §10.3). None of these establishes user intent. Only the Rust-drawn native confirmations for security-weakening settings (§10.3; including adding an instance or changing its base URL, so a compromised webview cannot point a PAT re-entry at another origin, §7.1), the Rust-chosen paths and certificates (§10.3) and the credential-entry window hold against a compromised webview; the latter only because it runs in its own incognito (or separate data-directory) webview, from its own entry point with no chunks shared with the main bundle, no web storage, and its own CSP (§10.3) — a separate window on the shared origin and profile alone would not separate it. The native batch-approval dialog, the Rust-checked "opened in this revision" flag, per-item `candidate_rev` and the duplicate exclusion (§5.6) guard only against accidental or blind approvals. A compromised approvals webview can approve every pending item individually; containing that would need a native confirmation per approval, which conflicts with SC3 (§1.4).
- Same-user malware can also read the OS keychain; the audit encryption protects against offline theft and casual tampering, not against a compromised user session (§8.9).

### 2.5 Application lifecycle

- Tray app with no main window (every tray function is also reachable through the GUI relaunch and the Approvals header below, §5.6); autostart at login (`tauri-plugin-autostart`, `--background`; AppImage: the entry records the stable `$APPIMAGE` path, §12.3), single instance (`tauri-plugin-single-instance` — used only to forward a relaunch to the existing instance, never as agent transport; registered only for GUI and `--background` launches, never for the early-argv modes of §12.1).
- **GUI relaunch** (same on every OS, one code path, so nothing depends on a tray host): a forwarded launch with no arguments (desktop entry, app menu, `atlas-duck-app` with no args) and macOS `RunEvent::Reopen` (Dock, Spotlight, Finder) open and focus the **Approvals window** (§5.6), whose header reaches every other window and Quit; if the app is **locked**, they open the credential-entry window for unlock instead; if the app serves no store (§7.7 non-local data dir, `keyring_not_local` §8.7, `store_newer` §8.13), they re-show that state's error window (Rust-drawn, app-generated text, with a Quit button). A cold GUI start with no arguments takes the same path once startup completes (first run: the wizard below instead). A forwarded `--background` launch (CLI §4.7, autostart) opens and raises nothing.
- Closing windows hides them; the app exits only through the **shutdown path** below.
- **Shutdown path** (one code path for **Quit** from the tray, the Approvals header (§5.6), the credential-entry and error windows, the installer's quit request (§12.2) and OS end-session: `WM_QUERYENDSESSION`/`WM_ENDSESSION` on Windows, `SIGTERM`/logind `PrepareForShutdown` on Linux, `applicationShouldTerminate` on macOS):
  1. Stop accepting work: new `request.submit`/`script.submit` get `failed`, `unreachable`, `details.reason = app_shutting_down`, exit 5, `retryable: true` (nothing queued).
  2. Cancel every request that has not started executing (all pending reads, scripts awaiting release, writes in AwaitingApproval or approved but not yet sent): `CANCELLED {reason: app_quit | os_shutdown}` (Quit and the installer's quit request use `app_quit`); the agent sees `cancelled` with that `details.reason`. A read in `Fetching`, or a write whose enrichment, stale-check or refresh GET was already written, first commits the bytes received as `READ_FETCHED`/`PREVIEW_FETCH {outcome: cancelled_in_flight}` (§5.2 step 3, §5.4 step 2), then `CANCELLED`.
  3. Kill running script workers (`TerminateJobObject`/`SIGKILL`, §3.4); unlike a user kill (§9.6) the run does not become a release item: it is logged `SCRIPT_FAILED {reason: app_quit}` (non-terminal) followed by `CANCELLED {reason}`, so nothing reaches the release flow.
  4. Let only a write request already on the wire finish within its 60 s budget (§7.2) and log its outcome event (every v1 write is a single HTTP request, §5.1 inv. 3). While waiting, the app delays OS shutdown: `ShutdownBlockReasonCreate` (Windows), `NSTerminateLater` (macOS), a logind delay inhibitor lock (Linux).
  5. Flush the head anchor, append `APP_STOP {reason: quit | os_shutdown | installer}`, exit.
  Every request therefore has a terminal event after a clean exit. A hard kill or power loss falls back to startup reconciliation (§11.3).
- **Uninstall and reinstall**: see §12.5. A reinstall onto an existing data dir is not a first run (below): it continues the existing chain through §8.7 verification, or the keychain-loss path when the keychain entries are gone.
- macOS: `ActivationPolicy::Accessory` (menu-bar app). Linux: tray **menu** items (no click events on Linux trays), including "Open approvals (N)" and "Unlock…"; if no tray host is available, "badge only" behaves as "show without activating" (§5.6), so new requests always open the approvals window.
- **Tray host check** (Linux): at startup the app checks the session bus for an owner of `org.kde.StatusNotifierWatcher`; the result is recorded in `APP_START` (`tray_host: present|missing`, §8.3) and reported by `doctor` (§4.7). If it is missing (e.g. stock Fedora Workstation GNOME), the app shows a one-time hint naming the GNOME "AppIndicator and KStatusNotifierItem Support" extension and relies on the GUI relaunch above and the Approvals header (§5.6) for every tray function; dismissing the hint is UI state, not audited.
- If the app starts **locked** (passphrase mode, §8.6; or keychain lost, §8.7, where the window offers "Recover this log"), the credential-entry window (§10.3) opens for unlock automatically only at startup (also under `--background`), from the tray's "Unlock…" item and on a GUI relaunch (above). Requests that arrive while locked (refused, exit 9) only update the tray and the credential window's context header (§10.3) ("Locked — N requests refused", app-generated text) and re-raise the window at most once per 5 min, and never while it is already open.
- **Scope**: the single-instance plugin, `instance.lock` (§3.1), the app-side data-dir check (§7.7), startup hardening and the stderr redirect below apply to GUI and `--background` launches only. The early-argv modes `__cli` and `__verify-export` (§12.1) are dispatched before all of them and never become a tray instance.
- **Startup hardening** (however a GUI or `--background` launch was started), before any webview is created:
  - Release builds disable devtools and remote debugging.
  - Remove debug-channel and loader-injection variables from the app's own environment and log a warning: `--remote-debugging*` inside `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, `WEBVIEW2_USER_DATA_FOLDER`, `WEBKIT_INSPECTOR_SERVER`, `WEBKIT_INSPECTOR_HTTP_SERVER`, `LD_PRELOAD`, `GTK_MODULES`, `GIO_EXTRA_MODULES`. (`WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` is kept for fixed-version enterprise deployments.)
  - Windows: `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_APPLICATION_DIR)` early in `main`; applicable `SetProcessMitigationPolicy` settings. The process keeps the default mandatory policy (`NO_WRITE_UP | NO_READ_UP`, the default for process objects), which blocks only **lower-integrity and AppContainer subjects** (including the sandbox worker, §9.4). Ordinary same-user medium-integrity processes can still open the app with `PROCESS_VM_READ` through the default DACL; this is within the accepted same-user limits (§2.4) and no DACL hardening is added.
  - **Crash artifacts**: the release panic hook and `panic = "abort"` (§7.7); the app's own stderr goes to the null device however it was launched (GUI and `--background`; the `__cli` and `__verify-export` modes keep their stdio, §12.1). Windows: `WerAddExcludedApplication` for `atlas-duck-app.exe` and `atlas-duck-sandbox.exe` (no WER heap dumps of PATs, the KEK or previews). WebView2: the user-data folder is set through the Tauri webview configuration (never the scrubbed env var) to `<data>/webview`; its `Crashpad/reports` directory is cleared at every start and crash-report upload is disabled (mechanism verified per §15). Linux: non-dumpable (below) also suppresses core dumps.
  - Linux: `prctl(PR_SET_DUMPABLE, 0)` (blocks same-uid ptrace, `process_vm_readv` and `/proc/<pid>/mem` from the worker or other processes).
  - macOS: hardened runtime without `get-task-allow` (same-user processes cannot obtain the app's task port).
  - Memory-read protection is checked only by the §9.4 probe worker's memory-read attempt: the result is recorded in `APP_START`, shown in Settings, and **never blocks startup**. There is no separate startup self-test.
  These do not stop a same-user process from driving the UI via OS accessibility/input-injection APIs or from killing and relaunching the app — within the accepted limits (§2.4).
- **Store version gate**: first at startup, the app checks the audit DB and the anchor/vault/recovery layout versions (§8.13); a store written by a newer atlas-duck is never written (only its version markers are read). A newer `config.toml` is not part of the gate: it is read as far as known and left read-only (§7.7).
- **First run** means *no audit DB in an existing, local pinned data dir* (§7.7; a host with no pinned file of its own, e.g. a second host on an NFS-shared home, is before first run), never "keychain entries missing" and never "pinned data dir missing" (that is `not_configured`, §7.7). An existing DB whose keychain entries are missing is never treated as first run, and the app never writes a new `GENESIS` over or beside it. Instead it follows the keychain-loss path (§8.7).
- **First-run wizard** (in this order; the data dir is resolved before anything secret is asked):
  - **(0)** Resolve the data dir: the default, or the advanced override with its local-filesystem check (§7.7). Check it for an audit DB.
  - **(1a) An audit DB exists** (renamed host, unstable macOS hostname, deleted pinned file, §7.7): write this host's pinned file with the store's `install_id` (§8.6: that of the latest `RESTORE`, else `GENESIS`). Skip the recovery-passphrase step, the recovery-note step and any `GENESIS` write; the `recovery` row is left untouched (a passphrase change goes only through the normal logged change flow, `CREDENTIAL_CHANGED`, §8.6). Continue with §8.7 startup verification, or with `keychain_lost` → "Recover this log". Instance setup is skipped when `config.toml` already lists instances, apart from the native confirmation of any instance whose origin the store does not yet hold (§7.1), so otherwise only install CLI to PATH and the onboarding snippet remain.
  - **(1b) No audit DB**: optional external anchor directory (advanced; chosen before `GENESIS`, so a previous chain in it is detected, §8.5) → generate `install_id` and `chain_id` → recovery passphrase (mandatory, entered twice and confirmed, with a one-line purpose, §8.6) → write `GENESIS` → optional recovery note (offered only now, so it can include `install_id`, `chain_id` and the data-dir path, §8.6) → add instance(s) → install CLI to PATH → agent onboarding snippet.

## 3. IPC transport

### 3.1 Endpoints

**Single instance.** (GUI and `--background` launches only; the `__cli` and `__verify-export` modes, §12.1, take no lock and are never forwarded to a running instance.) The app holds an exclusive lock on `instance.lock` in the **data dir** (next to the audit DB) for its whole lifetime (`flock(LOCK_EX|LOCK_NB)` on Unix; `CreateFileW` with share mode 0 on Windows), taken before the IPC server binds and before the audit store or keychain anchor is touched. The audit store's `open()` requires the lock handle (type-enforced). The lock file records `{host, pid}` of its holder. A second app instance exits immediately; if the recorded host differs from its own, it first shows "atlas-duck is running on another machine (<host>) with this data directory". The data dir is checked to be on a local filesystem before the lock is taken (§7.7). The data-dir path never depends on per-session environment variables (§7.7).

**Endpoint discovery.** One shared function in the `ipc` crate, used by both CLI and app, computes the endpoint location (Unix: socket path; Windows: pipe-name prefix). At bind the app writes `<data>/endpoint` (user-only ACL / 0600) containing only the actual endpoint name (Windows: the pipe name). On Windows the CLI must read this file; a missing file, or a pipe name that does not start with the user's SID-derived prefix, means "not running".

**Windows** — named pipe `\\.\pipe\atlas-duck-<first 16 hex of SHA-256(user SID)>-<128-bit random>`; the random suffix is regenerated on each start (and on bind failure), so the name cannot be pre-squatted:
- Every pipe instance is created with the **same** security descriptor: protected DACL with a single ACE granting the current user SID `FILE_GENERIC_READ | FILE_GENERIC_WRITE`; no Everyone/Anonymous ACEs. `FILE_GENERIC_WRITE` includes `FILE_CREATE_PIPE_INSTANCE`; this is deliberate. Server and clients run under the same SID, so the right cannot be denied to clients without denying the server its own 2nd and later instances, and tokio `ClientOptions` can request only `GENERIC_READ`/`GENERIC_WRITE`. Pre-squatting is still prevented by the random suffix plus `first_pipe_instance(true)`. A rogue same-user instance is outside the trust boundary (§2.4); the `hello` `build_id` check (§3.3) detects only stale or foreign builds, not forgery.
- `reject_remote_clients(true)`; first instance created with `first_pipe_instance(true)`; never retried without the flag. The accept loop always keeps one listening instance (the next instance is created before a connected one is handed off); if creating an instance fails, the IPC server stops and the UI shows an error.
- Clients connect with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` set explicitly.
- Server identifies the client's user via `ImpersonateNamedPipeClient` → `OpenThreadToken(OpenAsSelf = TRUE)` → `TokenUser` → `RevertToSelf` (must equal the server's SID). Impersonation succeeds only after data has been read from the pipe, so it runs **after the `hello` frame has been read**: the frame is parsed but not acted on until the SID matches, and the 24 MiB frame cap and 5 s deadline bound it (§3.3). The sequence runs as one synchronous block with no `.await` inside it (impersonation is thread-scoped), or in `spawn_blocking`. If `RevertToSelf` fails, the process aborts. The PID → `QueryFullProcessImageNameW` lookup is for display/audit only.

**Linux** — Unix socket in `/run/user/<geteuid()>/atlas-duck/` if `/run/user/<uid>` exists, is owned by the uid and has mode 0700; otherwise `~/.local/state/atlas-duck/run-<hostname>/` (host-qualified because homes may be NFS-shared). `$XDG_RUNTIME_DIR` is not trusted for this.
**macOS** — Unix socket in `confstr(_CS_DARWIN_USER_TEMP_DIR)/atlas-duck/` (never `$TMPDIR` or `/tmp`); length checked < 104 bytes, fallback `~/Library/Caches/atlas-duck/`.
- Directory created `0700`; before binding (app) and before connecting (CLI), `lstat` verifies owner == euid, mode == 0700, not a symlink.
- Stale-socket handling: the app holds `instance.lock`, so a socket file without a live app is unlinked before binding. No `try_overwrite`.
- On accept: `peer_cred().uid() == geteuid()` or reject. pid → exe via `/proc/<pid>/exe` (Linux; the CLI is dumpable) / `proc_pidpath` (macOS) for display/audit only.
- Socket touched periodically / sticky bit set to survive runtime-dir cleanup.

**Peer origin (all OSes; best effort, advisory).** The direct peer is always the atlas-duck CLI/MCP binary (under AppImage, `atlas-duck-app` in `__cli` mode, §12.1), so at accept the server also walks the peer's ancestors (parent pid via `/proc/<pid>/stat`, `proc_pidinfo`, or a Toolhelp snapshot), up to 4 levels. It skips atlas-duck binaries (incl. the AppImage runtime and `AppRun`) and shells (`sh`, `bash`, `zsh`, `fish`, `dash`, `cmd`, `powershell`, `pwsh`) and stops at the first other process. Each hop records `{pid, start_time, exe}`. The walk stops if a parent's start time is not earlier than its child's, which guards against pid reuse. The result is `peer_chain`, stored in the encrypted payload of `REQUEST_RECEIVED` and `DELIVERED`. Its last entry is `peer_origin_exe` (+ `peer_origin_start_time`), or null if nothing was found; it is a plaintext column (§8.2). It is used for display, grouping and fairness limits (§3.3, §5.6, §8.10), never as an authentication signal (§2.4).

### 3.2 Anti-squatting (client side)

On every connection (including MCP reconnects), the CLI verifies (a) before sending any byte and (b) in the handshake, before any request:

**(a) Server owner.** Windows: the user SID of the server process token (`GetNamedPipeServerProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `OpenProcessToken` → `TokenUser`) and the pipe's owner SID (`GetSecurityInfo(OWNER_SECURITY_INFORMATION)`) must both equal the CLI's own user SID. Unix: `peer_cred().uid() == geteuid()` plus the client-side directory check (§3.1). Failure to open the server process or token counts as a mismatch.

On a mismatch the CLI sends nothing and exits 5 with `error.code = "server_identity"`.

**(b) Build match (not an identity check).** The first frame is `hello`, which carries the CLI's `build_id`; the server answers with its own and accepts only an exact match (§3.3), so a stale or foreign build is detected before any `request.submit`. There is no executable-path, file-identity or runtime signature check; the server's own pid → exe lookups of its clients (§3.1) remain for display and audit only.

**App location** (checked before connecting; used for launching, §4.7, not for identity): when `$APPIMAGE` is set (the CLI runs as `atlas-duck-app __cli` inside an AppImage, §12.1), the app location is the stable `$APPIMAGE` file itself and the next-to-CLI rule does not apply, because the CLI's canonical location lies in a per-invocation `/tmp/.mount_*` that disappears when the CLI exits. Otherwise: the `atlas-duck-app` next to the CLI's own canonical location; if not present (e.g. CLI symlinked into `~/.local/bin`), the `app_path` from `cli.toml` (written by "Install CLI to PATH", §12.3). If neither exists, the CLI sends nothing, launches nothing and exits 5 `unreachable`, `details.reason = not_running`, with the hint "atlas-duck app not found; reinstall or re-run Install CLI to PATH" — a configuration problem, not `server_identity`.

**Scope**: (a) is the only identity control; it excludes other users' endpoints and remote clients. Anything running as the same user — a rogue server on the endpoint, or binaries replaced in user-writable install locations (Windows per-user, AppImage, `~/.local`) — is outside the trust boundary (§2.4); `build_id` only turns version skew into a clear error. Release binaries stay code-signed (§12.2); `doctor` and Settings report the install mode.

### 3.3 Framing and protocol

- `u32` big-endian length-delimited frames (`tokio_util::codec::LengthDelimitedCodec`), **max frame 24 MiB** (= 16 MiB release cap + envelope/escaping headroom; §5.2). Applies to the IPC and sandbox channels.
- Payload: JSON-RPC 2.0. Methods: `hello`, `ops.list`, `ops.describe`, `instances.list`, `request.submit`, `request.await`, `request.status`, `request.cancel`, `requests.list`, `script.submit`, `doctor`. Server notification: `request.progress` (§4.5).
- `request.submit` / `script.submit` carry routing fields next to the params: `{op_id, params, instance?, reason?}`. `instance` defaults to the product's default instance and is resolved to a concrete instance id before validation (so previews and audit always show a concrete instance).
- Handshake `hello`: `{build_id, client_kind: "cli"|"mcp", agent_name, agent_name_source: "flag"|"env"|"mcp-clientInfo"|"none", cwd_basename}` (`build_id` = release version + commit, compiled into every binary; `cwd_basename` = last component of the CLI/MCP process's working directory; self-reported, **unverified**). `hello` must be the **first frame and arrive within 5 s**, or the connection is closed; any other method before `hello`, or a second `hello`, is rejected. All binaries ship together, so **`build_id` must match exactly**; on mismatch the server returns `protocol_mismatch {client_build, server_build}` and the CLI sends nothing further. If the CLI's version is newer than the server's (the app was upgraded on disk while the old one runs), it exits 5 `unreachable`, `details.reason = app_upgraded`: "atlas-duck was upgraded; restart the app". Otherwise it exits 5 `protocol_mismatch` with "atlas-duck app (vX) differs from CLI (vY): quit and relaunch the app, or reinstall". `atlas-duck mcp` does not exit on a mismatch (§4.6).
- **Agent-supplied display strings** (`agent_name`, `reason`, `cwd_basename`, MCP `clientInfo.name`) are normalized in Rust at `hello`/submit: every character flagged by the invisible-character classifier (`preview::invisible`, §6.4) is removed, plus `\t`, `\n` and `\r` (newlines are kept only in `reason`), and an "unusual characters" flag is set if anything was removed; `agent_name` ≤ 64 chars, `cwd_basename` ≤ 64 chars, `reason` ≤ 1 000 chars. The raw originals are kept in the audit payload.
- `instances.list` returns `{alias, product, is_default, state}` only — never URLs, usernames or tokens.
- Limits (fairness, not security — the key is spoofable): max 64 concurrent connections (MCP connections are long-lived) and 16 per `peer_origin_exe` (§3.1; the direct peer is always the atlas-duck CLI, so `peer_exe` would make this a global cap); max 32 pending requests per agent key (`agent_name` + `peer_origin_exe`; unnamed agents are bucketed by `peer_origin_exe`, or by MCP `connection_id` when no origin was found). A CLI connection with a null `peer_origin_exe` falls back to `peer_exe` for both limits. Max 256 pending total, and optionally `max_pending_bytes`, compared with the sum of per-request static reservations of pending reads and scripts (§5.2 memory budget; never actual candidate sizes). When a limit is reached the server still accepts the connection and answers `busy`: envelope `status: failed`, `error: {code: "busy", retryable: true, details: {retry_after_s}}`, exit 11; nothing is queued. Script-slot saturation (§9.4) is never answered with `busy`; such runs wait. The approvals UI offers "Deny all pending from this session" (§5.6).
- Frame-size or JSON errors, `hello` timeouts and ordering violations produce a JSON-RPC error (`protocol_error`, exit 1) where possible, never a silent drop; they are recorded in the diagnostic log (metadata only: connection id, peer pid/exe, reason).

### 3.4 Sandbox channel

**Spawning.** The worker is spawned by a dedicated platform routine in `sandbox-host` (not `std::process::Command`) with exactly three handles — stdin, stdout, stderr — each a pipe owned by the host:
- Windows: `CreateProcessW`/`CreateProcessAsUserW` with `STARTUPINFOEX`, `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` naming only the three pipe handles, `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` (AppContainer, §9.4), and `PROC_THREAD_ATTRIBUTE_JOB_LIST` (or created suspended → `AssignProcessToJobObject` → resumed), so it is in the job before its first instruction.
- Linux: fork from **one dedicated, long-lived spawner thread** in `sandbox-host` (never from a tokio worker or `spawn_blocking` thread): `PR_SET_PDEATHSIG` fires when the *thread* that forked the child exits, so a short-lived forking thread would kill the worker shortly after spawn. Only async-signal-safe steps in the child: `dup2` the pipes to 0/1/2, `close_range(3, ~0U, 0)`, `PR_SET_PDEATHSIG(SIGKILL)`, then `getppid()` compared with the host process's pid recorded before the fork (if the parent already died, `_exit`), `PR_SET_NO_NEW_PRIVS`, rlimits (§9.4); then exec. macOS: `posix_spawn` with `POSIX_SPAWN_CLOEXEC_DEFAULT`.
- Environment cleared to a fixed allowlist (Windows: `SystemRoot` and `TZ=UTC0`; Unix: `TZ=UTC0`, plus `MALLOC_ARENA_MAX=1` on Linux). `TZ=UTC0` keeps libc from opening `/etc/localtime` under the confinement (§9.4); scripts therefore see UTC for local-time `Date` methods (§9.2). Working directory: an empty per-run directory (Windows) or `/` (Unix). Only the canonical sandbox binary from the install dir is executed (AppImage: the install dir inside the app process's own mount, §4.7, never a CLI's mount).
- **Binary identity re-check**: the confinement probe (§9.4) records the sandbox binary's file identity (device/inode or file index, size, mtime) and its embedded version. The host re-checks both at submit (before the compile check, §9.1 step 2) and before every spawn; a mismatch found only at spawn for a `queued` run (§9.5) ends that run through the release flow like its other outcomes, so the IPC/MCP response never reveals when a slot freed (§10.2). On a mismatch (an upgrade replaced the binary under a running app, e.g. a deb/rpm upgrade on Linux) the host spawns nothing and refuses the run data-free: `failed`, exit 8, `sandbox_unavailable`, `details.reason = app_upgraded`; the tray shows "Updated — restart to apply". It is never classified as a `protocol_violation`.
- The worker exits on stdin EOF (covers app crashes; macOS has no parent-death signal).

**stderr** is read by the host, capped at 64 KiB (stderr is drained continuously; bytes past the cap are read and discarded so the worker never blocks on it), stored only in the run's encrypted audit record, shown in the approval view like `atlas.log`, and reaches the agent only through the release flow (§9.5). Never written to diagnostic logs.

**Channel rules (the host treats the worker as hostile).** Same framing and JSON-RPC types (`host.call`, `host.log`, `script.result`, `script.error`); the worker never connects to the IPC endpoint.
- Frame caps: worker→host frames ≤ 1 MiB, except one terminal frame (`script.result`/`script.error`) ≤ `max_result_mb` + 64 KiB; host→worker frames ≤ 24 MiB (call results are already bounded by `max_call_result_mb`).
- No read-side backpressure: the host **always drains** the worker's stdout and stderr, decoding one frame at a time, and writes host-call results from a **separate writer task**, so a worker that is slow to read never blocks decoding (and a worker blocked writing a log never deadlocks against a host blocked writing a result). Concurrency is enforced by **counting**: a call is outstanding from its `host.call` frame until its result has been queued for writing. A `host.call` that arrives while `max_concurrent_calls` are outstanding is a protocol violation (below); the `atlas` shim never sends one (§9.2).
- Logs: `host.log` frames are always read and counted against the per-run cap of 1 MiB and 10 000 lines; past the cap they are discarded and one `[log truncated: N bytes]` marker is kept.
- Per-run state machine: request ids unique and strictly increasing; exactly one terminal message is accepted; host calls still in flight at that moment are cancelled (results never delivered to the worker); a cancelled call whose HTTP request was already sent commits a `SCRIPT_CALL {outcome: cancelled_in_flight}` with the request params and any bytes received, and every dispatched call counts as data exposure (§9.5); frames after the terminal message are ignored and the process is reaped.
- Violations (invalid UTF-8/JSON, unknown method, oversize frame, duplicate/non-increasing id, second terminal message, response to an id the host never issued, a `host.call` beyond `max_concurrent_calls` outstanding) → the host kills the worker immediately (`TerminateJobObject` / `SIGKILL`) and records `SCRIPT_FAILED {reason: "protocol_violation"}`, classified per §9.5.
- Each worker process is bound to exactly one run id.

## 4. Agent front ends

### 4.1 CLI

Resource-style subcommands generated from the `registry` data crate (per-op `CliBinding`; parsed locally, see "Local parsing" below), plus generic forms:

```
atlas-duck jira search --jql "project=ABC AND status=Open" [--fields f1,f2] [--max 50] [--start 0]
atlas-duck jira issue get ABC-123 [--comments] [--changelog] [--fields …]
atlas-duck jira issue create --project ABC --type Bug --summary "…" --description-file - [--body-format markdown|wiki] [--field customfield_10200='{"value":"Platform"}' …] [--fields-file f.json|-]
atlas-duck confluence page get 12345 [--format markdown|storage|view]
atlas-duck confluence page update 12345 --base-version 7 --body-file page.md [--body-format markdown|storage] [--title …]
atlas-duck script run report.js|- [--args '{"project":"ABC"}'] [--limits '{"timeout_s":60}'] [--dry-run[=full|sparse]]
atlas-duck call <op-id> --params '<json>' | --params-file f.json|-
atlas-duck ops list [--instance X] | ops describe <op-id> [--instance X]
atlas-duck instances
atlas-duck await <id> | status <id> | cancel <id>
atlas-duck requests list [--agent NAME] [--state pending|recent] [--match-params-file f.json|-]   # metadata only
atlas-duck mcp [--tools full|generic] [--instance X]
atlas-duck doctor                                    # install/connectivity diagnostics (§4.7)
atlas-duck verify-export <dir> [--anchor-dir <dir>] [--manifest-sha256 <hex>]   # offline export check (§8.10, §12.1)
```

Global flags: `--agent NAME` (or `ATLAS_DUCK_AGENT`), `--reason "…"` (agent's justification, shown in the approval dialog and logged), `--timeout SECONDS` (default **100**; `0` = submit and return the pending envelope immediately), `--instance ALIAS`, `--output json|text` (default `json`).

**`--timeout` is wall-clock from CLI process start** (for submit-wait and `await`). App launch polling, the pipe-busy wait and the `hello` handshake (§3.3, §4.7) count against it: each is capped at `min(its own limit, remaining deadline)`. If the deadline expires before submission, the CLI exits 5, `unreachable`, `details.reason = launch_timeout`, with nothing queued. With `--timeout 0` the pre-submission limits apply unchanged (only the wait after submission is skipped). So the §12.4 rule "10 s below your tool's kill timeout" holds even on a cold start.

`--format` is reserved for per-op body/representation formats (e.g. `page get --format markdown`); `--output` selects CLI output rendering.

**Local parsing.** The CLI links the `registry` data crate (§2.2, §2.3). argv parsing and flag binding, `--help`, usage errors (exit 2, `usage`), stdin/file reading, and `ops list`/`ops describe` without `--instance` run **locally**: they never connect to the app and never launch it (§4.7). `verify-export` also never connects to or launches the tray app: it runs the app binary as a short-lived child in its read-only `__verify-export` mode with inherited stdio and passes its exit code through (§12.1). Only commands that need the app connect: request submission, `await`/`status`/`cancel`, `requests list`, `instances`, `doctor`, `mcp` (a long-lived IPC client, §4.6), and `ops list`/`ops describe --instance X` (instance availability and effective limits, §2.3). Schema validation of the bound params stays in the app (§5.2 step 1).

**Stdin and input encoding.**
- Stdin is read only when an argument's value is exactly `-` (`--*-file -`, `--params-file -`, `script run -`). At most one argument may be `-`; more → exit 2. With no `-`, stdin is never read.
- Input text (stdin and files) must be UTF-8; a leading UTF-8 BOM is stripped; invalid UTF-8 → exit 2 with byte offset.
- On Windows, agents should pass file paths rather than piping through PowerShell 5.1 (which re-encodes pipeline input); documented in onboarding.
- File arguments are read **by the CLI** and sent as content; the app never reads agent-specified paths. Attachment upload sends file bytes (base64) plus filename; max 10 MiB per attachment.

**`--output text`**: stdout carries a human rendering of `data`; the envelope minus `data` goes to stderr as one JSON line; exit codes are identical. JSON is the agent contract.

**Submission notice.** Immediately after the server accepts a request, the CLI writes one line to **stderr** and flushes: `{"event":"submitted","request_id":"…","params_sha256":"…","status":"pending"}` (§4.4). On SIGINT/SIGTERM/SIGHUP/CTRL_CLOSE_EVENT/broken pipe it prints the pending envelope if stdout is still writable and exits 4. It **never** cancels the request (and a SIGKILL'd CLI still leaves the id on stderr).

### 4.2 Output envelope

Every invocation prints exactly one JSON envelope to stdout (in `--output json`), including usage errors and unreachable-app cases (`request_id: null` when nothing was queued). The one exception is `verify-export`, an operator tool rather than an agent command: its stdout is the verification report and its exit codes are its own (§12.1).

```json
{
  "request_id": "req_…",
  "op_id": "jira.search",
  "instance": "jira-main",
  "status": "pending",
  "data": null,
  "edited": false,
  "redacted": false,
  "redaction_note": null,
  "message": null,
  "error": null,
  "meta": null
}
```

- `request_id` — opaque string; `req_` + ≥ 122 bits of CSPRNG randomness (not time-ordered, not monotonic); unique across restarts.
- `error` — `null` or `{code: string, retryable: bool, message: string, details?: object}`. Codes (stable, machine-readable) include: `usage`, `validation`, `markdown_placeholders` (§7.6), `op_unsupported_by_instance`, `internal`, `audit_failure`, `audit_storage_low`, `busy`, `unreachable`, `server_identity`, `protocol_mismatch`, `upstream_http`, `upstream_network`, `upstream_unavailable`, `upstream_unknown_outcome`, `result_too_large`, `needs_token`, `locked`, `not_configured`, `script_syntax`, `script_limit`, `sandbox_unavailable`, `result_evicted`, `denied`, `resolution_failed`, `expired`, `cancelled`, `abandoned`, `unknown_request`, `protocol_error`. (Runtime errors of scripts are never an `error.code`; they reach the agent only as released `data.script_error`, or directly from a data-free dry run, §9.5.) `error` is null for `executing`, `succeeded`, `released` and `pending` (except `pending` with `connection_lost`, §4.3), and non-null for every other status.
- `error.retryable` — `true` only if resubmitting the identical request **cannot duplicate an effect** and the outcome was **not** a human decision on this request, a rejection of its params, or a failed security check. The per-row value is normative in §4.3. It never says when to retry; `busy` adds `details.retry_after_s`.
- `meta` — for released reads: `{fetched_at, released_at, page?: {start, returned, total|null, truncated, next_start|null} (normative semantics §7.5), redactions?: {items_dropped, fields_dropped: [names], spans_masked}, conversion?: {lossy, lost: {macros, images, links, layouts}}}`; for script dry runs: `{dry_run: true}` (§9.5). Redaction metadata is counts and field names only — never positions or values.

**`data` shape.**
- **Reads**: `data = {result}`, where `result` is the Atlassian DC response **with field names and nesting unchanged**, pruned to the op's allowed fields, after redaction. Exceptions are documented per op (e.g. `confluence.page.get` with `format=markdown` replaces `body` with `{format: "markdown", value}`). Server-reported totals (`total`, `maxResults`, nested `comment.total`/`worklog.total`, `totalSize`) are passed through unchanged, also after redaction drops items; `meta.page` and `meta.redactions` explain gaps.
- **Writes**: `data = {receipt, executed_params?, edited_keys?}`. `receipt` is the op's static `result_projection` of the server response (Jira: `id`, `key`; Confluence: `id`, `type`, `status`, `version.number`, `_links.webui`; labels: only the labels the agent supplied; declared empty success (201/204, §7.2) → `{}`). `executed_params` and `edited_keys` appear only when `edited: true`. `executed_params` contains **only the agent's own param keys** with the user's edits applied — never app-filled values (kept title/body, resolved ids, version numbers); a key the user removed is **absent**, never `null`. `edited_keys = {changed, added, removed}` lists param names only (schema param names; for map-valued params such as Jira `fields`, the path `fields.<field id>`), never values. Values of `added` keys (incl. paths added inside an agent-supplied map such as `fields`) are not delivered, because they may come from enrichment (createmeta options, kept bodies); the agent re-reads the target if it needs them (§12.4). The full server response is audit-only. Approving a write releases its receipt: the projection is static and shown in the approval view (§5.6), and it is a listed residual channel (§10.2).
- **Write with unknown outcome**: `data = {target}`.
- **Script results**: `data = {result}` (the JSON returned by the script, after redaction) or, for released error details, `data = {script_error: {class, message, stack, elapsed, logs?}}`.
- **Script dry runs** (§9.5): `data = {result, logs}` or `data = {script_error: {class, message, stack, elapsed, logs}}`, returned without release.

| `failed` | 6 | `upstream_network` (connection-level only, before the request was written; §5.2 step 6, §5.4 step 2) and `upstream_unavailable` (reads, enrichment; only when decided from status and headers alone, §7.2; incl. `details.reason` `identity_header_missing`/`identity_header_mismatch`, §7.2 *Header lost*), returned directly; post-send enrichment timeouts, network errors, the 32 MiB cap and a JSON 2xx whose body fails to read or parse never return here (they reach the agent only as a deny hint, exit 3, §5.4 step 2); `upstream_unavailable` on write execution (3xx, §7.2); `upstream_http` (write failed after approval, or released upstream-error details — see §11.2); `result_too_large`, data-dependent `upstream_network` (read cap/budget/timeout outcomes) and body-decided `upstream_network`/`upstream_unavailable` (a read whose JSON 2xx body failed to read or parse, §7.2) — **delivered only after the user releases the outcome item** (§5.2 step 6) | `true` for directly returned `upstream_network` (pre-send, connection-level only) and `upstream_unavailable` on reads and enrichment, except `identity_header_missing`/`identity_header_mismatch` (`false`); `false` for everything else (incl. released outcome items) | null |
| `failed` | 8 | `script_syntax` (submit-time compile check), `script_limit` (only for a run that was neither `queued` nor dispatched, §9.5), `sandbox_unavailable` | `false`; `sandbox_unavailable` with `details.reason = app_upgraded`: `true` | null |
| `failed` | 9 | `locked` (`details.reason`: `passphrase`, `keychain_unavailable`, `keychain_lost`, `keyring_not_local` (the keyring's backing directory is on a network filesystem, §8.6); §8.7), `not_configured` (incl. `details.reason`: `data_dir_missing`, `data_dir_not_local`, from the CLI-side check, §7.7; `config_unreadable`, a newer `config.toml` this version cannot parse, §7.7; `insecure_scheme`, an `http://` base URL, and `instance_unconfirmed`, an instance whose origin is not yet natively confirmed, §7.1), `needs_token` | `true`; `needs_token` from write execution: `false` | null |
| `outcome_unknown` | 6 | `upstream_unknown_outcome`: write sent but outcome unknown (timeout/reset after send, 5xx, a 2xx that is not the op's declared success shape (§7.2), a Jira write response whose `X-AUSERNAME` is not the PAT's user (§7.2), crash after approval incl. during the stale check, §11.3) — **check the target before retrying** | `false` | `{target}` |
| `abandoned` | 7 | `abandoned`: request was pending when the app crashed/was killed (a write whose latest approval was not returned to the queue by `WRITE_STALE`/`WRITE_EDITED`/`WRITE_DENIED` becomes `outcome_unknown` instead, §11.3) | `true` | null |
| *(any terminal)* | 10 | outcome known, but result data no longer available (`error.code = result_evicted`) | `true` for reads/scripts; `false` for writes | null |
| `failed` | 11 | `busy` — nothing queued; retry after `retry_after_s` | `true` | null |

Agents branch on `status` + `error.code` + `error.retryable`, never on the exit code alone (§12.4). No `next_action` field exists. The matrix governs submission (submit-wait) and `await`. `status` exits 0 for any known id, whatever the status, and exits 2 (`unknown_request`) for an unknown one (§4.4). A write that reached execution is never `retryable`.

### 4.4 Timing semantics

- **Reads** are fetched immediately on submit (beyond 8 concurrent fetches they queue, §5.2 memory budget); the preview is built from the fetched data; the request then waits for release.
- A pending request is **independent of the connection** that submitted it: client disconnect or kill never cancels it. It ends only by decision, expiry, `cancel`, or the shutdown path (§2.5).
- **Expiry**: pending requests expire 24 h after **submission** (configurable 1 h–7 d); a Stale return to AwaitingApproval does not reset the timer. A fetch in flight at expiry commits its received bytes before `EXPIRED`, as for `cancel` below.
- **Approved writes** execute immediately on approval even if the CLI has stopped waiting.
- **Result retention for `await`**: released data / write receipts remain deliverable for 1 h after the decision and may be delivered **any number of times** within that window (each delivery logged, §8.3 `DELIVERED`). They are not held in memory: each delivery reads the committed `READ_RELEASED`/`SCRIPT_RELEASED` payload (writes: the `WRITE_EXECUTED`/`WRITE_FAILED` projection) and checks its hash (inv. 2). After that, `await` returns the request's true terminal status (read from the audit log's plaintext columns, for the whole retention period) with `data: null`, exit 10.
- **`await` vs `status`**: only submit-wait and `await <id>` / MCP `request_await` deliver data. `await` blocks until the request is terminal or the wait ends (`--timeout`, wall-clock as in §4.1; MCP: `ATLAS_DUCK_MCP_TIMEOUT`, §4.6), then returns per §4.3. `status <id>` / MCP `request_status` **never blocks and never carries data**: its envelope reports `request_id`, `status` and the routing fields as submitted (`op_id`, `instance`), with `data` and `meta` null; for a terminal non-success status, `error` is reduced to `{code, retryable}` with a fixed app-generated `message` ("use await for details") and no `details`; the deny reason, attached deny details, released upstream-error details and write error text come only from `await`. `status` exits 0 for any known id and is never logged as `DELIVERED`. There is no multi-id `await`; agents with several pending ids use `requests list --agent NAME` to see which are decided, then `await` those (§12.4).
- `cancel` is allowed while a request is pending (before decision); afterwards it returns the current status. The response does not depend on the internal state: a read in `Validated`/`Fetching` (the fetch is aborted), a script waiting for a slot or `Running` (the worker is killed, §9.5) and any item in `AwaitingRelease` all return the identical envelope (`cancelled`, exit 7, `details.reason = by_client`, `retryable: false`). A fetch that had already written an HTTP request (a direct read, or a write's enrichment/stale-check/refresh GET) is stopped at once and its buffered bytes are committed as `READ_FETCHED`/`PREVIEW_FETCH {outcome: cancelled_in_flight}` before `CANCELLED` (§5.2 step 3, §5.4 step 2), like `SCRIPT_CALL {cancelled_in_flight}` for scripts (§3.4). The app responds as soon as `CANCELLED` is committed: the response waits only on these bounded local audit commits of bytes already buffered, never on network I/O, on an aborted connection closing, or on a killed worker being reaped; the latency of those local commits is the §10.2 shared-resource residual. The same commit-before-terminal rule applies on expiry (`EXPIRED`) and on the shutdown path (§2.5 step 2). A cancelled request never becomes a release item.
- `requests list` returns metadata only (`request_id, op_id, instance, target_display` (§2.3)`, params_sha256, status, submitted_at`) for pending and recently decided (≤ 24 h) requests, filterable by agent name. It lets an agent whose CLI was killed or whose output was lost recover its ids. `params_sha256` = SHA-256 of the RFC 8785 (JCS) encoding of `{op_id, instance_id, params}` as submitted, after instance resolution (§3.3). For `script.run`, `params` = `{source, args, limits, dry_run?}` and `instance_id` = null. `--match-params-file` (MCP `request_list` `match_params`) sends `{op_id, params, instance?}`; the server computes its hash with the same instance resolution and returns only matching rows. Agents recover by matching, never by resubmitting (§12.4).

### 4.5 Agent-visible state (opacity rule)

Before a decision, the agent can observe only `pending`. `executing` is emitted when a write's stale check passes and execution begins; once emitted, the agent-visible status stays `executing` until a terminal state — including across a version-conflict return to AwaitingApproval (§5.4 step 6). A failed pre-execution stale check happens while the status is still `pending`. Re-approvals after staleness are therefore invisible to the agent. Before a decision, `status`, `await`, `request.progress` and MCP progress notifications carry only `{request_id, status}` and are emitted **only when the agent-visible status changes**, plus content-free heartbeats on a fixed timer (§4.6). Internal states (Fetching, AwaitingRelease, Compiling, SlotWait, Running, Enriching, Stale), whether a script was `queued`, script-slot occupancy, counts, sizes, durations, warnings, titles and staleness are never exposed in the contents of IPC/MCP responses (status stream, envelope, exit code, `details`), including through `cancel` (§4.4) and `busy` (§3.3), apart from what §10.2 enumerates. Response latency, file sizes and process counters observable by the same OS user are the §10.2 shared-resource residual. The remaining channels are enumerated in §10.2.

### 4.6 MCP server

`atlas-duck mcp` runs a stdio MCP server (official Rust SDK `rmcp`). It is another client of the app IPC — same queue, approvals, audit and semantics.

- **Tools** (`--tools full`, default): one per registry operation (name = op id with `.` → `_`, e.g. `jira_issue_get`), input schema = op params schema plus optional `reason` and `instance`; plus `script_run` (optional `dry_run: "full" | "sparse"`, §9.5), `request_await`, `request_status`, `request_cancel`, `request_list`, `ops_list`, `ops_describe`, `instances_list`.
- `--tools generic` (for clients with tool-count limits): only `call(op_id, params, reason?, instance?)`, `script_run`, `ops_list`, `ops_describe`, `instances_list`, `request_await/status/cancel/list`.
- Tool annotations: Read ops `readOnlyHint: true`; Write ops `destructiveHint` as appropriate. **No tool declares an `outputSchema`.** MCP requires `structuredContent` to conform to a declared schema, but the server returns the §4.2 envelope (`pending` with `data: null`, `denied`, redacted, script errors), which no op-specific schema matches. Without a schema, returning the envelope as `structuredContent` is valid. Result shapes are documented through `ops_describe` (`result_example`).
- **Waiting**: tool calls (including `request_await`) block up to `ATLAS_DUCK_MCP_TIMEOUT` (default **50 s**, below common 60 s client timeouts), measured wall-clock **from receipt of the tool call**: app launch polling, reconnect and the `hello` handshake count against it, each capped at `min(own limit, remaining)`, and a deadline that expires before submission returns `unreachable`/`launch_timeout` with nothing queued (as §4.1). `request_status` never blocks and carries no data (§4.4). If the client supplied a `progressToken`, the server sends a progress notification **immediately after submit** (message contains the `request_id`), a heartbeat at least every 10 s, and one on each agent-visible status change.
- On timeout: non-error result with `structuredContent` = the §4.2 envelope (`status: pending`) and text "Approval pending. Call request_await with request_id=<id>. Do not resubmit."
- `notifications/cancelled` for a tool call stops waiting only; it never cancels the queued request (only `request_cancel` does).
- Denials, expiries and failures are returned as tool results with `isError: true` and the envelope as structured content.
- Agent name = MCP `clientInfo.name` (unverified), overridable by `--agent`. `--instance X` sets the default instance for this MCP server.
- **Tool descriptions** carry the registry guidance (§2.3): paginated read tools say "continue only from `meta.page.next_start`" (§7.5); write tools say "submit human names; the app resolves them; do not pre-read metadata".
- **App restarts and upgrades**: `atlas-duck mcp` is long-lived and never exits because of the app. On `protocol_mismatch`, `unreachable` (incl. `app_upgraded`, `app_shutting_down`, `store_newer`) or a dropped connection it keeps serving stdio, answers each tool call with an `isError: true` result carrying the §4.2 envelope and the text "atlas-duck was restarted or upgraded; restart this MCP server (or your MCP client) if this persists", and re-runs the §3.2 checks and `hello` on the next tool call. Pending requests are recovered with `request_await`/`request_list`, never by resubmitting.

### 4.7 App launch and `doctor`

- **When to launch**: never for the local-only commands (§4.1 "Local parsing"), never when the CLI-side data-dir check fails (§7.7) and never when no app binary is found (§3.2 "App location"); otherwise only when the endpoint does not exist (Windows: endpoint file missing, or the named pipe returns `ERROR_FILE_NOT_FOUND`; Unix `ENOENT`, or `ECONNREFUSED` on a stale socket). On `ERROR_PIPE_BUSY` the CLI calls `WaitNamedPipeW` (raw Win32 via `windows-sys`; tokio has no wrapper) for up to 5 s, then exits 11 (`busy`) — never launches. The CLI does not launch when there is no interactive GUI session (Linux: neither `DISPLAY` nor `WAYLAND_DISPLAY`; Windows: non-interactive session/session 0; macOS: no Aqua session) and exits 5 with a hint to start the app from the desktop. A same-host SSH session of the same user therefore reaches an already running app through the pinned data dir and endpoint (`paths.toml`, §7.7; §3.1) but never launches it. Concurrent launches are serialized via a launch lock file in the data dir.
- **How to launch** (hygiene): by the canonical absolute app path located as in §3.2, passing only `--background` (agent argv never forwarded); under AppImage this is `$APPIMAGE --background` (no `__cli` marker), so the new app process gets its own mount, independent of the launching CLI's, and resolves its install dir and sandbox binary inside it (§3.4); no inherited handles; stdin/stdout/stderr on the null device (keeps MCP stdout clean); working directory = install dir (Windows) or `/`; **detached from the caller's process tree and job** so killing the agent never kills the app — macOS LaunchServices `open -n -g -a <app> --args --background`; Linux double-fork + `setsid` (and, where available, `systemd-run --user --scope` so the app also leaves the caller's cgroup); Windows as follows (creation flags alone do not change the parent PID, so a plain child would die with a `taskkill /T` of the agent's tree or a `KILL_ON_JOB_CLOSE` job):
  1. **Preferred**: `CreateProcessW` with `STARTUPINFOEX` and `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` set to the session's shell process, found via `GetShellWindow` → `GetWindowThreadProcessId` → `OpenProcess(PROCESS_CREATE_PROCESS)` and verified to run as the CLI's user SID in the same session; flags `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. The app inherits the shell's job and parentage, not the agent's. (Equivalent alternative: `IShellDispatch2::ShellExecute` obtained through the desktop folder view.)
  2. **Fallback**, only if breakaway is actually granted (checked with `IsProcessInJob`/`QueryInformationJobObject`, or by the `CreateProcess` result): a short-lived launcher stub (the CLI re-executed in an internal mode) spawns the app with `CREATE_BREAKAWAY_FROM_JOB | DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and exits at once, leaving the app orphaned.
  3. The app is **never launched inside the agent's job** (no in-process `ShellExecute`, which would stay in the job). If neither path works, the CLI exits 5 `unreachable`, `details.reason = launch_blocked_by_job`, with the hint "start atlas-duck from the desktop or enable autostart", nothing queued.
  On every OS and path, the argv rule above and the following environment rule apply: the environment is rebuilt from an explicit allowlist: `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `HOME`/`USERPROFILE`, `LANG`/`LC_*`, `TMP`/`TEMP`/`TMPDIR`, `SystemRoot`, and a system `PATH`. Proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, in every case variant) are **never** forwarded: the app takes its proxy only from its own configuration (§7.2), so a CLI-launched app behaves like a login-started one and never routes PAT-bearing traffic through the launching agent's egress proxy.
- After launching, the CLI polls the endpoint for up to 20 s, then exits 5. This poll, the 5 s `WaitNamedPipeW` wait and the `hello` round trip are each capped at the time remaining before the `--timeout` deadline (§4.1; MCP §4.6); a deadline expiry before submission exits 5 `launch_timeout`, never 11.
- `doctor` (IPC method `doctor`, §3.3) reports per instance alias only `{configured, config_error: null|insecure_scheme|instance_unconfirmed, reachable, needs_token, locked, tls_error, proxy_error: null|unreachable|auth_required, identity_header: null|ok|missing|mismatch, version_supported}` (`config_error` per §7.1; `identity_header`, Jira only, as in the §7.1 connection test and §7.2 *Header lost*) plus `pac_configured` (the OS proxy setting uses a PAC script, which is not evaluated) and local install checks (PATH, app path, IPC endpoint, `data_dir_local`, on macOS and Linux `keyring_local` (the §8.6 keyring locality check; `keyring_not_local` blocks keychain mode), on Windows `job_blocks_breakaway` (the CLI runs in a job that does not allow breakaway, so a cold start depends on the shell-parent launch path, see "How to launch"), and on Linux `wsl` = `/proc/sys/fs/binfmt_misc/WSLInterop` exists, with the warning "running inside WSL: call the Windows `atlas-duck.exe` through interop and do not install the Linux package here", §12.4). The local checks, including `data_dir_local` and whether the pinned data dir exists, are computed by the CLI itself, so `doctor` reports them even when the app refused to start (§7.7). The app additionally reports `tray_host: present|missing` on Linux (`null` elsewhere and when the app is not running; the §2.5 startup check), with the hint "no system tray: open atlas-duck from the app menu; for a tray icon enable the GNOME AppIndicator extension". No usernames, URLs, proxy hosts, server titles or version strings. The app answers from cached instance state; a fresh probe is logged as `SYSTEM_FETCH {purpose: doctor}` (§8.3).

## 5. Request lifecycle and approvals

### 5.1 State machine (in `core`)

```
Received ─validate(static)─▶ Validated            (validation failure → Rejected, exit 2)
  Read:   Validated → Fetching → AwaitingRelease(result | upstream-error | outcome) → {Released | ReleasedRedacted | Denied} → Delivered*
          Fetching → AwaitingRelease(outcome) (result_too_large from the 16 MiB release cap, the 32 MiB per-response cap or the 50 MiB fetch cap, read-budget expiry, per-call timeout or network error after the request was sent, a JSON 2xx whose body fails to read or parse; §5.2 step 6) → {Released (outcome only) | Denied}
          Fetching → Failed (READ_FAILED, data-free outcomes only: needs_token, connection-level upstream_network, upstream_unavailable decided from status and headers alone; §5.2 step 6)
  Write:  Validated → Enriching → AwaitingApproval(preview | enrichment-error | collision | unresolved-name | conflict | identity_mismatch)
              AwaitingApproval(preview) → {Approved | ApprovedEdited} → StaleCheck   (only an approvable revision, §5.1 inv. 6)
              AwaitingApproval(enrichment-error | collision | unresolved-name | conflict | identity_mismatch | no valid PAT) ─approve─▶ rejected (DECISION_INVALID {not_approvable}, no state change)
              StaleCheck → Executing → {Succeeded | Failed | OutcomeUnknown}
              StaleCheck → Stale → AwaitingApproval (changed or recheck_failed, §5.4 step 5; candidate_rev++)
              Executing → Stale → AwaitingApproval (version conflict 409/400, §5.4 step 6; candidate_rev++)
              AwaitingApproval | StaleCheck → Stale → AwaitingApproval (credential_changed: PAT replaced with another user's; instance_changed: base URL change natively confirmed, §7.1; candidate_rev++)
              AwaitingApproval → Stale → AwaitingApproval (user_renamed: same user key, new Atlassian username, §7.1; candidate_rev++)
              StaleCheck → Stale → AwaitingApproval (identity_mismatch: the pre-write identity call did not return the PAT's user, §5.4 step 5; Approve disabled until a valid PAT exists)
              AwaitingApproval ─edit─▶ AwaitingApproval (re-validated; an enrichment-relevant field re-runs enrichment, §5.4 step 4; candidate_rev++)
              AwaitingApproval ─target/baseline edit or approve of an unopened rev─▶ rejected (DECISION_INVALID, no state change)
          Enriching → Failed (REQUEST_FAILED, data-free classes only: confirmed needs_token, connection-level upstream_network before the request was written, upstream_unavailable decided from status and headers alone; §5.4 step 2)
          Enriching → AwaitingApproval(enrichment-error) (upstream HTTP error, or a post-send failure: per-call timeout, network error/reset after send, 32 MiB per-response cap, a JSON 2xx whose body fails to read or parse; Approve disabled; §5.4 step 2)
          AwaitingApproval → Denied (optionally with attached details: upstream_http | upstream_network / result_too_large outcome hint | resolution_failed | missing_fields)
  Script: Validated → Compiling (submit-time compile check in the dry-run pool, §9.5) → SlotWait → Running → AwaitingRelease(result | error-details) → {Released | ReleasedRedacted | Denied} → Delivered*
          Compiling → Failed (script_syntax, data-free, returned directly)
          Running → Failed (only when SCRIPT_FAILED has `direct = true`: a host-measured limit of a run that is neither `queued` nor dispatched, §8.3, §9.5; or audit_failure); every other Running termination except client cancel and the shutdown path (below) → AwaitingRelease
          Dry run: Validated → DryRunning (dry-run pool) → {Succeeded (result | error-details) | Failed (data-free, §9.5)}; never reaches the HTTP client or the release flow
  Any pending state → Expired | Cancelled (by_client | app_quit | os_shutdown); a client cancel in Fetching (or Enriching) aborts the fetch, commits any bytes already received as READ_FETCHED / PREVIEW_FETCH {cancelled_in_flight} before the terminal event (also on expiry and shutdown), and returns the same envelope as in AwaitingRelease (§4.4)
  StaleCheck → Cancelled only via the shutdown path (§2.5); Running → Cancelled {by_client} (kills the worker as in §2.5 step 3, §9.5) or via the shutdown path
  Infrastructure failures (audit append, internal) → Failed (REQUEST_FAILED, or the phase-specific *_FAILED event)
```

Invariants (enforced in code and property-tested):

1. **Audit-before-effect.** **No HTTP request carrying a PAT is sent unless a covering audit record is durably committed first.** This is enforced in the §7.2 client, which refuses to send without either a request id whose `REQUEST_RECEIVED`/`SCRIPT_STARTED` is committed, or a committed `SYSTEM_FETCH` start record (§8.3). In particular, each of the following side effects happens only after its audit record is durably committed: any upstream HTTP call (`REQUEST_RECEIVED` / `SCRIPT_STARTED` with full params, committed before the first call), handing a host-call response to the sandbox (`SCRIPT_CALL`), release to the agent (`READ_RELEASED`/`SCRIPT_RELEASED`), each delivery (`DELIVERED`), and execution of a write (`WRITE_APPROVED`). If the append fails, the transition fails closed (no call, no release, no execution) and the request goes to `Failed` (`audit_failure`, exit 1).
2. **No unreleased delivery.** A delivery carrying data exists only if a `READ_RELEASED`/`SCRIPT_RELEASED` record exists for that request id whose released-payload hash equals the delivered bytes' hash. Write deliveries contain only the `result_projection` of the logged `WRITE_EXECUTED` response plus the agent's own (possibly edited) params and, for an edited write, the `edited_keys` list of param names (§4.2; names only, never values of added keys); for a failed approved write, the Atlassian `errorMessages`/`errors` of the logged `WRITE_FAILED` response (capped 2 KiB, §11.2; listed in §10.2). A script dry-run delivery needs no release record: its output derives only from registry examples and agent-supplied source and args, so it is data-free (§9.5); it is logged as `SCRIPT_DRY_RUN`.
3. **Approval binds the wire.** A `WRITE_APPROVED` record stores `request_set_hash` = SHA-256 over the canonical, ordered list of exact HTTP requests (index, method, resolved URL, `Content-Type`, body bytes — after conversion and enrichment, as they will be sent), i.e. exactly what the Raw tab showed. In v1 every write op maps to exactly one HTTP request; the list form is kept. Its payload also stores that list itself (§5.4 step 4), so verification can recompute the hash (§8.7). The executor sends only requests from that list, in order, checking each against it. Only the latest approval counts, and only if no `WRITE_EDITED`/`WRITE_STALE` follows it.
   Outside approved write execution, the HTTP client permits only `GET` plus a closed, code-level allowlist of side-effect-free POSTs: **`POST /rest/api/2/search`**. Enrichment and stale checks are GET-only.
4. **Raw = released/sent.** The Raw tab shows exactly the bytes that will be released or sent. The rendered Preview may summarize, but displays a "hidden in preview: N bytes" indicator for any collapsed, truncated or placeholder region (§6.1).
5. **Decision binding.** A decision is accepted only if its `candidate_rev` equals the request's current revision. Every change to the candidate (redaction, edit, stale refresh, re-render) increments it. An approve/release is accepted only if that revision was opened (`PREVIEW_SHOWN` committed, §5.6). An edit is accepted only if its `target_params` values and conflict baselines (`base_version`, `expected`) equal the current candidate's; otherwise `DECISION_INVALID`, no state change (§5.4 step 4).
6. **Approvability.** Rust computes, per revision, whether it is approvable and delivers that with the preview; the UI's disabled Approve/Release only mirrors it. A write revision is approvable only in `AwaitingApproval(preview)` while its instance has a valid, identity-matched PAT: never in the conflict, attachment-collision, unresolved-name or enrichment-error state (incl. post-send enrichment outcomes, §5.4 step 2), never after `identity_mismatch` (incl. the identity-header states, §7.2) until a key-matched identity call has passed, and never after `credential_changed`/`instance_changed` until the instance again has a valid PAT. A read or script release is approvable only if its rebuild-hash check (§5.2 memory budget) and the mirror and every-occurrence mask checks (§5.3) pass. An approve/release (individual or batch) is accepted only if the current revision is approvable; otherwise `DECISION_INVALID {reason: not_approvable}`, logged, no state change.

### 5.2 Reads

1. Commit `REQUEST_RECEIVED` (full params), then validate (static schema + field rules + caps + instance version gate). Failure → `REQUEST_REJECTED`, exit 2, nothing queued. (Same order for writes, §5.4 step 1, and scripts, §9.1 step 2.)
2. Fetch. Paginated ops page internally up to `max` (clamped to the op's hard cap), using server-returned page sizes; total fetched bytes per read ≤ 50 MiB (exceeding it → outcome item `result_too_large`, step 6).
3. Log `READ_FETCHED` (full response, or upstream error; for an outcome item (step 6) every byte received up to the abort plus `{outcome, cap_or_budget, size, pages}`; for a Confluence body converted to Markdown also the `user_resolutions` map the `ri:user` resolution used, §7.6, which runs before this commit). The commit runs on the shared audit writer (§8.1); its latency is the §10.2 shared-resource residual.
   **Cancelled in flight**: when a read that has already written at least one HTTP request leaves `Fetching` early (client `cancel`, expiry, or the shutdown path, §2.5 step 2), the app stops the body stream at once, synchronously takes the buffered bytes (at most the 50 MiB fetch cap) and commits `READ_FETCHED {outcome: cancelled_in_flight, reason: by_client|expired|app_quit|os_shutdown, pages, size}` carrying every byte received, **before** `CANCELLED`/`EXPIRED` (in the same append batch where possible), mirroring `SCRIPT_CALL {cancelled_in_flight}` (§3.4, §9.5). The response waits only for this bounded local commit, never for network I/O or for the connection to close (§4.4). If no request had been written yet, nothing extra is logged.
4. Normalize into the release candidate (§5.3 rules), compute `meta.page`, apply the **release cap: 16 MiB** serialized JSON. Over the cap → outcome item `result_too_large` (step 6). Whether a read exceeds a cap or budget depends on what the agent's query selected, so it is never returned without release.
5. Build preview; enqueue → `AwaitingRelease`.
6. **Upstream errors** (any HTTP status ≥ 400 except 401) are release candidates too: the preview is the compact upstream-error card (§6.3) with status, capped error body and app-generated consequence lines; the user may **Release**, **Release status only**, release with other redactions, or deny. Until then the agent sees `pending`. A released upstream error is delivered as `status: failed`, exit 6, `error = {code: "upstream_http", details: {status, error_messages}}` (after redaction). "Release status only" is a one-click preset of the drop-field redaction on `error_messages` (§5.3): it yields `READ_RELEASED` with `details: {status}`, `redacted: true` and `meta.redactions.fields_dropped: ["error_messages"]`, with no new envelope shape. The app does not pre-check JQL/CQL syntax locally (plugin-provided functions make a local parser unreliable), so such errors still come from the server; the only local CQL check is the structural split that precedes the `confluence.search` type-filter rewrite (quotes, parentheses, `ORDER BY`, §7.4). **Outcome items**: every other failure whose occurrence can depend on what the query selected becomes an `AwaitingRelease` item with an outcome-only card (§6.3): `result_too_large` from the 16 MiB release cap (step 4), the 32 MiB per-response cap or the 50 MiB fetch cap (step 2, §7.2), expiry of the 120 s read budget, the 30 s per-call timeout on a request that was already sent, a network error after the request was sent, and a 2xx with a JSON `Content-Type` whose body fails to read or parse (body-decided, §7.2). The card is UI-only: cap, budget or failure hit, size or page count, the query. Its actions are **Release outcome** and **Deny**. Until then the agent sees `pending`. Release → `READ_RELEASED` with the outcome-only payload, delivered as `failed`, exit 6, `error.code = result_too_large | upstream_network | upstream_unavailable` (the last only for a JSON body that failed to parse), the fixed hint to narrow `fields`/`max`/`expand`, no size and no content; Deny → `READ_DENIED`, `denied`, exit 3.
   **Directly returned without release** (`READ_FAILED`; nothing about them depends on what the query selected): a confirmed token failure (a JSON 401, or a Jira response not attributed to the PAT's user, each confirmed by `token_recheck`, §7.1, §7.2; → `needs_token`, exit 9); a request refused by the client's origin guard (`needs_token`, exit 9, §7.2); **connection-level** failures, i.e. before the HTTP request was written (DNS, connect timeout, TLS handshake, proxy CONNECT/407; exit 6, `upstream_network`); and `upstream_unavailable` decided from status and headers alone — any 3xx, a 2xx with a non-JSON or missing `Content-Type`, a non-JSON 401, or an instance in `identity_header_missing`/`identity_header_mismatch` (exit 6, §7.2; the body is audit-only). Validation errors are rejected before any fetch (step 1).
7. User: **Release**, **Release with redactions**, or **Deny (reason)** (outcome items: **Release outcome** or **Deny**) → `READ_RELEASED` (released bytes + redaction operations) or `READ_DENIED`.

**Memory budget** (reads and scripts awaiting release):
- At most 8 direct reads are in `Fetching` at once; further reads wait in `Validated` (the agent sees `pending` either way, §4.5).
- The raw fetch is freed once `READ_FETCHED` (scripts: `SCRIPT_FINISHED`/`SCRIPT_FAILED`) is committed and the candidate is normalized. Memory then holds only queue metadata (incl. the current redaction operations and the candidate hash of `candidate_rev`) plus an **LRU cache of candidates** (`candidate_cache_mb`, default 512; Settings).
- An evicted candidate is rebuilt when it is opened or released: Rust decrypts the committed `READ_FETCHED` payload with its committed `user_resolutions` map (§7.6) (scripts: the committed `SCRIPT_FINISHED` payload, or the `SCRIPT_FAILED {direct: false}` payload that holds the error-details candidate, §8.3), re-runs the deterministic normalization with that map, re-applies the stored redaction operations and checks the result against the candidate hash of the current `candidate_rev` (inv. 4, 5). A rebuild makes no network call and never consults the live user cache or `PREVIEW_FETCH {purpose: resolve}` records. On a hash mismatch the item fails closed: Release is disabled with an `internal` banner and only Deny remains.
- Optional admission cap `max_pending_bytes` (Settings; off by default): the sum of **per-request static reservations**. Each pending read reserves, at admission, the 16 MiB release cap (or its op's static cap, if lower); each pending script reserves its static `max_result_mb` (§9.4). A reservation is freed when the request is terminal. A submit whose reservation would push the sum above the cap gets `busy` (exit 11, §3.3). Committed or actual candidate sizes are never used for admission, so `busy` depends only on the count and kind of pending requests (§10.2); actual memory stays bounded by the candidate LRU and the rebuild-from-audit path above.
- The tray tooltip and Settings show the pending count and actual pending bytes (UI only).
- Restart semantics are unchanged: pending requests become `ABANDONED` (§11.3).

### 5.3 Redaction

Operates on the structured release candidate:
- **Drop items** (issues in a result set, comments, child pages, …).
- **Drop fields** (per item or across all items).
- **Mask text** → replaced with `[REDACTED]`. By default masking replaces **every occurrence** of the selected string across all string values of the candidate, in every canonical match form (below); an option restricts it to the selected occurrence.
- **Drops never look like empty values**: a dropped field is removed as a key at every location (never `null`, an empty string or an empty array), and a dropped item is removed from its array. Masking is the only redaction that leaves a placeholder (`[REDACTED]`). Upstream `null`s are released unchanged. The same applies to script results (redacted only at release, §9.2). A key missing from an item while named in `meta.redactions.fields_dropped` therefore means "withheld", not "empty" (§12.4).

Per-op `redaction_rules` ensure copies go too. For Jira: dropping field X also drops `renderedFields.X`, `names.X`, `schema.X`, `editmeta.fields.X`, and changelog items whose `field`/`fieldId` is X.
- **Item-level mirrors**: every op whose `expand` allowlist includes `renderedFields` declares in its `redaction_rules` the arrays that `renderedFields` mirrors, e.g. `mirrors: [{src: "fields.comment.comments", dst: "renderedFields.comment.comments", key: "id"}, {src: "fields.worklog.worklogs", dst: "renderedFields.worklog.worklogs", key: "id"}]`, and every other mirrored array. An item drop on either side removes the matching entry on the other; a per-item field drop removes the same key on the mirrored entry; a per-item mask also applies to the mirrored entry; a whole-field drop of X still drops `renderedFields.X`. Entries are matched by `key`; an item without one is matched by position only when both arrays have the same length and order, otherwise the release fails closed (below).
- **Mirror check** (fail closed, before release): release is blocked with an `internal` banner if any mirror entry remains whose `fields` counterpart (field, item or per-item field) was dropped, or which has no counterpart at all.

Item drops never rewrite server totals (§4.2); `meta.page` and `meta.redactions.items_dropped` account for them (§7.5). Before release, the preview lists "also appears in: …" for selected values. **Release is blocked if a string masked in every-occurrence mode still occurs anywhere** in the candidate, in any canonical match form. For single-occurrence masks, the preview shows "N other occurrences remain" and release requires an explicit confirmation.

**Canonical match form** — one definition used for every-occurrence masking, for "also appears in: …" and for the release-blocking check:
1. Each string value is compared in its raw form and in its decoded views: HTML/XML character references decoded (named, decimal and hex); percent-decoding as UTF-8, hex matched case-insensitively, plus a view with `+` read as a space; NFC normalization of each view. The decoders are applied repeatedly until the value stops changing, at most 3 rounds; while an every-occurrence mask is active, a value still changing after the third round blocks release and is listed under "also appears in" (fail closed). The selected string is compared in NFC.
2. **URL-valued fields** declared in the op's `redaction_rules` (§2.3: `url`, `_links.*`, `self`, ancestor links): if a masked string occurs in any decoded view, the whole value is replaced with `[REDACTED]`, or (user's choice) the field is dropped and recorded in `meta.redactions.fields_dropped`.
3. **Other values**: the match is masked in the decoded view and the value re-encoded in its original encoding. If that is not possible (e.g. the match spans an encoded sequence ambiguously), it fails closed: release stays blocked and the value is listed under "also appears in: …" for the user to drop or mask by hand.
4. Any remaining decoded hit blocks release. "Also appears in" lists every released field with a hit, including fields the per-type preview does not render (§6.3).

One-click presets are plain combinations of these operations: **"Release status only"** for read upstream errors (drop field `error_messages`, §5.2 step 6) and **"Keep error class only"** for script error details (§9.5).

The agent receives `redacted: true`, `meta.redactions` (counts + dropped field names), and the optional note. The audit record stores the original fetch (`READ_FETCHED`), the redaction operations, and the released bytes.

### 5.4 Writes

1. Commit `REQUEST_RECEIVED`, then **validate** (static). Body formats converted to the native format here (Markdown → wiki markup / storage XHTML, §7.6), including the converter's re-parse hard check (an unrecorded macro, mention, include or `ri:user` → `REQUEST_REJECTED`, exit 2). Before conversion, Confluence Markdown bodies (`confluence.page.create`/`update`, `confluence.comment.add` with `body_format=markdown`) pass the **placeholder check** (§7.6): app placeholders copied from a `page get` Markdown body → `REQUEST_REJECTED`, exit 2, `error.code = markdown_placeholders`.
2. **Enrich** (GET only; logged as `PREVIEW_FETCH {purpose}`; never released to the agent): resolve names (project, issue type, transition, user, parent page), createmeta required fields, current state for diffs (fields / current storage body), current version numbers, Confluence duplicate-title check, attachment filename collision, sprint state, lossy-conversion detection (§7.6), and for a conflict (below) the agent's base version body (`GET /rest/api/content/{id}?version=<base_version>&status=historical&expand=body.storage`). Enrichment results also form the **stale-check baseline**.
   **Conflict (lost-update protection)**: the baseline must be the version the agent read, not the version at enrichment. `confluence.page.update` requires `base_version` (from `page get` `version.number`) and sends `version.number = base_version + 1`, so Confluence's own optimistic lock rejects a lost update (→ `WRITE_STALE {version_conflict}`, step 6). `jira.issue.edit` accepts an optional `expected` map `{field id: value as returned by jira.issue.get}`. If at enrichment the current version ≠ `base_version`, or a current field value differs from its `expected` value (compared like the step 5 rule), the request goes to `AwaitingApproval` with a **"conflict: changed since the agent read it"** preview (`vN → vM` and the diff between the agent's base and the current state) and Approve disabled, like the collision state. The user denies; the deny reason is pre-filled with the app-generated text "target changed since you read it; re-read and resubmit" (editable), delivered as `denied`, exit 3.
   An enrichment fetch that returns an upstream error puts the request in `AwaitingApproval` with an "enrichment failed" preview: Approve is disabled; the user may deny (reason), optionally attaching the (redactable) error details, which the agent then receives as `denied`, exit 3, `error.code = upstream_http`, `error.details`.
   **Post-send enrichment failures** go to the same "enrichment failed" state, never directly to the agent: whether an enrichment GET (fields, createmeta, current or historical storage body) times out, is reset mid-body or exceeds the 32 MiB per-response cap (§7.2) depends on the size of the content the agent chose. This covers the 30 s per-call timeout after the request was sent, a network error or reset after send, the per-response cap, and a 2xx with a JSON `Content-Type` whose body fails to read or parse (body-decided, §7.2). The `PREVIEW_FETCH` records the outcome and every byte received. Approve is disabled; Deny may attach an **outcome-only hint**: `error.code = upstream_network` (timeout, network, body-read error), `upstream_unavailable` (JSON parse failure) or `result_too_large` (cap) with a fixed app-generated message and no size, delivered as `denied`, exit 3 (§4.3). Until the decision the agent sees `pending` (§4.5).
   **Cancelled in flight**: an enrichment, stale-check or refresh GET that was already written when the request is cancelled (client, expiry, shutdown) is stopped at once and committed as `PREVIEW_FETCH {purpose, outcome: cancelled_in_flight}` with the partial response before `CANCELLED`/`EXPIRED` (§4.4, §5.2 step 3).
   **Unresolved name**: the enrichment fetch succeeded, but a project, issue type, transition, assignable user, link type or parent page named in the params has no unique match. The request goes to `AwaitingApproval` with an "unresolved name" preview (param, submitted value, match count) and Approve disabled. Deny offers an app-generated hint `{code: "resolution_failed", retryable: false, details: {param, value, message, candidates?}}`: `message` is app-generated text ("no issue type named 'Bugg' in ABC"); `candidates` (matching names, capped at 10) is Atlassian-derived, off by default, and included only if the user ticks it and may be redacted. The hint is stored in `WRITE_DENIED` and delivered as `denied`, exit 3 (§4.3). Agents therefore submit human names and never pre-read metadata (§2.3, §12.4).
   **Missing required fields** (`jira.issue.create`): every createmeta field with `required && !hasDefaultValue` that the params do not set (dedicated params or `fields`, §7.3) yields a Caution warning (§6.2) "missing required fields: Team (customfield_10200, option)". Approve stays enabled (createmeta is advisory; Jira decides). The edit form pre-adds typed inputs for the missing fields, built from the createmeta `schema` and `allowedValues`, so **Edit & approve** fixes the request in one round. Deny can pre-attach the (redactable) details `missing_fields: [{id, name, schema_type, allowed_values?}]` (`allowed_values` capped at 10 and included only if the user ticks it, like `candidates`), stored in `WRITE_DENIED` and delivered as `denied`, exit 3, `error.details.missing_fields` (§4.3).
   **Directly returned** (`REQUEST_FAILED`, exit 6 or 9; nothing about them depends on the content the agent chose): enrichment fetches classified from status and headers alone (3xx, a 2xx with a non-JSON or missing `Content-Type`, non-JSON 401, an instance in `identity_header_missing`/`identity_header_mismatch`) → `upstream_unavailable`, exit 6 (§7.2); a 2xx with a JSON `Content-Type` whose body fails to read or parse is a post-send failure (above), never returned here; connection-level failures before the request was written (DNS, connect, connect timeout, TLS handshake, proxy CONNECT/407) → `upstream_network`, exit 6; a confirmed token failure (JSON 401 or a Jira response not attributed to the PAT's user, confirmed by `token_recheck`, §7.1, §7.2) or a request refused by the origin guard (§7.2) → `needs_token`, exit 9.
3. **Enqueue** → `AwaitingApproval`.
4. User: **Approve**, **Edit & approve**, or **Deny (reason)**.
   - The edit form is generated from the op's params schema; raw-JSON editor as fallback. **Target-identifying params (`target_params`: instance, issue key, page id, project, space, parent) are read-only** — to retarget, deny with a reason. The conflict baselines `base_version` and `expected` (step 2) are read-only too. For `jira.issue.create`, missing required fields (step 2) appear as pre-added `fields.<id>` inputs. **Rust enforces the read-only rule**: an edit whose `target_params` values or conflict baselines differ from the current candidate's is rejected (`DECISION_INVALID {reason: target_param_edit}`, logged, no state change), whatever the UI sent. Other edits are re-validated (static, step 1), bodies re-converted, and an edit touching an enrichment-relevant field (a name to resolve, issue type, transition, assignee, parent, attachment filename, a body subject to the lossy check) re-runs enrichment (`PREVIEW_FETCH {purpose: enrich}`, step 2); then the request list and preview are re-rendered (`candidate_rev++`). Approval is only enabled on a valid, freshly rendered, approvable preview (Rust-enforced, §5.1 inv. 6).
   - Logged: `WRITE_EDITED` (original + edited params), `WRITE_APPROVED` with payload `{candidate_rev, request_set_hash, requests: [{index, method, resolved_url, content_type, body_bytes}]}`. This is exactly the list that was hashed and shown in Raw: converted storage XHTML/wiki markup, kept title, resolved ids and version numbers included; multipart and binary bodies are stored as base64. The `Authorization` header is never included.
5. **Stale check** immediately before execution. It always starts with the **identity check**, for every write op including those whose stale rule below is "none": the §7.1 identity call (Jira `GET /rest/api/2/myself`, Confluence `GET /rest/api/user/current`), logged as `PREVIEW_FETCH {purpose: stale_check}`, must be an identity match (§7.1: the stored `atlassian_user_key`; Confluence also `type == "known"`). Then the per-op rule:

   | Op(s) | Stale rule |
   |---|---|
   | `jira.issue.edit` | current values of exactly the edited fields equal the "before" values shown in the diff |
   | `jira.issue.assign` | current assignee equals the previewed one |
   | `jira.issue.transition` | current `status.id` equals the previewed from-status **and** the transition is still listed |
   | `jira.sprint.move_issues` | target sprint `state` still `future` or `active` |
   | `confluence.page.update`, `confluence.page.move` | `version.number` unchanged |
   | `confluence.attachment.upload` with `replace` | attachment `version.number` unchanged |
   | additive / idempotent ops (`jira.comment.add`, `jira.worklog.add`, `jira.issuelink.create`, `jira.issue.create`, `jira.backlog.move_issues`, `confluence.comment.add`, `confluence.label.add`, `confluence.label.remove`, `confluence.page.create`, plain attachment upload) | none — a vanished target surfaces as the write's own error |

   Stale-check and refresh fetches are logged as `PREVIEW_FETCH {purpose: stale_check|refresh}`. If stale → `WRITE_STALE {reason: changed}`, back to `AwaitingApproval` flagged **"Changed since you reviewed"** with refreshed enrichment and diff (`candidate_rev++`, "opened" flag cleared); the re-review leads with the baseline delta (what changed in the target since the previous review) before the refreshed diff. The return is an attention event (§5.6). Never auto-retried. A confirmed PAT identity change (§7.1) sends pending writes of that instance through the same path with `reason: credential_changed`, a natively confirmed change of the instance's base URL (§7.1) with `reason: instance_changed`, and a username rename (§7.1; writes in `AwaitingApproval` only) with `reason: user_renamed`.
   **Identity mismatch**: if the identity call returns a parsed 2xx JSON response that is not an identity match (anonymous, another user), or any Jira stale-check/refresh response fails the `X-AUSERNAME` check (§7.2), nothing is sent: `WRITE_STALE {reason: identity_mismatch}`, back to `AwaitingApproval` (`candidate_rev++`, "opened" flag cleared) with the Caution "token no longer resolves to <user>", Approve disabled until the instance again has a PAT whose identity matches, and the §7.1 `token_recheck` runs. When the token is restored ("Re-test stored token") or replaced, or a key-matched identity call confirms a rename, the write is refreshed like `credential_changed` (re-enrichment under the valid token, `candidate_rev++`). A key match with a new `name` is a rename, not a mismatch: the stored name is updated and the stale-check or refresh fetch is re-run once (§7.1 *Username rename*). If the instance has entered `identity_header_missing`/`identity_header_mismatch` (§7.2), the return is `WRITE_STALE {reason: identity_mismatch, class: identity_header_missing | identity_header_mismatch}` with the Caution "Jira did not send a matching X-AUSERNAME (possibly stripped by a reverse proxy); ask the Jira administrator" instead of the token text, since a new PAT does not help; Approve stays disabled until "Re-test stored token" clears the state.
   **Re-check failed**: any stale-check or refresh fetch that does not return a parsed 2xx JSON response (network error, timeout, 3xx, 401, 4xx, 5xx, non-JSON body, a response over the 32 MiB per-response cap, §7.2) → `WRITE_STALE {reason: recheck_failed, class}` (`class` e.g. `network`, `http_503`, `redirect`, `non_json`, `too_large`, `origin_mismatch` (refused by the §7.2 origin guard)), back to `AwaitingApproval` flagged **"Could not re-check target"** (`candidate_rev++`, "opened" flag cleared). Nothing is sent; the user may approve again later or deny. A 401 here also follows the §7.1 token rule.
   **Crash after approval**: the write is sent right after the `stale_check` `PREVIEW_FETCH` commits, so a hard kill or power loss at any point after `WRITE_APPROVED` (before a `WRITE_STALE`, `WRITE_EDITED` or `WRITE_DENIED`), including after a post-approval `DECISION_STALE`/`DECISION_INVALID`, is reconciled as `outcome_unknown`, never `ABANDONED` (§11.3).
6. **Execute** the approved request list:
   - Each outcome event (`WRITE_EXECUTED`/`WRITE_FAILED`/`WRITE_OUTCOME_UNKNOWN`) carries the `request_index` of the approved request it concerns. `WRITE_FAILED` and `WRITE_OUTCOME_UNKNOWN` (and a version-conflict return) are attention events and appear under "Needs attention" (§5.6).
   - Success (the op's declared success shape, §7.2: a JSON 2xx, or the declared empty 201/204) → `WRITE_EXECUTED` (full response and the server-reported `X-AUSERNAME`; audit only). A Jira write response whose `X-AUSERNAME` is missing, `anonymous` or another user (§7.2) is `WRITE_OUTCOME_UNKNOWN {reason: identity_mismatch, server_user}` instead (status `outcome_unknown`, "check target"), and `token_recheck` runs.
   - Server error response (4xx) → `WRITE_FAILED`. A Confluence `409`, or a `400` signalling a version conflict, is recorded as `WRITE_STALE {reason: version_conflict}` instead and returns to `AwaitingApproval`; the refreshed enrichment then sees current ≠ `base_version` and shows the conflict state, which is not approvable (step 2): Rust rejects any approval of it, individual or batch, with `DECISION_INVALID {reason: not_approvable}` (§5.1 inv. 6).
   - Timeout or connection reset **after** the request was sent, any 5xx, or a 2xx that is not the op's declared success (a non-JSON body on a `Json` op, a non-empty non-JSON body on an `Empty` op, an undeclared status; §7.2) → `WRITE_OUTCOME_UNKNOWN`; status `outcome_unknown`; never retried. Any 3xx → `WRITE_FAILED {upstream_unavailable}` (redirects are never followed, §7.2), never `WRITE_EXECUTED`. Non-GET requests are retried only on 429 (`Retry-After`) and on connection errors that occur before any byte was sent.

### 5.5 Scripts

See §9. Internal reads are executed without prompts and logged individually; only the final outcome (result or error details) goes through the release flow.

### 5.6 Approvals UI

- **Queue list**: agent name (text badge "unverified"), op id, **instance alias**, `target_display` (§2.3), the first ~60 characters of the agent's reason (or a "no reason given" badge), age, class (Read/Write/Script), stale flag, a text-labelled **"caution (N)"** badge when the item's preview has Caution-level warnings (§6.2; Info warnings never appear in the list), **"possible duplicate"** flag (any other pending item with the same `params_sha256`, §4.4, regardless of session, so a resubmission after a reconnect is still caught; the flag names the other item's session). Duplicates are flagged only; the server never coalesces them. Separately, a **"similar request"** flag marks an item when another request of the same op id and instance that matches it under the op's `similarity` rule (§2.3; listed per op in §7.3/§7.4) is pending or was decided or executed in the last 24 h, regardless of `params_sha256` and agent name:
  - `Target` (keyed ops: issue key, page id, space key, …): same `target_params` values;
  - `Create` (`jira.issue.create`, `confluence.page.create`): same project or space, same issue type or parent, **and** the same normalized summary or title (trimmed, case-folded, whitespace runs collapsed);
  - `MoveIssues`: `jira.sprint.move_issues` — same sprint id and at least one shared issue key; `jira.backlog.move_issues` — at least one shared issue key;
  - `None` (searches, ops without `target_params`, `script.run`): never flagged "similar" (exact duplicates are still caught by "possible duplicate").
  Exact value match after the stated normalization only, no fuzzy matching. It comes from the core's in-memory index of recent requests' target values, normalized summaries/titles and moved issue keys (no decrypt). After a restart the index is seeded only from the plaintext `target` column, so `Target` matches cover the last 24 h while `Create` and `MoveIssues` matches cover requests since the app started. A hit appears as a §6.2 Caution warning ("similar to req_… executed 14:02"). Routine multi-item work (several creates with different summaries, disjoint moves into one sprint) is therefore not flagged and stays batchable. Items are grouped by **session**: `agent_name` + `peer_origin_exe` (MCP: `connection_id`) + `cwd_basename`, all marked unverified. Each group has "select all from session" for batch deny.
- **Detail pane** tabs:
  - *Preview* — rendered, sanitized (§6).
  - *Structured* — item/field tree with redaction controls (reads) or the edit form (writes).
  - *Raw* — exact bytes to be released, or the exact HTTP request list to be sent (method, resolved URL, `Content-Type`, body).  - *Request* — params, `params_sha256`, agent `--reason`, instance, connection info (client kind, agent name + source, `cwd_basename`, peer pid, peer exe, peer origin chain), timestamps.
- **Executing identity**: a write's detail pane always shows "executes as <atlassian_user>" for the instance's current PAT (§7.1); after a username rename (§7.1) it shows the new name. It is verified just before execution by the identity check (§5.4 step 5); a mismatch returns the write to the queue (`identity_mismatch`) instead of sending it.
- **Write receipts**: a write's detail pane names the receipt fields the agent gets on success (the op's static `result_projection`, §4.2, e.g. "agent receives: id, key"). Approving a write releases that receipt (§10.2); no separate release step follows.
- **"Opened"** = Rust has delivered the preview of the item's current revision to the Approvals window in response to a `preview fetch` command. The UI issues that command only on explicit user navigation (click or next/prev keys while the window has focus); auto-display on a new request renders the queue list only and never fetches a preview. Any candidate change (new revision) clears the flag. The first delivery of a revision's preview commits `PREVIEW_SHOWN {candidate_rev, warning_ids, preview_builder_version}` (§8.3) **before** the preview is delivered and the flag is set; if the append fails, nothing is delivered and the flag stays clear (fail-closed, like §5.1 inv. 1). Rust rejects an approve/release of a revision whose flag is not set (`DECISION_INVALID {reason: not_opened}`, no state change, §5.1 inv. 5). This guards against blind or accidental approvals, not against a compromised webview (§2.4).
- **Keyboard**: approve/release, deny and next/prev are modifier chords, never single keys; approve/release is Ctrl/Cmd+Shift+Enter (not Ctrl/Cmd+Enter, which is "send" in common chat apps). Handlers ignore `KeyboardEvent.repeat` and accept a decision chord only after every key of the previous decision chord has been released. **No auto-advance**: after approve, release or deny, no other item opens; the next preview loads only on explicit next/prev or a click (the "opened" rule above), which starts the 1 s inert period. The deny chord opens a focused reason field; Enter in that field submits the deny and Esc cancels it. Approve/release controls and shortcuts are inert for 1 s after the window gains focus or the displayed candidate changes. After a focus the user did not request ("show and focus" mode), **all** keyboard input to the window is inert for 1 s, and initial focus goes to a non-input element (never the deny-reason field or an edit form).
- **Batch**: batch deny is always available. **Batch approve/release is enabled only when every selected item has been opened** in its current revision (checked in Rust); items flagged "possible duplicate" or "similar request" must be approved individually, never in a batch; the request carries each item's `candidate_rev`. A batch approval is **all-or-nothing**: Rust checks every item (opened in its current revision, `candidate_rev` current, not flagged, approvable per §5.1 inv. 6) before showing the dialog and again after it returns, and the UI disables batch approve for a selection containing a non-approvable item; if any item fails, the whole batch is rejected (`DECISION_STALE` for a stale revision, otherwise `DECISION_INVALID`, logged with `batch: true`), no item is decided and the UI reports which items failed. Rust shows a **native confirmation dialog** (through `NativeConfirmer`, §2.2: count, op ids, `target_display` per item, instance, and each item's Caution-level warning texts, §6.2) before applying a batch approval; Cancel changes nothing and writes no `BATCH_CONFIRMED` or `WRITE_APPROVED`. After the dialog returns OK, Rust commits `BATCH_CONFIRMED {batch_id, items: [{request_id, candidate_rev}], dialog_text_sha256}` (§8.3) before any per-item decision; if that append fails, no item is decided. Each item is then logged individually with `batch: true` and the `batch_id`. These batch rules guard against accidental approvals, not against a compromised approvals webview (§2.4).
- **Attention mode** (setting, §5.7): **"show without activating"** (default: the approvals window is shown without taking focus, Tauri `focus: false`; where the platform cannot do that, a taskbar flash, dock bounce or urgency hint instead), **"badge only"**, or **"show and focus"** (opt-in). The window is raised only on a pending-queue transition 0 → 1 or when it is hidden, at most once per 60 s. The app sends one coalesced OS toast ("N pending: x reads, y writes, z scripts"; attention only, not actionable), at most one per 30 s, and relies on the OS's own Do Not Disturb / Focus Assist handling. The tray badge/tooltip always shows the pending count. A tray **"Presentation mode"** item switches to "badge only" without confirmation. Changing the mode is logged as a plain `CONFIG_CHANGED`. **Toast, tray and header-banner text is app-generated only** (class, op id, counts) and never interpolates agent-supplied strings.
- **Header** (app-generated, above the queue, on every OS): buttons **Settings**, **Audit**, **Running scripts**, **Onboarding** and **Quit** (shutdown path, §2.5, `APP_STOP {reason: quit}`), and a status banner that mirrors every tray status line: the locked/refused count (§2.5), "Waiting for keyring" (§8.7), "Updated — restart to apply" (§3.4, §12.2) and the store version gate (§8.13; while no store is open, the §2.5 error window shows it instead), the unacknowledged "Needs attention" count (below), token expiry warnings (§7.1), low storage (§8.1), anchor/keychain-anchor write failures (§8.5, §8.8, §8.11) and the integrity-incident banner (§8.7). Its text follows the tray rule below (app-generated only, never agent-supplied strings). With no tray host (§2.5) the header and the GUI relaunch are the only path to these windows and Quit.
- **Attention events**: besides new requests, a stale return to `AwaitingApproval` (§5.4 steps 5–6) and every post-approval `WRITE_FAILED` or `WRITE_OUTCOME_UNKNOWN` trigger attention per the mode (toast or tray text); the item is pinned to the top of the queue or of "Needs attention".
- **"Recently decided (24 h) / Needs attention"** list: built from the plaintext columns behind `requests list` (§4.4; metadata only, no new decrypt path). It shows succeeded, failed (with the capped Atlassian error while it is still deliverable to `await`, §4.4, §11.2), `outcome_unknown` ("check target"), returned for re-review, and expired. Post-approval failures and unknown outcomes stay under "Needs attention" until acknowledged; the tray shows the count of unacknowledged ones. Acknowledgement is UI state in Rust (not audited) and resets on restart, where the §11.3 startup notice covers interrupted writes.
- Agent-supplied strings (name, reason) are rendered as quoted plain text in a bidi-isolated element (`unicode-bidi: isolate`), after a fixed-width, non-truncatable "unverified" badge; the "unusual characters" flag (§3.3) is shown when set. Op class and target are always displayed from the registry and validated params.
- All badges, warnings and flags are text-labelled with accessible names; colour is never the only signal.
- Approver identity recorded: OS username + the Atlassian username **and user key** bound to the instance PAT.

### 5.7 Other windows

**Settings** (instances, limits, retention/legal hold, attention mode (§5.6), CLI install, recovery/backup (with the pre-upgrade backup recommendation, §8.13), external anchor, confinement status, "Prepare for removal" (§12.5)), **Audit** (§8.10), **Running scripts** (§9.6), **Agent onboarding** (§12.4), **Credential entry** (PATs, passphrases, unlock; §10.3). Settings, Audit, Running scripts and Onboarding open from the tray menu or the Approvals header (§5.6); Rust opens each with its own capability file.

## 6. Previews

### 6.1 Principles

1. The preview is built from the **exact release candidate** (reads) or the **exact request list to be sent** (writes); the Raw tab shows those bytes verbatim (inv. 4).
2. Best effort: unknown structures fall back to a JSON tree; unknown macros to placeholders.
3. Every preview header shows: instance alias, item count ("N of total", or "N shown, more available" when the server reports no total), byte size, fields included, "hidden in preview: N bytes", and **warnings** (Caution strip and Info line, §6.2).
4. All views, including Raw, visibly mark every character flagged by the invisible-character classifier (`preview::invisible`, §6.4) and trailing whitespace, and the header counts flagged characters in two groups, **bidi controls** and **other invisible**, over the full candidate. "Confusable" marking is limited to mixed-script detection on issue keys, space keys, usernames and URL hosts (§6.4); no confusables table is applied to other text.
5. **Performance** (SC3, §1.4): the preview model is built in Rust off the UI thread, and Approve/Release stays disabled until it is ready (the "opened" flag is set only when the built preview is delivered, §5.6). Structured, Raw, diff and JSON-tree views use windowed rendering. Raw is paged on demand: Rust keeps and hashes the exact full bytes, every page is an exact slice of them (inv. 4), and header counts (principles 3–4) are computed over the full candidate, not the rendered window.

### 6.2 Warnings (non-exhaustive)

Every warning has a stable id (recorded in `PREVIEW_SHOWN`, §8.3) and one of two levels. The level follows what the warning says about **this content**, not whether the agent used default parameters (default `jira.issue.get` fields include `parent`, `issuelinks` and `security`, §7.3, but only a non-null `security` value raises a Caution).

- **Caution** — shown in a distinct, text-labelled **"Caution"** strip at the top of the preview, as a "caution (N)" badge in the queue list (§5.6), and per item in the native batch-approval confirmation (§5.6):
  "includes restricted-visibility comments" (only when a released comment has a `visibility` restriction; computed over both `fields` and its `renderedFields` mirrors, §5.3); "issue has a security level" (only when `security` is non-null); "all fields requested (`*all`)"; "contains N bidirectional control characters" and "contains N other invisible characters" (the two classifier groups, §6.4); "mixed-script identifier: <issue key / space key / username / URL host>" (§6.4); "N changes not visible in rendered diff" (raw-only diff changes, §6.3); "this update will remove N macros / M images / K links" (lossy update, §7.6); "server-rendered view: macros may include content from other pages"; "possible duplicate of req_…" and "similar to req_… executed 14:02" (§5.6); "conflict: page changed since the agent read it (v5 → v6)" (§5.4 step 2); "missing required fields: Team (customfield_10200, option)" (§5.4 step 2); "Changed since you reviewed" and "Could not re-check target" (stale, §5.4 step 5); "token changed: now executes as <user>" (§7.1); "token no longer resolves to <user>" (identity mismatch, §5.4 step 5); "Jira did not send a matching X-AUSERNAME (possibly stripped by a reverse proxy); ask the Jira administrator" (identity header lost, §7.2); "Atlassian username changed: <old> → <new>" (rename, §7.1); "instance URL changed: <old> → <new>" (§7.1).
- **Info** — one muted line in the preview header only:
  "includes summary/status of N linked/parent/sub-task issues"; "contains N custom fields"; "result truncated by cap (N of M)"; "N host calls returned truncated or lossy data" (scripts, §9.5); "body contains unknown macros"; "mention could not be resolved"; "CQL may enumerate many results"; "source formatting removed (hidden/colour styling present)" (§6.4).

Neither level gates Approve/Release (no scroll or acknowledge gate); the Caution strip and badge exist so that rare, content-specific warnings are not lost among routine ones.

### 6.4 Rendering safety

- **Preview iframe**: preview HTML is generated in Rust, sanitized with an allowlist sanitizer (`ammonia`) that **never keeps `style`/`class` attributes or `<style>` elements** (no source-derived colour, size, visibility or position survives; the wiki renderer ignores `{color}` and similar), and displayed via **`srcdoc`** in an iframe with `sandbox=""` (no tokens: no scripts, no same-origin, no forms, no popups). The document's first `<head>` element is `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src <app-origin>/preview.css; img-src data:">`, where `<app-origin>` is the explicit per-platform app origin (`tauri://localhost` on macOS/Linux, `http://tauri.localhost` on Windows; never `'self'`, which in a sandboxed document means its opaque origin). The only styling is `<link rel="stylesheet" href="<app-origin>/preview.css">`, an app-bundled file: no nonce, no inline `<style>`, no `style` attributes. The inherited main-window CSP (below) also applies to the `srcdoc` document and stays unchanged. (Equivalent alternative: a static `sha256-` hash of `preview.css` in both policies.) No remote resource is ever loaded (prevents exfiltration/tracking via image URLs). Server-rendered HTML (`--format view`) goes through the same sanitizer and is labelled as a secondary view.
- Links are shown as text (URL visible), not clickable — **everywhere**, not only in the iframe.
- **Invisible-character classifier** (`preview::invisible`; the single definition used for agent-string stripping (§3.3), preview marking and header counts (§6.1), warnings (§6.2) and escaping here): a character is flagged if it is `Default_Ignorable_Code_Point` ∪ `Cc` except `\t`, `\n`, `\r` ∪ `Zl` ∪ `Zp`. This covers Cf, bidi controls, tag characters, U+00AD, U+034F, the Hangul fillers (U+115F, U+1160, U+3164, U+FFA0), U+180B–180F, variation selectors and C0/C1 controls such as ESC and NEL. Not flagged: U+FE0E, U+FE0F and U+200D inside a well-formed (RGI) emoji sequence. Flagged characters are split into **bidi controls** (`Bidi_Control`: U+061C, U+200E–200F, U+202A–202E, U+2066–2069) and **other invisible**. The Unicode/emoji table version is part of `preview_builder_version` (§8.3), so counts are reproducible.
- Flagged characters are rendered as visible escapes such as `⟨U+202E⟩` in Preview, Raw and diff views (Raw still releases/sends the exact bytes, inv. 4); every rendered field/URL/mention is bidi-isolated (`<bdi>` / `dir=auto`). Warnings: "contains N bidirectional control characters", "contains N other invisible characters", "source formatting removed (hidden/colour styling present)".
- **Mixed-script detection** (UTS #39 mixed-script check) runs only on issue keys, space keys, usernames and URL hosts in the candidate; a hit marks the identifier and raises the Caution "mixed-script identifier" (§6.2). No confusables table is applied to prose, titles or bodies.
- **Outside the preview iframe**, all request-, agent-, Atlassian- and audit-derived content (Structured, Raw and Request tabs, diffs, script source and logs, error bodies, queue list, Audit window) is rendered as **text nodes only**. `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`, `document.write` and HTML-emitting Markdown/linkify components are banned in `ui/`, enforced in CI by ESLint (`react/no-danger`, `no-unsanitized/*`) plus a grep gate. JSON-tree, diff and code-editor components must render text nodes and must not need `eval` or blob workers.
- **Isolation origin**: with the Tauri isolation pattern (§2.4) every IPC message passes through a hidden sandboxed iframe at `<isolation-origin>`, defined per platform next to `<app-origin>` with the exact strings Tauri's `format_real_schema` emits: `isolation://localhost` on macOS/Linux, `http://isolation.localhost` on Windows (`https://isolation.localhost` when `useHttpsScheme` is set). Tauri patches that origin into `default-src` only, so every policy that sets `frame-src` (or a stricter `default-src` in a meta CSP) must name it explicitly, or every invoke hangs or fails. The `#__tauri_isolation__` iframe is hidden by a rule in the app's bundled stylesheet and in the credential page's stylesheet, because `style-src 'self'` blocks the inline `<style>` that `isolation.js` injects (equivalent alternative: a static `sha256-` hash of that style).
- **Main-window CSP** (in `tauri.conf.json`, expected to be delivered as a response header (verified per platform, §15), with Tauri's build-time hash/nonce injection): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src ipc: http://ipc.localhost; frame-src 'self' <isolation-origin>; worker-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (`<isolation-origin>` generated per platform at build time; `frame-src` stays explicit; `frame-ancestors` lives here because browsers ignore it in a meta CSP, §10.3). No `'unsafe-inline'`, no `'unsafe-eval'`; runtime CSS-in-JS style injection is not used. A CI check fails the build if the `tauri.conf.json` CSP contains `'unsafe-inline'` or `'unsafe-eval'`, or if the isolation origin is missing from `frame-src` of the main or the credential-window policy. The credential-entry window adds its own stricter policy (§10.3).

## 7. Atlassian adapters

### 7.1 Instances and setup

- Multiple instances per product, each with an alias; one default per product. Instance config (non-secret) in `config.toml` (§7.7); PAT in the keychain under `atlas-duck/<install_id>/pat/<instance-id>` (Windows persistence = Local) or in the vault (§8.6). Instance ids are random when the instance is created (never derived from the alias or URL), and every keychain entry is scoped by `install_id` (§8.6), so installs sharing a local keyring (a keyring on a network filesystem is refused, §8.6) or a `config.toml` (NFS homes, roaming profiles, §7.7) never read or overwrite each other's PAT entries; a shared instance without a PAT for this install shows `needs_token` (once its origin is confirmed for this install, below).
- Base URL includes the context path (e.g. `https://wiki.corp/confluence`) and **must use `https`**. Instance setup (Settings, first-run wizard), the credential-window connection test (§10.3) and the `config.toml` loader reject an `http://` base URL with the fixed hint "atlas-duck requires https; if your server uses an internal CA, add it as the instance's custom CA" and never send the PAT. An `http://` URL in `config.toml` leaves the instance refused with reason `insecure_scheme` (logged `CONFIG_CHANGED {source: file}`; requests to it get `not_configured`, exit 9, `details.reason = insecure_scheme`; `doctor` reports it, §4.7); the §7.2 origin guard refuses any non-https URL as a second check. There is no http toggle in v1 (one would need §10.3 security-weakening treatment and its own corroboration rule, §8.8).
- **Authoritative origin**: each instance's normalized base URL (scheme, host, port, context path) is authoritative in the audit DB, like its custom CA fingerprint and proxy (below). A differing base URL in `config.toml` is logged `CONFIG_CHANGED {source: file, old, new}` and **not applied**: the instance keeps its stored URL and PAT, nothing is sent to the new origin, and Settings shows "config.toml requests a URL change for <alias>". A base-URL change (accepted from that banner or made in Settings) applies only after a Rust-drawn native confirmation (§10.3) showing the old and new normalized origins, with a warning when the new host is a loopback address or an IP literal or differs from the old host. A **new instance** (added in `config.toml`, or created from the Settings webview or the first-run wizard) stays **unconfirmed** until its alias and normalized origin are confirmed in the same native dialog: requests to it get `not_configured`, exit 9, `details.reason = instance_unconfirmed`, and the credential window cannot be opened for it. On a shared `config.toml` (NFS home, roaming profile, §7.7) each install therefore confirms every instance, and every URL change made on another host, once before entering its PAT.
- Each stored PAT is bound to a hash of its normalized base URL (stored beside the secret). A **confirmed** change of an instance's host, port or context path deletes/invalidates the PAT, sets the instance to `needs_token`, and requires re-entry plus a passing connection test (logged `CONFIG_CHANGED` + `CREDENTIAL_CHANGED`); the loader refuses to use a PAT whose URL hash does not match, and the client attaches it only to URLs under its bound base URL (send-time origin guard, §7.2). The same change puts every non-executing write of that instance (`AwaitingApproval`, `StaleCheck`, approved but not yet sent) into `WRITE_STALE {reason: instance_changed}` (§5.4 step 5): `candidate_rev++`, "opened" flag cleared, Caution "instance URL changed: <old> → <new>" (§6.2), Approve disabled until the instance has a valid PAT again; the write is then re-enriched and its request list re-rendered under the new base URL, so Raw shows the new origin. Every script awaiting release that called the instance gets `candidate_rev++`, "opened" cleared and the same Caution, as for `credential_changed` (below). The per-instance custom CA (stored as a fingerprint) and proxy settings are authoritative in the audit DB like the audit policy (§8.8): a differing value in `config.toml` is logged as `CONFIG_CHANGED {source: file}` and not applied until confirmed in the UI (Rust-drawn confirmation, §10.3).
- Connection test (logged as `SYSTEM_FETCH {purpose: connection_test}`; later version re-detection as `{purpose: version_detect}`, §8.3):
  - Jira: `GET /rest/api/2/myself` (identity: `name`, `key`) + `GET /rest/api/2/serverInfo` (version). The `/myself` 200 must also carry `X-AUSERNAME` matching its `name` under the §7.2 username comparison; otherwise the test fails with `identity_header_missing` ("X-AUSERNAME not received, possibly stripped by a reverse proxy in front of Jira") or `identity_header_mismatch`, shown in the credential window (§10.3), and the token is not stored as working.
  - Confluence: `GET /rest/api/user/current` must be 200 **and** `type == "known"` (anonymous access also returns 200); version from `GET /rest/applinks/1.0/manifest` (`version`, `buildNumber`; present on all DC versions), cross-checked with `GET /rest/api/server-information` on 10.x. A working PAT implies ≥ 7.9.
- Version policy: refuse below PAT support (Jira < 8.14, Confluence < 7.9); warn below Jira 9.12 / Confluence 8.5. If the version stays unknown: warn once and use the most conservative behaviour for version-gated features.
- Ops may declare `min_version`; `ops list/describe --instance X` exposes `available: bool` per op plus the app's own configured limits (§2.3; app configuration, not Atlassian-derived), never the instance's version; calling an unavailable one → exit 2, `op_unsupported_by_instance` with `details: {min_version}` (the static registry value; the instance's version is never returned to agents), nothing queued.
- **401 handling**: a 401 whose body is not JSON (SSO or maintenance front ends) is `upstream_unavailable` (§7.2) and never changes the token state. A JSON 401, or a Jira response that fails the `X-AUSERNAME` check (§7.2; Jira DC answers an invalid or unknown PAT with 200 as anonymous, JRASERVER-78126), triggers one re-test of the §7.1 identity call (logged `SYSTEM_FETCH {purpose: token_recheck}`).
  - The re-test **succeeds only on an identity match**: Jira `GET /rest/api/2/myself` returns 200 with `key` equal to the stored `atlassian_user_key` and `X-AUSERNAME` matching its `name` (§7.2 username comparison); Confluence `GET /rest/api/user/current` returns 200 with `type == "known"` and `userKey` equal to the stored one. A Jira 200 with the stored key but an absent `X-AUSERNAME`, or one that does not match `name`, is not a token failure: the instance enters `identity_header_missing` or `identity_header_mismatch` (§7.2 *Header lost*). A key match with a different `name` is a rename (*Username rename*, below).
  - Any other parsed JSON response (a JSON 401; a 200 for anonymous or for another user) is a **confirmed token failure**: the instance goes to `needs_token` (logged `INSTANCE_STATE_CHANGED`) and requests to it then fail with exit 9. For another user the UI says "token now resolves to <other>".
  - If the re-test succeeds, an original JSON 401 is handled like any other 4xx (§11.2) and an original `X-AUSERNAME` mismatch is `upstream_unavailable` (§7.2), except after a detected rename, where the call is re-fetched once (*Username rename*, below); if the re-test is not a parsed JSON response (or fails at network level), the original call is `upstream_unavailable` and the token state is unchanged. A header mismatch alone never sets `needs_token`.
- **Token identity**: beside each stored PAT (with the URL hash) the app stores the identity from the connection test, `{atlassian_user, atlassian_user_key}` (Jira `name`/`key`; Confluence `username`/`userKey`). When a PAT is replaced, the connection test compares user keys. If they differ, Rust shows a native confirmation (§10.3) "This token belongs to <new>, previously <old>"; on cancel the old PAT stays. `CREDENTIAL_CHANGED` records `{old_user_key, new_user_key, expires_at?}`. On a confirmed identity change, every pending write on that instance (`AwaitingApproval`, or in `StaleCheck`) is refreshed through the §5.4 step 5 path as `WRITE_STALE {reason: credential_changed}` (refreshed enrichment under the new token, `candidate_rev++`, "opened" cleared, Caution "token changed: now executes as <new>", §6.2), and every script awaiting release that called that instance gets `candidate_rev++` with "opened" cleared and the same Caution. A write already in `Executing` finishes with the token it was sent with; later host calls of a running script use the new token, and each `SCRIPT_CALL`/`PREVIEW_FETCH` payload records the `atlassian_user_key` it ran as. The approval pane always shows "executes as <user>" for writes (§5.6).
- **Username rename**: `atlassian_user_key` (Confluence `userKey`) is the only identity anchor; `atlassian_user` is a cached comparison and display value, refreshed on every key-matched identity call. Jira DC admins, LDAP/AD sync and directory migrations can rename a user with the key unchanged. When a connection or version re-test, a `token_recheck`, "Re-test stored token" or the §5.4 step 5 identity call returns 200 with the stored key but a different `name` (Confluence `username`), and (Jira) that response's own `X-AUSERNAME` matches the new name under the §7.2 username comparison, it is an identity match: Rust updates the stored `atlassian_user` in the same transaction that logs `INSTANCE_STATE_CHANGED {user_renamed: {old, new, user_key}}` (not `CREDENTIAL_CHANGED`: token and key are unchanged). The triggering call, consistent with the response check (§7.2):
  - its original body stays audit-only and is never released retroactively;
  - a read, enrichment call or script host call is re-fetched once under the same request id (with the normal audit records); if the re-fetch still fails the check, it falls back to `upstream_unavailable` (retryable, as before);
  - a stale-check or refresh fetch is re-run once instead of returning `WRITE_STALE {identity_mismatch}`;
  - a write response is never retried: it stays `WRITE_OUTCOME_UNKNOWN {identity_mismatch, server_user}`, so the user can see it was a rename.
  Every write of that instance in `AwaitingApproval` gets `WRITE_STALE {reason: user_renamed}` (`candidate_rev++`, "opened" cleared, Caution "Atlassian username changed: <old> → <new>", §6.2), like `credential_changed` but without a native confirmation; "executes as" shows the new name (§5.6), and a write held in `identity_mismatch` becomes approvable once the key-matched identity call has passed. A different key is still a confirmed token failure (`needs_token`). §11.2 lists the rename as its own self-healing case.
- **Token expiry**: the credential-entry window (§10.3) takes an optional "token expires on" date (DC shows it when the PAT is created), stored non-secret beside the URL hash and recorded in `CREDENTIAL_CHANGED`. The tray and Settings warn 14, 7 and 1 days before it; expiry never gates requests (the server decides, §7.1 401 handling). Reading the expiry from the DC PAT REST resource instead is a §15 item.
- A 401 **never deletes the stored PAT** (only a base-URL change does, above). For a `needs_token` instance the UI offers **"Re-test stored token"** (a `token_recheck` that restores the instance only on an identity match, above) before **"Replace token"**, since DC shows a PAT only once and re-minting leaves the old token live.

### 7.2 HTTP client

- `reqwest` with rustls; trust store = OS roots + optional per-instance custom CA bundle (PEM).
- **Proxy**: the client is built with `.no_proxy()` plus at most one explicit `Proxy`. It is the per-instance override from `config.toml` (§7.1, §7.7) if set. Otherwise it is the OS static proxy setting: the WinHTTP/WinINet registry settings on Windows, SystemConfiguration on macOS, GNOME/KDE proxy settings on Linux. The **process environment (`HTTP(S)_PROXY`, `ALL_PROXY`, `NO_PROXY`) is never consulted**, so behaviour does not depend on who launched the app (§4.7). The effective proxy `host:port` per instance (never userinfo or credentials) is recorded in `APP_START` and in `CONFIG_CHANGED` when it changes. Proxy failures surface in `doctor` as `proxy_error: unreachable | auth_required` (407), and an OS setting that uses a PAC script is reported as `pac_configured`.
- Headers: `Authorization: Bearer <PAT>`, `Accept: application/json`, `User-Agent: atlas-duck/<version>` (so server access logs can tell atlas-duck traffic apart), `X-Atlassian-Token: no-check` on every non-GET.
- **Audit guard**: every send requires a covering audit record (§5.1 inv. 1): a request id with a committed `REQUEST_RECEIVED`/`SCRIPT_STARTED`, or a committed `SYSTEM_FETCH` start record. The client API cannot be called without one.
- **Origin guard** (send time, on every path: reads, pagination, enrichment, stale checks, script host calls, write execution, `SYSTEM_FETCH`): the client attaches `Authorization` only when the request URL's scheme is `https` (§7.1) and its normalized scheme + host + port + context-path prefix hashes to the PAT's bound base-URL hash (§7.1). On a mismatch (or a non-https URL) it refuses without sending and never sends the request unauthenticated: a write goes back to the queue as `WRITE_STALE {reason: recheck_failed, class: origin_mismatch}` (§5.4 step 5); direct reads and enrichment fail data-free with `needs_token`, exit 9; script host calls reject inside the script with `needs_token`.
- **Identity check on responses** (Jira): every Jira response (reads, pagination, script host calls, enrichment, stale checks, write responses) is checked before its body can become a release candidate, be handed to the sandbox or count as a write success: `X-AUSERNAME` must match the stored `atlassian_user` (§7.1) under the **username comparison**, the one function used wherever atlas-duck compares Jira usernames (this check, the §7.1 connection test, `token_recheck` and rename detection): trim the value; percent-decode it as UTF-8 only if it contains a `%XX` sequence; NFC-normalize; compare with Unicode simple case folding (Jira usernames are case-insensitive). `anonymous` never matches. A missing header, `anonymous` or another user is treated like a JSON 401: the body is audit-only (`READ_FETCHED`, `PREVIEW_FETCH`, `SCRIPT_CALL`, outcome events) and `token_recheck` runs (§7.1). If the re-check confirms a token failure, direct reads and enrichment fail data-free with `needs_token`, exit 9, and script host calls reject with `needs_token`; if it detects a rename, the call is re-fetched once (§7.1 *Username rename*); otherwise, if it passes, the outcome is `upstream_unavailable` (data-free, exit 6). Stale-check and refresh fetches return the write as `WRITE_STALE {reason: identity_mismatch}`, and a write response gives `WRITE_OUTCOME_UNKNOWN {reason: identity_mismatch}` (§5.4 steps 5–6). Confluence responses are not header-checked until §15 confirms an equivalent header; Confluence writes rely on the pre-write identity check (§5.4 step 5).
  - **Header lost**: if a Jira data response lacks `X-AUSERNAME` (or carries a value that does not match) and the re-check's `/myself` returns the stored key but its own header is likewise absent or does not match its `name`, the instance enters `identity_header_missing` (or `identity_header_mismatch`), logged `INSTANCE_STATE_CHANGED`. While in that state no agent request is sent to the instance: direct reads and enrichment fail data-free with `upstream_unavailable`, exit 6, `details.reason = identity_header_missing | identity_header_mismatch`, `retryable: false`, and the fixed admin hint "X-AUSERNAME not received, possibly stripped by a reverse proxy in front of Jira; ask the Jira administrator"; script host calls reject with the same class; pending writes show this reason (Caution, §6.2) instead of the "replace PAT" hint, with Approve disabled (§5.1 inv. 6). `doctor` reports it (§4.7). The state clears only when "Re-test stored token" (Settings, §7.1) is an identity match with the header present. Skipping the per-response check when the header is absent is not offered.
- Method guard: enforces §5.1 inv. 3 (GET + allowlisted POSTs outside approved write execution).
- **Declared write success**: each write op's registry entry declares `success: {statuses, body: Json | Empty}` (§2.3); the default is `{2xx, Json}`. `{[201], Empty}`: `jira.issuelink.create` (201 with an empty body, on Jira 10 with `Content-Type: text/html`). `{[204], Empty}`: `jira.issue.edit`, `jira.issue.assign`, `jira.issue.transition`, `jira.sprint.move_issues`, `jira.backlog.move_issues`, `confluence.label.remove`. For an `Empty` op, a declared status with an empty body (`Content-Length: 0` or zero bytes read, any `Content-Type`) is `WRITE_EXECUTED` with receipt `{}`. A non-empty non-JSON body on an `Empty` op (e.g. an HTML SSO or maintenance page), an undeclared status, and a non-JSON (or empty) 2xx on a `Json` op fall under the rule below. Each declaration is confirmed per §15.
- **Redirects and non-JSON responses**: redirect policy `none` (reqwest `redirect::Policy::none()`). Every v1 endpoint returns JSON or the empty success its registry entry declares (above). A response is `upstream_unavailable` **decided from status and headers alone** if it is any 3xx, a 2xx with a non-JSON or missing `Content-Type` (e.g. an SSO login page or a maintenance page served with 200), or a 401 whose body is not JSON (§7.1); the identity-header paths above are decided the same way. The body is stored in the audit record only (`READ_FETCHED`, `PREVIEW_FETCH`, `SCRIPT_CALL`, outcome events) and never released or shown to the agent. Effects: direct reads and enrichment fail data-free with exit 6 (§5.2 step 6, §5.4 step 2); stale checks return the request to the queue (`recheck_failed`, §5.4 step 5); script host calls reject inside the script with `upstream_unavailable`; for writes, a 3xx is `WRITE_FAILED` and a 2xx that is not the op's declared success (non-JSON on a `Json` op, non-empty non-JSON on an `Empty` op, or an undeclared status) is `WRITE_OUTCOME_UNKNOWN`, never `WRITE_EXECUTED` (§5.4 step 6). A non-JSON 4xx/5xx other than 401 is classified as before (§11.2).
  - **Body-decided failures** are not data-free: a 2xx with a JSON `Content-Type` whose body fails to parse or ends before the JSON value completes, and any body-read error (missing final chunk, short `Content-Length`, decode error). Whether they occur can depend on the content the query selected (Jira can commit a 200 and then cut the body short when a field serializer throws for one issue; parser limits such as nesting depth or lone-surrogate escapes are triggered by content), so they join the post-send path: direct reads → an outcome item (§5.2 step 6), released as `upstream_network` (body-read error) or `upstream_unavailable` (parse failure) with a fixed hint and no content; enrichment → the "enrichment failed" state, reaching the agent only as a deny hint (§5.4 step 2); stale checks and refreshes → `recheck_failed` (unchanged); script host calls → an in-script rejection after the committed `SCRIPT_CALL`, release-gated (§9.5, unchanged); writes → `outcome_unknown` (unchanged). The safety property is "any failure after a JSON `Content-Type` is gated" and does not depend on the parser. Parser hardening (e.g. decoding a lone-surrogate `\uXXXX` to U+FFFD with `meta.conversion.lossy` set, since a serde_json `String` cannot hold it losslessly, or a raised depth limit) is optional and only reduces spurious outcome items.
- Per-instance limiter: max 4 concurrent requests (shared by direct reads, enrichment and scripts); token-bucket pacing using `X-RateLimit-*` when present.
- Retries: `429` → honour `Retry-After` (each wait ≤ 30 s), max 3 retries. Non-GET: see §5.4 step 6.
- Time budgets: connect 10 s; 30 s per HTTP call; **120 s total per read request** (all pages and retries); 60 s per write. The connect timeout is a connection-level failure (data-free; direct reads: exit 6 `upstream_network`). The per-call timeout on a request that was already sent and the read budget are **not** grouped with network errors: for direct reads they become a release-gated outcome item (§5.2 step 6); for script host calls the call rejects inside the script after a committed `SCRIPT_CALL` (§9.5); for enrichment the request goes to the "enrichment failed" approval state with Approve disabled, reaching the agent only as a deny hint (§5.4 step 2); stale-check/refresh fetches return the write to the queue as `recheck_failed` (§5.4 step 5); for sent writes, `outcome_unknown`. Only enrichment failures before the request was written (DNS, connect, connect timeout, TLS handshake, proxy CONNECT/407), `upstream_unavailable` and a confirmed `needs_token` fail enrichment directly (`REQUEST_FAILED`, §11.2).
- **Pagination** is purely offset-based. Each next-page request is rebuilt from the op's own endpoint template and validated params under the configured base URL, including its context path (§7.1):
  - Confluence: `start` = previous `start` + the server-returned `size`;
  - Jira: `startAt` = previous `startAt` + the number of returned `issues`/`values`;
  - the page size is the server's `limit`/`maxResults`.
  An absent `_links.next`, `isLast`, `size < limit` or zero items, and `start + size ≥ total` serve only as end-of-results signals. `_links.next` is **never followed as a URL** (Confluence DC returns it origin-relative without the context path), so the PAT goes only to app-built URLs. This is the same arithmetic as `meta.page.next_start` (§7.5).
- Caps: 32 MiB per HTTP response; 50 MiB total fetched per paginated read. The per-response cap applies to every PAT-bearing GET, including enrichment, other `PREVIEW_FETCH` calls (stale check, refresh, resolve) and the historical-body fetch of the conflict check (§5.4 step 2). Exceeding a cap is, for direct reads, a release-gated outcome item (§5.2 step 6); for enrichment, the "enrichment failed" state (§5.4 step 2); for stale checks and refreshes, `recheck_failed {class: too_large}` (§5.4 step 5); for script host calls, an in-script rejection (§9.5).

### 7.5 Pagination for agents

Paginated read ops accept `start` (default 0) and `max` (op default; for CLI/MCP clamped to the hard cap and reported via `meta.page.truncated`; inside scripts, which never see `meta`, a `max` above the hard cap is a validation error, §9.2). They page internally up to `max`, so server clamping never reaches the agent. The released `meta.page = {start, returned, total|null, truncated, next_start|null}` mirrors the preview's "N of M". Its fields are **normative**:
- `returned` = number of items released (after redaction drops).
- `next_start` = `start` + number of items the server returned across the internal pages, before redaction (computed from the server's own `startAt`/`start` + page size arithmetic, as for internal paging, §7.2; `_links.next` is never used), or `null` when the server reports no further items.
- `truncated` = internal paging stopped because `max` or a cap was reached, not because the results ended.
- `total` = the server-reported total, unchanged, or `null` when the server reports none.
- Invariant: `returned + meta.redactions.items_dropped` = items fetched.
Agents **MUST continue only from `meta.page.next_start`**, never from `start + returned`; continuing from `start + returned` would re-request dropped items as new approvals. This rule is repeated in onboarding (§12.4), `ops describe` and the MCP tool descriptions (§2.3, §4.6). Each further page is a separate request with its own release; **for large multi-page reads agents should use a script** (`atlas.all(...)`, §9.2), which needs one release.

### 7.6 Format conversion (`convert` crate)

- **Storage XHTML → Markdown**: wrap fragment in a root declaring `ac:`/`ri:` namespaces; parse with `quick-xml` with an HTML named-entity resolver; map `ac:structured-macro` → `[macro: name {params}]` (rich-text bodies inlined, `ac:plain-text-body` CDATA → fenced code), `ac:link`/`ri:page` → `[title](confluence:SPACE/title)`, `ac:image` → `![filename](confluence:attachment/filename)`, `ri:user` (`ri:userkey` or legacy `ri:username`) → `@username` (unresolved → `@user:<key>`), `ac:task` → `- [ ]`/`- [x]`; remaining HTML → Markdown via `htmd`. Fallback on XML parse failure: extract CDATA bodies first, then html5ever-based conversion. The conversion reports `lossy` + counts of constructs reduced to placeholders. **Look-alike escaping**: source text that would match a placeholder (below) is emitted backslash-escaped (`\[macro: …`, `\@user:…`, and a genuine link whose target uses the `confluence:` scheme as escaped text), so genuine prose round-trips through the placeholder check. Golden-file tested.
  - **User resolution**: the conversion itself is a pure function that takes an explicit map and returns the map it used, `user_resolutions: {user_key → username | null}`, covering cache hits, fresh lookups and keys that stayed unresolved. The map is filled during the fetch from the per-instance cache and, for misses, `GET /rest/api/user?key=` (logged as `PREVIEW_FETCH {purpose: resolve}` under the request id, also inside script runs). It is committed with the request's own payload before the candidate hash is computed: in `READ_FETCHED` for direct reads (§5.2 step 3) and in the `SCRIPT_CALL` of a script host call. The §5.2 rebuild uses only the committed map, never the cache or the network, so cache changes after the fetch never change a candidate's hash.
- **Placeholder check** (Markdown → storage, for `confluence.page.create`/`update` and `confluence.comment.add` with `body_format=markdown`; part of §5.4 step 1 static validation): on the `pulldown-cmark` event stream the app detects (1) link or image destinations with the `confluence:` scheme, (2) Text events whose **source span** (offset iterator, so a backslash-escaped form never matches) matches the exact `[macro: <name> {…}]` grammar, and (3) `@user:<key>` tokens, likewise by source span. Any hit → `REQUEST_REJECTED`, exit 2, `error.code = markdown_placeholders`, `details.placeholders: [{kind: link|image|macro|user, count}]`, hint "fetch with `--format storage` and submit `body_format=storage`". `ops describe` for these ops documents the check; `meta.conversion.lossy` on `page get` already tells the agent that its Markdown is not round-trippable (no separate flag).
- **Markdown → Jira wiki markup** and **Markdown → storage XHTML**: `pulldown-cmark` event stream with custom renderers (headings, emphasis, lists, code blocks → `{code}` / code macro, tables, links, blockquotes). **All raw HTML and wiki-special sequences (`{`, `[`, `|`, `[~`, `!`, `\`) are escaped**, so Markdown input can never produce macros, mentions or includes. To produce macros/mentions, agents use `--body-format wiki|storage` explicitly. The preview lists every macro, mention, include and link target present in an outgoing payload.
  - **Code bodies** (fenced/indented code, inline code spans) cannot be escaped inside their container, so the container is chosen by content. Jira: `{code}`; `{noformat}` if the content contains `{code`; if it contains both `{code` and `{noformat`, escaped monospace paragraphs (`{{…}}` per line with every wiki-special sequence escaped). Storage: `ac:plain-text-body` CDATA with every `]]>` split as `]]]]><![CDATA[>`.
  - **Hard check** (for `body_format=markdown`, part of §5.4 step 1 validation): the converter records every construct it emits itself (its code containers and code macros). The outgoing wiki markup / storage XHTML is then re-parsed with the app's own parser (the wiki→preview renderer's parser for Jira, the storage parser above for Confluence). Any macro, mention, include or `ri:user` that the converter did not record fails validation: `REQUEST_REJECTED`, exit 2, `validation`, nothing queued. The check depends only on the params, so validation stays static (§2.3).
- **Lossy updates**: for `confluence.page.update` with `body_format=markdown`, enrichment compares the current storage body with the outgoing storage; if constructs (`ac:structured-macro`, `ac:image`, `ac:link`, `ri:*`, `ac:layout`) would be lost, the preview shows the Caution warning (§6.2) "this update will remove N macros / M images / K links". `ops describe confluence.page.update` advises `body_format=storage` for pages where `get` reported `meta.conversion.lossy = true`.
- **Wiki markup → preview HTML**: local best-effort renderer (headings, emphasis, lists, tables, `{code}`/`{noformat}`, `{quote}`, links as text, `{panel}` etc. as labelled blocks; unknown macros as placeholders).

### 7.7 Configuration, paths, diagnostics

- **Config** `config.toml` (with `schema_version`, migrated additively per §8.13; cross-version rules below) in the per-OS config dir (Windows `%APPDATA%\atlas-duck`, macOS `~/Library/Application Support/atlas-duck`, Linux `$XDG_CONFIG_HOME/atlas-duck`). Holds instances (alias, product, base URL, CA bundle path, proxy), UI preferences, limits. **Audit policy (retention, legal hold, external anchor dir) is authoritative in the audit DB**, not in the config file (§8.8); so are each instance's normalized base URL, custom-CA fingerprint and proxy, and a new or changed instance in the file takes effect only after a native confirmation (§7.1). On Windows `config.toml` may roam with the profile; a roamed instance whose PAT is not in this machine's keychain (persistence = Local) shows `needs_token`.
- **Machine-local files**: `paths.toml` and `cli.toml` hold machine-specific paths, so on Windows they live in `%LOCALAPPDATA%\atlas-duck` (never the roaming `%APPDATA%`). On macOS and Linux, where the home (and with it the config dir and the keyring files) may be NFS-shared, they are **host-qualified** like the §3.1 socket-dir fallback: `paths-<hostname>.toml` and `cli-<hostname>.toml` in the passwd-home-derived config dir, with `<hostname>` from the same shared `ipc` function as §3.1. Elsewhere in this spec, `paths.toml`/`cli.toml` denote this host's own pinned files. A host with no pinned file of its own is **before first run** and runs the wizard, even if another host's files sit beside it; a missing data dir named in this host's own pinned file is still `not_configured` (below). If the wizard is pointed at a local data dir that already holds an audit DB, that is not a first run (§2.5): the store's `install_id` is read (that of the latest `RESTORE`, else `GENESIS`, §8.6) and the normal verification or keychain-loss path follows (§8.7). The wizard resolves and checks the data dir before it asks for any recovery passphrase (§2.5 step (0)), so this path never prompts for or writes a passphrase or recovery note. A renamed host therefore runs the wizard again and continues its existing chain this way. Each pinned `paths.toml` also records the `install_id` of the store it pins (§8.6).
- **Cross-version sharing of `config.toml`** (roaming on Windows, NFS homes elsewhere): config migrations are additive only (never renaming, removing or reinterpreting a key; a breaking change keeps the old key beside the new one), so an older binary can read a newer file. An older binary that finds a newer `schema_version` reads the keys it knows, ignores the rest and treats the file as **read-only** (it never rewrites, migrates or downgrades it); settings and instance edits are disabled with the banner "config written by vX; settings read-only until you upgrade" (also in `doctor`), and requests keep working. A newer-schema file that does not parse gets the banner "config written by vX could not be read; upgrade atlas-duck", is left untouched, and the app runs with no instances from it (requests `not_configured`, exit 9, `details.reason = config_unreadable`). Either state is recorded once per start in `APP_START {config_read_only: {schema_version, parsed}}` (non-incident). The audit store version gate (§8.13) never looks at `config.toml`.
- **Data dir** default: `%LOCALAPPDATA%\atlas-duck`, `~/Library/Application Support/atlas-duck`, `$XDG_DATA_HOME/atlas-duck`; overridable only in the first-run wizard (advanced step). **Local filesystem only, enforced**: at first run and at every start, before taking `instance.lock` (§3.1), the app checks the data dir's filesystem (Linux `statfs` `f_type` against the network/FUSE types listed per §15; macOS `statfs` `MNT_LOCAL`; Windows `GetDriveTypeW` on the volume root, and UNC paths refused). A non-local data dir is refused: the wizard requires a local path, and at a later start the app opens no store, binds no IPC and shows the error in the tray and a window. SQLite WAL and `flock` are unsafe on network filesystems, and two hosts could otherwise share one DB. The same check guards the keyring backing directories in keychain mode (§8.6 *Keyring locality*).
- **Path stability**: base folders are resolved from OS known-folder APIs / the passwd home directory, not per-session environment. XDG overrides and the data-dir override are honoured only at first run and then pinned in `paths.toml` (at the home-derived default location above), which both the app and the CLI read — so differently-configured sessions (SSH, `systemd --user`, IDE sandboxes) always find the same data dir, lock and endpoint file. A pinned data dir that does not exist (unmounted drive, removed folder) is **not configured**, never a fresh store: the app shows "data directory <path> not found" and does not run the first-run wizard or write anything (§2.5).
- **CLI-side data-dir check**: when this host's `paths.toml` exists (a pinned data dir), before connecting or launching, the CLI resolves the data dir through the same shared function (§3.1) and applies the same existence and local-filesystem checks; with no `paths.toml` (before first run) the CLI launches the app as before and the wizard enforces locality. A missing or non-local pinned data dir → `failed`, exit 9, `not_configured`, `details.reason = data_dir_missing | data_dir_not_local`, no launch, nothing queued (§4.3).
- **`cli.toml`** (non-secret; machine-local, above): `app_path`, written by "Install CLI to PATH" and removed by "Prepare for removal" (§12.5).
- **Uninstallers never touch** the data dir, config dir, `paths.toml`, the external anchor dir or keychain entries (§12.5).
- **Diagnostic log** (`tracing`, rolling files under `<data>/logs`, 10 MiB × 5, ≤ 7 days): metadata only — op id, request id, instance alias, HTTP method, path template, status code, duration, error class. **Never** headers, query strings, JQL/CQL, params, request/response bodies, titles, keys or Atlassian error text, at any log level; no setting enables body logging.
- **Panics**: release builds use `panic = "abort"` and a panic hook that writes only `file:line`, the thread name and a static category to the diagnostic log, **never the panic payload** (which may carry `Debug`-formatted params or responses). A panic is a hard kill and falls under §11.3 reconciliation. Request, params and response types in `atlassian` and `core` (incl. `reqwest` error wrappers) implement a redacting `Debug` (like the §10.1 secret type), and CI runs `clippy::unwrap_used`/`expect_used` as errors on those crates (§13).
- **Support artifacts** are `atlas-duck doctor` output (JSON) and the diagnostic logs only. The documentation tells users never to send the audit DB, exports, backups, `<data>/webview` or preview screenshots.

## 8. Audit log

### 8.1 Storage

- SQLite via `rusqlite` (bundled). Single writer thread in the app; CLI and sandbox never open the DB. Every agent response waits for at least one commit on this writer, so large commits delay responses queued behind them; that latency is the §10.2 shared-resource residual. Engineering note (not a security guarantee): zstd compression and AES-GCM encryption run off the writer thread, so the writer only appends prepared rows, to limit head-of-line delay.
- Pragmas: `journal_mode=WAL`, `synchronous=FULL`, `secure_delete=ON`, `page_size=8192`, `auto_vacuum=INCREMENTAL`. After each prune: `PRAGMA incremental_vacuum` then `wal_checkpoint(TRUNCATE)`.
- **Low-space admission**: before accepting a request, free space on the DB volume must exceed a threshold (default `max(2 GiB, 4 × 24 MiB)`). Below it, new agent requests are refused (`audit_storage_low`, exit 1) with a UI/tray warning; system events and pruning continue within the headroom.

### 8.2 Schema (main table `events`)

| Column | Encrypted? | Content |
|---|---|---|
| `seq` INTEGER PK | no | monotonic |
| `format_version` | no | canonical encoding version (§8.4) |
| `chain_id` | no | random per installation segment (§8.11) |
| `ts_utc` | no | wall clock, RFC 3339 ms |
| `epoch` | no | UTC date, **non-decreasing and corroborated**: `max(prev_epoch, min(today_utc, corroborated_date))` (§8.8); with no corroboration yet in this process, `prev_epoch`; `GENESIS` takes `today_utc` |
| `request_id`, `event_type` | no | |
| `op_id`, `op_class`, `instance_id` | no | |
| `target` | no | issue key / page id / space key / `jql:<sha256>` / `cql:<sha256>`; for `GENESIS`, `RESTORE` and `APP_START` the `install_id` of the install that wrote them (§8.6), so the store's `install_id` is readable before the KEK |
| `agent_name`, `agent_name_source`, `client_kind`, `connection_id`, `peer_pid`, `peer_exe`, `peer_origin_exe` | no | unverified identity (`peer_origin_exe` from the ancestor walk, §3.1; full `peer_chain` and `cwd_basename` only in the encrypted payload) |
| `os_user`, `atlassian_user`, `atlassian_user_key` | no | approver/actor (script releases: null; instances listed in payload) |

### 8.3 Event types

- **Lifecycle**: `REQUEST_RECEIVED` (full params, `params_sha256`, connection info incl. `cwd_basename` and `peer_chain`, §3.1), `REQUEST_REJECTED` (terminal), `REQUEST_FAILED {code}` (terminal; data-free enrichment-phase failures only — confirmed `needs_token`, connection-level `upstream_network` before the request was written, `upstream_unavailable` decided from status and headers alone (§5.4 step 2, §7.2) — and `internal` errors), `PREVIEW_FETCH {purpose: enrich|stale_check|refresh|resolve, method, path, status, full response | outcome}` (every app-initiated GET under a request id that is not released: enrichment, stale checks, name/user/field resolution; `outcome: timeout|network|too_large|unparsable|cancelled_in_flight` with every byte received for a GET that did not complete or whose JSON body failed to parse, §5.4 step 2, §4.4), `DECISION_STALE {submitted_rev, current_rev, decision, batch}` (non-terminal; a rejected decision, or a batch rejected because an item's revision was stale), `DECISION_INVALID {reason: target_param_edit | not_opened | not_approvable | batch_item_flagged, submitted_rev, decision, batch}` (non-terminal; a decision rejected by the Rust rules of §5.1 inv. 5–6, §5.4 step 4 and §5.6; no state change), `PREVIEW_SHOWN {candidate_rev, warning_ids, preview_builder_version}` (non-terminal; committed before Rust first delivers a revision's preview to the Approvals window, i.e. when "opened" is set, §5.6), `BATCH_CONFIRMED {batch_id, items: [{request_id, candidate_rev}], dialog_text_sha256}` (`request_id` null; committed after the native batch dialog returns OK and before the per-item decisions, which carry `batch_id`, §5.6), `DELIVERED` `{connection_id, client_kind, agent_name(+source), cwd_basename, peer_pid, peer_exe, peer_chain, payload_sha256}` (on every hand-off: submit-wait, `await`, MCP `request_await`; never for `status`, §4.4). `PREVIEW_SHOWN` and `BATCH_CONFIRMED` add no plaintext columns; their fields are payload only.
- **Reads**: `READ_FETCHED` (with the `user_resolutions` map of a Markdown-converted Confluence body, §7.6; for an outcome item also `{outcome, cap_or_budget, size, pages}` beside the bytes received; for a read aborted in `Fetching` `{outcome: cancelled_in_flight, reason: by_client|expired|app_quit|os_shutdown, pages, size}` with every byte received, committed before `CANCELLED`/`EXPIRED`; §5.2 step 3), `READ_RELEASED` (for an outcome item an outcome-only payload `{code, hint}`), `READ_DENIED`, `READ_FAILED` (terminal; data-free outcomes only: `needs_token`, connection-level `upstream_network`, `upstream_unavailable` decided from status and headers alone, §5.2 step 6, §7.2).
- **Writes**: `WRITE_EDITED`, `WRITE_APPROVED` (`{candidate_rev, request_set_hash, requests}`, §5.4 step 4), `WRITE_DENIED` (incl. the attached hint, if any: enrichment-error details, the post-send enrichment outcome hint, `resolution_failed` or `missing_fields`, §5.4 step 2), `WRITE_STALE {reason: changed|recheck_failed|version_conflict|credential_changed|identity_mismatch|instance_changed|user_renamed, class?}` (`class` incl. `origin_mismatch`, §7.2, and for `identity_mismatch` `identity_header_missing|identity_header_mismatch`, §5.4 step 5), `WRITE_EXECUTED` (incl. the server-reported `X-AUSERNAME` on Jira, §5.4 step 6), `WRITE_FAILED`, `WRITE_OUTCOME_UNKNOWN` (`reason` incl. `crash`, `identity_mismatch {server_user}`) (outcome events carry `request_index`).
- **Scripts**: `SCRIPT_STARTED` (source + args + limits + `queued`, §9.1 step 2), `SCRIPT_CALL_SENT {call_id, op_id, instance}` (non-terminal; committed before the run's first HTTP request, marks the run dispatched, §9.5), `SCRIPT_CALL` (each internal read: op, params, instance, full response or failure outcome incl. network error, per-call timeout, size overrun and `cancelled_in_flight` with any bytes received, §3.4; the `user_resolutions` map of a Markdown conversion, §7.6), `SCRIPT_FINISHED` (the worker's result or error details, logs and captured stderr: the source of the release candidate, §5.2 memory budget), `SCRIPT_FAILED {reason, queued, dispatched, data_free, direct: bool}`: `dispatched` = `SCRIPT_CALL_SENT` was committed; `data_free` = not dispatched (informational only); `direct` is exactly the §9.5 single rule, i.e. `reason = script_syntax` (submit-time compile failure), or a host-measured limit (or a spawn-time `sandbox_unavailable`, §3.4) with `queued` and `dispatched` both false. Every `SCRIPT_FAILED` with `direct = false`, other than `app_quit`, `cancelled_by_client` and `audit_failure` (nothing is released), stores the full candidate source `{class, message, stack, elapsed, logs, stderr}`, whether or not the run dispatched; it is the release candidate and its §5.2 rebuild source (reasons incl. `script_syntax` (submit-time compile check, before `SCRIPT_STARTED`), `killed_by_user`, `protocol_violation`, `audit_failure`, `app_quit` and `cancelled_by_client` (each always followed by `CANCELLED`, §2.5, §9.5), limit names), `SCRIPT_RELEASED`, `SCRIPT_DENIED`, `SCRIPT_DRY_RUN {mode: full|sparse, calls: [{op_id, params, instance, validation}], outcome: result | error | script_syntax | script_limit, result | error details, logs}` (terminal; a data-free dry run, §9.5; no `SCRIPT_STARTED`/`SCRIPT_CALL`).
- **Terminal**: `EXPIRED`, `CANCELLED {reason: by_client|app_quit|os_shutdown}`, `ABANDONED`.
- **System**: `GENESIS` (incl. `archived_db` when started fresh beside an archived log, §8.7, and `{previous_chain_id, previous_last_anchor}` when the anchor dir already holds a chain for this host and user, §8.5), `APP_START` (incl. `install_id` (also in `target`, §8.2), `app_version`, QuickJS-NG `engine_version`, sandbox binary identity and confinement status (§3.4, §9.4), effective proxy `host:port` per instance, `tray_host: present|missing` on Linux (§2.5), and `config_read_only {schema_version, parsed}` when `config.toml` was written by a newer version, §7.7), `APP_STOP {reason: quit|os_shutdown|installer}`, `SCHEMA_MIGRATED {from, to, app_version}` (§8.13), `CONFIG_CHANGED` (`source: app|file`; incl. effective-proxy changes and "Prepare for removal", §12.5), `INSTANCE_STATE_CHANGED` (incl. `needs_token`, `identity_header_missing|identity_header_mismatch` (§7.2), and `{user_renamed: {old, new, user_key}}`, a key-matched rename that updates the stored `atlassian_user`, §7.1), `CREDENTIAL_CHANGED` (PAT added, replaced or deleted, or recovery-passphrase change; for a PAT `{old_user_key, new_user_key, expires_at?}`, §7.1; never the secret), `SYSTEM_FETCH` (below), `PRUNE` (with its `prune_log` row, §8.5, and the `key_id`s of the DEKs destroyed in the same transaction, §8.8), `EXPORT {manifest_sha256}` (§8.10), `BACKUP`, `RESTORE` (fields in §8.11 step 5), `KEY_ROTATED`, `KEY_RECOVERED {what: [kek, anchors, …]}` (§8.7), `VERIFY` (incident results flagged `integrity_incident`; informational results incl. unanchored tail records, `interrupted_prune_reconciled` and `interrupted_restore_reconciled`, §8.7), `INTEGRITY_ACK`, `LEGAL_HOLD_CHANGED`, `CLOCK_ANOMALY` (`{local, server}` once per episode for the local date more than 1 day ahead of a server `Date` header (never of the monotonic extrapolation) or more than 1 day behind the corroborated date, or the skipped-prune reason, §8.8).
- **`SYSTEM_FETCH`** covers every PAT-bearing call made outside a request (`request_id` null): `{purpose: connection_test|version_detect|metadata_cache|doctor|token_recheck, instance_id, fetch_id, phase}` (`token_recheck`: the §7.1 identity re-test after a JSON 401 or from "Re-test stored token"). The `phase: start` record lists the planned `{method, path}` and is committed before the first call (§5.1 inv. 1), so even a crash mid-call leaves evidence that a call was attempted. One `phase: result` record per call stores `{method, path, status, full response}`, like `SCRIPT_CALL`. A start without a result needs no reconciliation (§11.3).

A request is **terminal** after any of: `REQUEST_REJECTED`, `REQUEST_FAILED`, `READ_RELEASED`, `READ_DENIED`, `READ_FAILED`, `WRITE_EXECUTED`, `WRITE_FAILED`, `WRITE_OUTCOME_UNKNOWN` (a write is terminal once the request of its latest `WRITE_APPROVED` has one of these outcome events; every v1 write is one request, §5.1 inv. 3), `WRITE_DENIED`, `SCRIPT_RELEASED`, `SCRIPT_DENIED`, `SCRIPT_DRY_RUN`, `SCRIPT_FAILED` iff `direct = true` or `reason = audit_failure` (`app_quit` and `cancelled_by_client` are never direct and are followed by `CANCELLED`; any other non-direct `SCRIPT_FAILED` is a pending release item, so a crash before its decision ends in `ABANDONED`, §11.3), `EXPIRED`, `CANCELLED`, `ABANDONED`.

### 8.4 Canonical encoding and hash chain

- `canonical_bytes` (versioned by `format_version`): a fixed, ordered field list per version — every column except `record_hash`. Each field: presence byte (0 = NULL, 1 = present), u32-BE length, bytes. Integers fixed-width big-endian; strings UTF-8 (lossless WTF-8 for OS paths). Adding hashed columns bumps `format_version`; old rows verify under their own version. `format_version` covers row encoding only; the SQLite schema, config and anchor layouts are versioned separately (§8.13). Exact layout fixed by golden test vectors in the `audit` crate.
- `record_hash = SHA-256("atlas-duck/audit/v<format_version>" ‖ prev_hash ‖ canonical_bytes)`. The first record is **`GENESIS`** (`prev_hash` = 32 zero bytes) containing `{chain_id, install_id, created_at}`.
- The chain is verifiable **without decryption**: `payload_sha256` (plaintext) is inside the hashed bytes, so hashing a decrypted export payload and comparing binds it to the chain.
- **AAD** for AES-GCM = same encoding over `[format_version, chain_id, seq, ts_utc, epoch, event_type, request_id, op_id, target, key_id, payload_sha256]`, domain `atlas-duck/aad/v1` — prevents moving ciphertexts between rows.
- No signatures: integrity rests on the chain, the anchors and the prune log (§8.5); an attacker who can run code as the user can rewrite the chain, which only an anchor directory the user cannot rewrite exposes (§8.9).

### 8.5 Anchors and prune log

- **Head anchor**: `(seq, record_hash)` mirrored into this install's keychain entry (§8.6) after commits (batched ≤ 1 s, flushed on `APP_STOP`). Keychain also holds `{chain_id, genesis_hash, first_retained_seq, first_retained_prev_hash}`, updated only by prune/restore (a restore resets them to the restored store and its `new_chain_id`, §8.11 step 5) and rebuilt by key recovery (§8.7). (Passphrase mode: both live in `<data>/anchor`, §8.6.)
- **Anchor ordering**: no anchor of any kind is written before startup verification has completed (§8.7 "No anchor writes before verification"). The head anchor never advances past a `PRUNE` or `RESTORE` record until that record's first-retained update (prune) or anchor reset (restore) has succeeded; batched flushes stop at that record's `seq` meanwhile. This keeps the §8.7 interrupted-prune/restore rules sound.
- **Prune log**: table `prune_log(range, cutoff_epoch, last_pruned_record_hash, first_retained_seq)`, one row per `PRUNE`, written in the same transaction as that `PRUNE` record and **never pruned**. Ranges are contiguous: each row's range starts at the previous row's `first_retained_seq`, and, after startup reconciliation (§8.7 interrupted prune), the latest row's `first_retained_seq` and `last_pruned_record_hash` equal the keychain's (or `<data>/anchor`'s) `first_retained_seq`/`first_retained_prev_hash`.
- **External anchor directory** (optional; strongly recommended, and required-with-confirmation in passphrase mode): the app appends unsigned JSON lines to `<anchor_dir>/<chain_id>.jsonl`: `{seq, record_hash, epoch}` (plus `clock_behind: true` when the record carries that flag, §8.8) once per corroborated `epoch` day (never for a date past the corroborated date, §8.8), on `APP_STOP` and on `RESTORE`, and `{first_retained_seq, first_retained_prev_hash, cutoff_epoch}` on `PRUNE`. Lines are append-only and fsynced; a write failure is shown in Settings and the tray. It protects against rollback only if the user cannot rewrite it (e.g. an append-only network share, §8.9).
  - **Header line**: the first line of each file is `{chain_id, install_id, host, os_user, created_at}`.
  - **Immediate lines**: `PRUNE`, `RESTORE`, `LEGAL_HOLD_CHANGED`, audit-policy `CONFIG_CHANGED` (retention, legal hold, anchor dir), `INTEGRITY_ACK` and `CLOCK_ANOMALY` records are each written to the anchor file right after they commit, as `{seq, record_hash, epoch, event_type}`, so a custodian sees policy changes and acknowledgements the same day.
  - **Changing or removing the anchor dir** is security-weakening (Rust-drawn confirmation, §10.3). Before switching, the app writes a final `{event_type: "ANCHOR_DETACHED", seq, record_hash, epoch, detached_at}` line to the old dir; the new dir starts with a header line.
  - **First run against a used anchor dir**: if the chosen anchor dir already holds a chain whose header names this `host` and `os_user`, the new `GENESIS` records `{previous_chain_id, previous_last_anchor}` and the app raises an integrity incident (`VERIFY {result: previous_chain_found}`, flag `integrity_incident`, needs `INTEGRITY_ACK`, §8.7). Exempt: the chain recorded as `archived_db` in the same `GENESIS` (§8.7).

### 8.6 Keys and recovery

- **Install-scoped keychain entries**: `install_id` (random, generated at first run, recorded in `GENESIS` (§8.4) and in this host's pinned `paths.toml`, §7.7) names every keychain entry of the install: `atlas-duck/<install_id>/kek`, `…/head_anchor`, `…/first_retained_anchor`, `…/canary` and `…/pat/<instance-id>` (§7.1). Startup looks up only its own `install_id`, the one in this host's pinned file, cross-checked with the **store's `install_id`**: that of the latest `RESTORE` (a restore keeps the live install's `install_id`, §8.11), else `GENESIS` (once `GENESIS` has been pruned, the value carried by the retained `APP_START` records); all three carry it in the plaintext `target` column (§8.2). A mismatch is an integrity incident (`VERIFY {result: install_id_mismatch}`, §8.7). First run never writes to or overwrites another install's entries, and another install's entries in the same keyring on a local filesystem (e.g. several installs on a multi-seat machine sharing one keyring) are never treated as tampering or an anchor mismatch. A keyring whose backing files are on a network filesystem is refused (*Keyring locality*, below). If this install's own entries are absent, the keychain-loss path applies (§8.7).
- **KEK** (32 B random) in the OS keychain (Windows persistence = Local, not roaming). **DEKs**: at least one per UTC month of `epoch` (created only when a record's corroborated `epoch` enters the month, §8.8; never for a future month); random 32 B; wrapped by the KEK (AES-256-GCM); stored in table `keys(key_id, month, wrapped_dek, created_at, destroyed_at)`. A restore or rotation adds a new DEK for the current month; each record references its `key_id`. The per-month grouping governs DEK **creation** only: a record is encrypted under the DEK of its own `epoch`'s month, so a record written before the first corroboration after a gap (whose `epoch` is still `prev_epoch`) uses the DEK of `prev_epoch`'s month. Destruction follows the reference rule of §8.8.
- **Recovery passphrase** (mandatory at the first run of a new store, §2.5 step (1b); never asked when the wizard finds an existing DB; min 12 chars, strength meter): a second copy of the KEK is wrapped with Argon2id (m = 64 MiB, t = 3, p = 4, 16-byte salt) in table `recovery`. Changing it re-wraps (logged `CREDENTIAL_CHANGED`).
  - **Entry** (first run and change, in the credential-entry window, §10.3): one fixed line states its purpose: "Unlocks and restores the audit log (after a keychain loss, from a backup, or on a new machine). Stored tokens are never recovered (from a backup or after a keychain loss); you re-enter them. It is not your Atlassian password. Store it where your compliance owner can retrieve it." The passphrase is typed twice; after wrapping, Rust unwraps the KEK once with the second entry and compares it with the KEK before committing the `recovery` row (a mismatch commits nothing and asks again).
  - **Recovery note** (optional; at first run offered right after `GENESIS` is written, §2.5 step (1b), so `install_id` and `chain_id` exist; after a passphrase change, right after the change): Rust opens a native save dialog (§10.3) and writes a plain-text note with the purpose line, host, OS user, `install_id`, `chain_id`, data-dir path, the restore/recovery steps (§8.7, §8.11) and a blank line for writing the passphrase by hand. The note never contains the passphrase.
- Random 96-bit nonces only; keys in `Zeroizing<[u8; 32]>`.
- **Keyring locality** (macOS and Linux; keychain mode): per-host keyring daemons (gnome-keyring, KWallet, securityd) hold the keyring file in memory and rewrite the whole file on each item write, and do not see writes made by another NFS client, so two hosts sharing a home would overwrite each other's KEK, anchor and PAT entries (the head anchor alone is rewritten up to once per second, §8.5). Before the canary self-test below, at first run and at every start, the app applies the §7.7 local-filesystem check to the keyring backing directories: Linux `$XDG_DATA_HOME/keyrings` (default `~/.local/share/keyrings`) and the kwalletd directory (`$XDG_DATA_HOME/kwalletd`); macOS `~/Library/Keychains`. Detection is heuristic, since Secret Service does not expose the file path; other providers are documented as unsupported on shared homes. If the keyring is not local, the wizard and `doctor` (§4.7) block keychain mode with `keyring_not_local`, and a later start stays `locked` with `details.reason = keyring_not_local` (exit 9, §4.3) and writes nothing to the keyring. If passphrase mode is part of v1, the Linux wizard may offer it instead, since it keeps the KEK, PATs and anchor in the local data dir.
- Startup self-test: write/read/delete this install's keychain canary entry (`atlas-duck/<install_id>/canary`; before first run, a canary named with the `install_id` about to be generated). Never a silent fallback to an insecure store.
- **Passphrase mode** (Linux without a usable Secret Service default collection): the app starts **locked** (exit 9 for requests; unlock via the credential-entry window, §2.5). The KEK is unwrapped from `recovery` with the passphrase. PATs are stored AES-GCM-wrapped under the KEK in table `vault`. The head anchor is a file `<data>/anchor` (0600, fsync + atomic rename) MAC'd with an HKDF-derived key from the KEK; a missing anchor file after first run is a verification failure. **Limitation (stated in Settings and §8.9):** a local anchor detects truncation of the DB alone but not a coordinated rollback of DB + anchor file; only an external anchor directory the user cannot rewrite protects against that (§8.5), so passphrase mode without an external anchor directory requires explicit confirmation and shows a persistent warning.

### 8.7 Verification

- **Startup**, in this order:
  1. Version gate (§8.13); it opens nothing for writing.
  2. Obtain the KEK: keychain mode — the keychain canary (§8.6) with the unreachable backoff and the `keychain_lost` locked state (below); passphrase mode — unlock (§8.6). While locked or waiting, nothing below runs (no migration, no write), and requests get `failed`, exit 9, `locked`.
  3. Load the head and first-retained anchors (this install's keychain entries, §8.6, or `<data>/anchor`) into memory, decrypt the newest record, and verify the chain from the latest `PRUNE`, `RESTORE` or `APP_START` record to the head **against the pre-migration store**; apply the anchor rule and the interrupted-prune/restore rules below and compare with the external anchor directory when configured. The outcome is held in memory.
  4. Run migrations and append `SCHEMA_MIGRATED` (§8.13); then append the `VERIFY` record step 3 produced, if any (incident or informational).
  5. Reconcile unfinished requests (§11.3) and append `APP_START`.
  Anchor rule:
  - pass if the record at `anchor_seq` exists with `record_hash == anchor_hash` and `db_head_seq ≥ anchor_seq`;
  - `db_head_seq > anchor_seq` (crash within the batching window): verify those tail records, log "N unanchored tail records" in `VERIFY` (informational), advance the anchor (after step 4);
  - fail if `anchor_seq > db_head_seq` or the hash differs, or if the first retained record does not match `first_retained_seq`/`first_retained_prev_hash`, unless the interrupted-prune or interrupted-restore rule below reconciles the mismatch.
  - *Interrupted prune* (the anchor update after a committed `PRUNE` did not happen, §8.8): reconciled without an incident only if **all** hold: (a) the anchored `first_retained_seq`/`first_retained_prev_hash` (keychain or `<data>/anchor`) equal the second-latest `prune_log` row, or the `GENESIS` values when only one row exists; (b) the latest `prune_log` row is contiguous with it; (c) the latest `PRUNE` record exists and verifies, and the first retained record's `prev_hash` equals that row's `last_pruned_record_hash`; (d) that `PRUNE` lies at or after the head anchor's `seq` or in the verified unanchored tail (the head anchor never advances past an unfinished `PRUNE`, §8.5), so an offline attacker cannot insert one mid-chain. Then `VERIFY {result: interrupted_prune_reconciled}` (informational) is appended, the first-retained anchor is advanced, and the missing anchor-dir `PRUNE` line is appended if an anchor dir is configured.
  - *Interrupted restore* (the KEK re-seal or the anchor reset of §8.11 step 5 did not happen): reconciled without an incident only if the head anchor equals the latest `RESTORE`'s `prior_keychain_anchor` `{chain_id, seq, record_hash}` (the source chain after a same-machine restore, the `replaced_db` chain otherwise), or is absent and `prior_keychain_anchor` is null, and that `RESTORE` verifies as the latest segment boundary (§8.11; it may lie below the prior anchor after a same-machine rollback with `records_lost > 0`, §8.11 step 4). If the keychain KEK does not yet unwrap the restored store's DEKs (crash before the re-seal), the newest record is that plaintext `RESTORE` row, and its `target` names this install (§8.2), the app does not take the keychain-lost path: it starts locked (requests get `locked`, `details.reason = keychain_lost`, exit 9) and the credential-entry window asks for the restored store's recovery passphrase ("Finish restore", §10.3) to unwrap its KEK from `recovery`, then verifies as above. Then the re-seal and the anchor reset are completed, `VERIFY {result: interrupted_restore_reconciled}` (informational) is appended, and the missing anchor-dir `RESTORE` line is written if configured.
  Any other mismatch stays an integrity incident. Once `GENESIS` exists, a missing head or first-retained anchor (keychain entry, or `<data>/anchor` in passphrase mode) is a verification failure in every mode, except as the interrupted-restore rule allows.
  **No anchor writes before verification**: until step 3 has completed and the `VERIFY` it produced (if any) is committed, the app writes no head-anchor or first-retained-anchor update, no `<data>/anchor` rewrite and no anchor-dir line, and batched head-anchor flushes (§8.5) of earlier commits such as `SCHEMA_MIGRATED` are suppressed. A migration on a tail-truncated DB therefore cannot move the anchor to the truncated head and hide the truncation.
- **Keychain cases at startup** (keychain mode, with an existing audit DB; passphrase mode keeps no keychain entries). Only this install's entries (`atlas-duck/<install_id>/…`, §8.6) count; other installs' entries in the same keyring are ignored:
  - *Keychain unreachable* (e.g. Secret Service or login keychain not ready yet at autostart): retry with backoff for 60–120 s while the tray shows "Waiting for keyring". Requests meanwhile fail with `locked`, `details.reason = keychain_unavailable` (exit 9). If the keychain is still unreachable, the app stays in that state and offers a manual retry.
  - *Keyring not local* (§8.6 *Keyring locality*, checked before any keyring access): the app starts **locked** with `details.reason = keyring_not_local` (exit 9), reads and writes no keyring entry, and shows the reason in the tray and an error window (not the credential-entry window: there is nothing to unlock).
  - *Entries present*: normal start.
  - *Entries missing or undecryptable* (Windows password reset by IT invalidating DPAPI, macOS keychain reset, VDI profile wipe, reinstall; except an interrupted restore before its KEK re-seal, which offers "Finish restore" instead, above): the app starts **locked** with `details.reason = keychain_lost` (exit 9). It never writes `GENESIS` and never treats the DB as first run (§2.5). The credential-entry window (§10.3) offers **"Recover this log"**.
- **Recover this log**:
  1. Unwrap the KEK from `recovery` with the recovery passphrase.
  2. Verify the chain from the first retained record (checked against the latest `prune_log` row, §8.5) to the head, and compare with the external anchor directory if configured.
  3. Run pending migrations (`SCHEMA_MIGRATED`, §8.13), then append `VERIFY {result: anchor_missing}` with flag `integrity_incident` (tail truncation cannot be ruled out without the lost anchor; needs `INTEGRITY_ACK`), then `KEY_RECOVERED {what: [kek, head_anchor, first_retained_anchor, pats_lost]}`.
  4. Re-seal the KEK into the keychain, rebuild the head and first-retained anchors from the verified DB (no anchor is written before this step, as at startup), and set every instance to `needs_token`.
  The `chain_id` is unchanged, so recovery is **not** a segment boundary, unlike restore (§8.11).
- **Archive old DB and start fresh**: the only alternative to recovery when the passphrase is unavailable. It requires a Rust-drawn native confirmation (§10.3). The old DB (with WAL) is moved aside within the data dir and never deleted, and the new `GENESIS` records `archived_db {file, chain_id, head_seq, head_hash}`. The first-run wizard then runs (§2.5), including a new recovery passphrase and instances. The archived DB is still a retained record. The operator must keep it for its remaining retention period, and it can later be recovered with its own passphrase through restore (§8.11).
- **Offboarding / machine change** (documented procedure; on the new machine the backup is restored per §8.11, which re-seals its KEK under the new install's keychain entries without an incident): make a full backup (§8.10; it never contains tokens) to an organization-controlled location, hand the recovery passphrase to the compliance owner, verify the backup, run "Prepare for removal" (§12.5), including its explicit, confirmed step to **revoke every PAT in Jira/Confluence** (DC PATs stay valid server-side until revoked), then wipe the machine.
- **Full verification** (daily background + on demand): the `prune_log` is contiguous from `GENESIS` (each range starts at the previous row's `first_retained_seq`) and its latest row matches the keychain (or `<data>/anchor`) first-retained anchor, after the interrupted-prune and interrupted-restore rules above have been applied as at startup; the first retained record's `prev_hash` equals that row's `last_pruned_record_hash` (or the first record is `GENESIS`); every retained record chains to the head; each `RESTORE` boundary matches (§8.11); no `PRUNE` cutoff lies inside `today − retention_days` (or a legal hold); a decrypt pass checking `payload_sha256` and recomputing each `WRITE_APPROVED` `request_set_hash` from its stored `requests` list; a retained row whose `key_id` names a destroyed DEK is an integrity incident (the §8.8 shredding rule never destroys a referenced DEK). With an anchor directory: every anchored `{seq, record_hash}` with `seq ≥` the latest `first_retained_seq` must match the record at that seq, every anchored `PRUNE` line must match its `prune_log` row, and an anchored record that was pruned although its epoch was still inside retention is flagged. An anchored line marked `clock_behind` (§8.5) is judged instead by the `date(ts_utc)` of the first later unflagged record while that record is retained: if that date is not older than the `cutoff_epoch` of the `prune_log` row whose range covers the anchored seq, the prune is flagged.
- **Anchor-dir lines**: header lines, `ANCHOR_DETACHED` lines and the immediate lines of §8.5 are checked like daily lines (each `{seq, record_hash}` must match the record at that seq while retained), and each immediate line's `event_type` must match that record's.
- **Integrity incidents** persist: on any failure, a `VERIFY` event with `result` and `{expected_seq, expected_hash, observed_seq, observed_hash, detected_at}` and flag `integrity_incident` is appended **before** any further anchor update; if an external anchor dir is configured, an incident JSON is written there. The red banner (UI + tray) is derived from the log: shown while any integrity-incident `VERIFY` has no later `INTEGRITY_ACK` referencing it. `INTEGRITY_ACK` is created by an explicit "Acknowledge integrity incident" action (OS user + note). The proxy keeps working (so the incident itself stays logged) unless the DB is unwritable.

### 8.8 Retention and policy

- `retention_days`: default 100, **minimum 92** (covers any three calendar months). Stored authoritatively in the audit DB; changed only via the UI (logged `CONFIG_CHANGED`). Legal hold likewise (`LEGAL_HOLD_CHANGED`). On startup, if `config.toml` requests different values, the difference is logged as `CONFIG_CHANGED {source: file, old, new}` before any prune; values below 92 are raised to 92; lifting legal hold or lowering retention never takes effect from a file edit — it needs UI confirmation.
- **Corroborated date**: the newest UTC date confirmed in this process by either (a) the HTTP `Date` header of a successful, parsed, TLS-verified Atlassian response from any configured instance (requests, script calls and `SYSTEM_FETCH` alike), or (b) the last such corroborated instant plus the monotonic time elapsed since it. Since every base URL is https (§7.1), every Atlassian response is TLS-verified, so corroboration happens on the first successful request or `SYSTEM_FETCH` of the process. Source (b) should be measured with a clock that keeps counting through suspend where the OS offers one (Linux `CLOCK_BOOTTIME`, macOS `mach_continuous_time`, Windows interrupt time including sleep; §15), but it may still undercount (VM pauses, a plain `Instant`). Source (b) therefore only caps `epoch` (an undercount errs low and only holds `epoch` back, the safe direction) and may reveal a behind clock (an undercount can only lower it, so it never reports "behind" falsely); it never sets `clock_forward` or raises a local-ahead `CLOCK_ANOMALY`. Until something is corroborated, `epoch` stays at `prev_epoch`. **Local ahead**: the local-ahead state is entered only when a server `Date` header (source (a)) is received while `today_utc` is more than 1 day ahead of that header's date, and left when a later header agrees within 1 day; on entering it the app logs `CLOCK_ANOMALY {local, server}` (once per episode), and records written while in it get the `clock_forward` flag; after a suspend, records written before the next server response therefore carry the held-back `epoch`, no flag and a current `ts_utc`, and the `ts_utc` clause of the prune rule keeps them for the full retention period. **Local behind**: when `today_utc` is more than 1 day behind the corroborated date (either source), the app logs `CLOCK_ANOMALY {local, server}` once per episode and applies the `clock_behind` rule below. No dialog is shown in either direction.
- **Backward clock** (`clock_behind`): while the local clock is behind, `epoch` stays at `prev_epoch` but every record's `ts_utc` carries the older local time, so `ts_utc` must not shorten retention. The flag `clock_behind` is set on (a) every record written while `today_utc < corroborated_date − 1 day`; (b) a `GENESIS` written before any corroboration; and (c) every record written before the first corroboration in this process whose `date(ts_utc)` is earlier than its predecessor's `epoch` (e.g. a CMOS reset) or whose predecessor carries `clock_behind`, so an uncorroborated first run or restart after a backward episode stays flagged until the date is corroborated. `epoch`, the daily anchor-dir lines (§8.5) and new month DEKs (§8.6) therefore never run ahead of the corroborated date.
- **Prune** deletes only the longest contiguous seq prefix of records whose `epoch` is older than the cutoff (`min(today_utc, corroborated_date, head epoch) − retention_days`) **and** which either carry `clock_forward` or have a `date(ts_utc)` — their own or that of any later record — older than the cutoff, where the `ts_utc` of a `clock_behind` record never counts (a prefix because `epoch` is non-decreasing). So a `clock_behind` record is prunable only when its `epoch` is older than the cutoff **and** a later unflagged record's `date(ts_utc)` is older than the cutoff, which holds it for at least `retention_days` after the clock is corrected. The `ts_utc` condition keeps records whose `epoch` was held back before corroboration (e.g. `APP_START` and the first `REQUEST_RECEIVED` after a long gap) for the full retention period; the "any later record" clause releases records stamped during an uncorroborated forward jump once the clock is corrected. Prune runs only after the date has been corroborated in this process. In one transaction it writes `PRUNE {range, count, cutoff}` and its `prune_log` row `{range, cutoff_epoch, last_pruned_record_hash, first_retained_seq}` (§8.5); it then updates `first_retained_*` in the keychain/anchor and appends the `PRUNE` line to the anchor directory if configured. If the keychain or anchor-file update fails after the commit, it is retried with backoff and the failure is shown in Settings and the tray, never as an integrity incident; meanwhile the head anchor stays at or before the `PRUNE` (§8.5), and a crash in this window is reconciled at the next start (§8.7 interrupted prune).
- **Clock guards**: prune is skipped (and `CLOCK_ANOMALY` logged) when `now < ts_utc` of the head record or `now <` the last `PRUNE` time; a run may advance the cutoff by at most 2 epochs beyond the previous `PRUNE` cutoff without explicit UI confirmation — so a forward clock jump can never mass-delete records, and (with the corroborated `epoch`) a jump that is later corrected leaves no future-dated epoch, anchor line or DEK behind. A record whose `ts_utc` is > 5 s earlier than its predecessor's gets the `clock_backwards` flag; this is a per-record step marker, independent of the date-level `clock_behind` flag above, which alone governs pruning.
- **Crypto-shredding**: a DEK is destroyed (wrapped key overwritten, `destroyed_at` set, listed in the `PRUNE`) only when no retained `events` row references its `key_id`. This is checked in the same transaction as the `PRUNE` that removes the last such row. The DEK must not be the one currently used for new records, and it is never destroyed while legal hold is on. Records held back on the previous epoch (§8.2, prune rule above) keep their month's DEK alive until they are pruned themselves.
- **Legal hold** pauses pruning and shredding.
- **Storage estimate**: ≈ retention_days × (events/day × ~2 KiB + bytes fetched/released per day ÷ zstd ratio). Example: 500 events/day of typical reads ≈ 1–1.5 GB per 100 days; 20 heavy script runs/day at 50 MiB each ≈ 10–20 GB. Settings shows a gauge, 7-day growth and projected days-to-threshold.

### 8.9 Threat model limits (documented to users)

Protects against: offline theft of the DB; casual/accidental modification; silent truncation of the tail (keychain anchor) or head (genesis/first-retained anchors + `prune_log`); and — only with an external anchor directory the user cannot rewrite (§8.5) — rollback or rewriting of history after an anchor line was written. Does **not** protect against malware running as the same OS user while the session is unlocked (it can call the keychain, rewrite the chain and re-seal the anchors), nor — under degraded sandbox confinement (§9.4) — against a sandbox escape, which then equals same-user code execution. A compliance export is trustworthy only against an anchor directory or a manifest SHA-256 obtained out of band (§8.10). Passphrase mode: see §8.6. **The local log does not protect against the audited OS user** deliberately deleting data, reinstalling or confirming destructive actions (clock-jump prunes, anchor-dir removal, acknowledging their own incidents); retention against that user requires an external anchor dir the user cannot rewrite (an append-only/WORM share administered by someone else, §8.5), whose immediate lines record such actions. Backups and exports are outside retention and crypto-shredding (§8.10). So are crash dumps of webview processes, swap and hibernation files on a disk without full-disk encryption, and OS-level backups or snapshots of the data dir (Time Machine, VSS/File History, filesystem snapshots), which copy the wrapped DEKs together with the recovery blob, so a "shredded" month stays recoverable from them. **Full-disk encryption is assumed**, and the operator's erasure procedure must cover such copies. The app does not exclude the data dir from OS backups (that would endanger retention).

### 8.10 Audit UI, export, backup

- **Audit window**: filter by time range, agent, op, class, instance, target, decision, flags; view decrypted payloads; follow a request's full event trail (incl. deliveries); highlight requests delivered more than once or to a peer different from the submitter (compared on `peer_origin_exe` + origin start time, §3.1, since the direct peer is always the CLI; advisory); "Verify now"; integrity incidents and acknowledgement.
- **Compliance export**: a time range → directory with `events.jsonl` (every canonical column incl. `key_id`, `nonce`, `payload_ct` base64, **plus** the decrypted payload), `prune_log.jsonl` (all rows), `manifest.json` (boundary `prev_hash`, head `{seq, record_hash}`, chain_id(s), restore and key-recovery records, and the accountability statement of §2.4: the approving OS user acting as PAT owner is the accountable principal; agent/peer fields are advisory). The manifest's SHA-256 is recorded in `EXPORT {manifest_sha256}` and shown in the UI, so the recipient can obtain it out of band. With an anchor directory, events after its last anchored line are marked `unanchored`. `atlas-duck verify-export <dir> [--anchor-dir <dir>] [--manifest-sha256 <hex>]` (the console CLI, which runs the app binary's read-only `__verify-export` mode as a child even while the tray app runs, §12.1; the export dialog's recipient instructions use this form) recomputes every `record_hash`, the chain, `payload_sha256` of the decrypted payloads and each `WRITE_APPROVED`'s `request_set_hash` from its `requests` list, checks the `prune_log` rows and `RESTORE` boundaries, and compares with the anchor lines (§8.7 rules) and the given manifest hash. Without `--anchor-dir`/`--manifest-sha256` it reports "internally consistent; trust root NOT verified" and exits non-zero (exit codes §12.1). The export dialog warns that files are decrypted and readable by any same-user process. Logged (`EXPORT`).
- **Full backup**: `VACUUM INTO` snapshot + recovery blob + a backup manifest with the snapshot's head `{seq, record_hash}`. Logged (`BACKUP`). **A backup never contains credentials** (in every mode): after `VACUUM INTO`, the app opens the snapshot, deletes all `vault` rows, sets `PRAGMA secure_delete=ON` and runs `VACUUM` on it again, so no wrapped PAT ciphertext survives in free pages (a plain `DELETE` would leave it); only then is the manifest written. `vault` is outside the hash chain, so the manifest head is unaffected. (Equivalent alternative: a copy path that never copies `vault`.) The UI states that backups and exports are outside retention/crypto-shredding; their lifecycle is the operator's responsibility. A full backup is the first step of the offboarding / machine-change procedure (§8.7) and of "Prepare for removal" (§12.5), and is recommended before every upgrade (§8.13).

### 8.11 Restore

1. Check the snapshot's versions (§8.13): a snapshot written by a newer atlas-duck is refused before anything is written. Verify the snapshot chain from its first retained record (against its `prune_log`) to the head recorded in the backup manifest, and against the anchor directory's lines for that `chain_id` if configured. An older snapshot is migrated forward (§8.13) only after it has verified and before the anchors are reset (step 5).
2. Unwrap the snapshot's KEK from its `recovery` row with the backup's recovery passphrase. That passphrase becomes the live recovery passphrase (in passphrase mode also the unlock passphrase); a passphrase change (§8.6) is offered right after the restore.
3. Generate a **new `chain_id`** and a new DEK, wrapped under the snapshot's KEK. Stored tokens are never restored: any `vault` rows in the snapshot are ignored and deleted, and every instance is set to `needs_token` (as in "Recover this log", §8.7). The live install keeps its own `install_id` (§8.6); the snapshot's is recorded as `source_install_id`.
4. If the keychain anchor on this machine names the snapshot head's `chain_id` and is ahead of the snapshot head (same-machine rollback), require explicit confirmation showing how many records will be lost. An anchor of another chain (a new machine, or a live DB that is not the snapshot's) is never compared; it is recorded as `prior_keychain_anchor`. The live DB (with WAL), if any, is moved aside within the data dir like `archived_db` (§8.7), never deleted, and stays recoverable with its own recovery passphrase through a later restore.
5. Append `RESTORE {install_id, source_install_id, source_chain_id, source_head_seq, source_head_hash, new_chain_id, backup_created_at, prior_keychain_anchor {chain_id, seq, record_hash}|null, replaced_db {file, chain_id, head_seq, head_hash}|null, records_lost, pats_lost}` (chained to the snapshot head; `target` = `install_id`, §8.2), then, as one completion step: re-seal the snapshot's KEK into this install's `atlas-duck/<install_id>/kek` entry (passphrase mode: the snapshot's `recovery` row is kept and `<data>/anchor` is rewritten under that KEK), reset the anchors and, if configured, write the `RESTORE` line to `<anchor_dir>/<new_chain_id>.jsonl`. A failed keychain or anchor update is retried with backoff and shown in Settings and the tray, not as an incident; a crash between the `RESTORE` commit, the re-seal and the anchor reset is completed at the next start (§8.7 interrupted restore), asking for the recovery passphrase only if the re-seal had not happened.

The verifier treats `RESTORE` as a segment boundary: its `source_head_seq`/`source_head_hash` must equal the record before it, records before it belong to `source_chain_id` and records after it to `new_chain_id`; anchored lines of the source chain beyond `source_head_seq` must be accounted for by `records_lost`. `verify-export` reports two exports sharing a prefix with different `chain_id`s as a **fork**, not tampering; the docs state the old installation must be decommissioned.

### 8.12 Data protection note

The audit log contains personal data of Atlassian users (names, comments, worklogs) and of approvers for the retention period. Plaintext index columns: `target`, `agent_name`, `peer_exe`, `peer_origin_exe` (an executable path, which may include the user's name), `os_user`, `atlassian_user(_key)`, timestamps. Erasure is possible only by whole month after retention (crypto-shredding, once no retained record references that month's DEK, §8.8); crypto-shredding does not reach webview crash dumps, swap/hibernation without full-disk encryption, or OS-level backups and snapshots of the data dir (§8.9), which the operator's erasure procedure must cover. Uninstalling atlas-duck does not erase the log (§12.5); the documentation lists the remaining paths and keychain entries per OS for manual deletion once retention has passed. Operators should reflect this in their records of processing.

### 8.13 Schema versions, migration, downgrade

- **Versions**: `PRAGMA user_version` holds the audit DB schema version; `config.toml` keeps `schema_version` (§7.7); keychain anchors, the `<data>/anchor` file, `vault` and `recovery` blobs carry a leading layout-version byte. Row encoding stays versioned by `format_version` (§8.4).
- **Version gate** (startup step 1, §8.7): if `user_version`, the head row's `format_version`, or the layout byte of the keychain anchors, `<data>/anchor`, `vault` or `recovery` is newer than this binary supports, the app does not open the store for writing and writes nothing (no `VERIFY`, no incident, no anchor update; files unchanged). The UI and tray show "audit data was written by atlas-duck vX; install vX or newer", and every request gets `failed`, exit 5, `unreachable`, `details.reason = store_newer`. A downgrade is therefore never reported as tampering. `config.toml`'s `schema_version` is **not** part of the gate: a newer config is read as far as known and treated as read-only (§7.7), so a staggered upgrade across machines sharing a roaming or NFS config never locks out the older one.
- **Migrations** are forward-only and additive (new tables, columns, indexes). They need the KEK (`SCHEMA_MIGRATED` has an encrypted payload) and run **after** startup verification (§8.7 step 4), in one SQLite transaction. While the app is locked or waiting for the keyring (`keychain_unavailable`, `keychain_lost`, `passphrase`), no migration runs and requests get `locked`, exit 9, never `internal`. Verifying first is valid because migrations never rewrite hashed columns, ciphertexts, wrapped keys or existing rows' `format_version`; old rows keep verifying under their own version. Each migration appends `SCHEMA_MIGRATED {from, to, app_version}` in the same transaction. A failed migration (with the KEK available) rolls back; the app shows the error and refuses requests (`failed`, exit 1, `internal`), retries on every start, and it is not an integrity incident. Layout migrations are rewritten atomically (write + fsync + rename) and logged in the same event. Config migrations are additive only (§7.7) and are written only by a binary whose `schema_version` is at least the file's.
- **Recovery and restore**: "Recover this log" migrates after its verification (§8.7 step 2) and before the anchors are rebuilt; restore migrates an older snapshot after it has verified and before the anchors are reset (§8.11).
- **No automatic pre-upgrade snapshot** (it could outlive retention, §8.10). Release notes and Settings recommend a full backup (§8.10) before upgrading.

## 9. Script sandbox

### 9.1 Flow

1. `atlas-duck script run file.js|- [--args JSON] [--limits JSON]` — the CLI sends **source + args**, never a path.
2. App commits `REQUEST_RECEIVED`, validates (source ≤ 256 KiB, args ≤ 1 MiB JSON, limits keys/values §9.4; failure → `REQUEST_REJECTED`, exit 2), then runs the **submit-time compile check**: a compile-only worker from the dry-run pool (§9.4; same confinement, no host calls, never a real-run slot) compiles the wrapped source. A compile failure → `SCRIPT_FAILED {reason: script_syntax, queued: false, dispatched: false, data_free: true, direct: true}` (terminal, §8.3), `failed`, exit 8, returned directly (§9.5). Otherwise the run joins the real-run queue; when a slot is free the app commits `SCRIPT_STARTED {…, queued}` (`queued: true` if the run waited for a slot held by another real run).
3. App spawns `atlas-duck-sandbox` with OS limits and confinement (§9.4) and sends the init frame `{source, args, limits, read_op_ids}` over stdin (`read_op_ids`: the registry's Read op ids, from which the worker generates `atlas.*`, §9.2).
4. Each `atlas.*` call → `host.call` → the app validates (**Read class only**, schema, field rules, caps, instance). When the host accepts the run's first validated `host.call`, before any limiter, rate-limit or retry wait and before its first HTTP request, the app commits `SCRIPT_CALL_SENT {call_id, op_id, instance}` (the run is now **dispatched**, §9.5). It executes via the shared client/limiter, commits `SCRIPT_CALL` (full response, or the call's failure outcome), **then** returns the result to the worker. If an append fails, the script is killed (`SCRIPT_FAILED {audit_failure}`), nothing is released.
5. Worker returns `script.result` (JSON) or `script.error`; the app also observes limits and process exit.
6. Outcome classification and release per §9.5.
7. **Dry run** (`--dry-run[=full|sparse]`, default `full`; MCP `script_run {dry_run}`): steps 1–3 and 5 as above (same worker, confinement and limits) but in the **dry-run pool** (§9.4), which real runs never occupy, and with no `SCRIPT_STARTED`. In step 4 the host validates every call identically (Read class, schema, field rules, caps, instance) and answers it from the op's `result_example` (`full`) or `result_example_sparse` (`sparse`); an invalid call rejects inside the script as usual. The dry-run host-call path is constructed **without an HTTP client handle** (type-level, like the `CredentialProvider` injection, §2.2), so it cannot reach Atlassian, and no `SCRIPT_CALL` is committed. Outcome per §9.5 (dry runs).

### 9.2 Script API

The source is wrapped as the body of `async function main(args, atlas) { … }`; its return value (JSON-serializable) is the result.

```js
const res = await atlas.jira.search({ jql: `project = ${args.project} AND resolution = Unresolved`,
                                      fields: ["summary","status","assignee"], max: 500 });
const byAssignee = {};
for (const i of res.issues) (byAssignee[i.fields.assignee?.name ?? "unassigned"] ??= []).push(i.key);
atlas.log(`processed ${res.issues.length} issues`);
return byAssignee;
```

- `atlas.<product>.<…>(params, {instance}?)` — async functions mirroring every **Read** op (generated from the init frame's `read_op_ids`, §9.1 step 3; params are validated by the host), returning the same `result` shape as the CLI's `data.result` (unredacted — redaction applies only at release). Scripts never see `meta`, so nothing is adjusted silently. A `max` above the op's hard cap **rejects with a `validation` error** instead of being clamped as it is for CLI/MCP (§7.5).
- `atlas.call(opId, params, {instance}?)`, `atlas.ops()`, `atlas.instances()`, `atlas.log(...strings)`.
- `atlas.all(opId, params, {instance}?)` pages through a paginated read op. It resolves to the op's **native result shape**, with the items array named by the op's `PageSpec.items_key` (shown by `ops describe`, e.g. `issues`, `results`, `values`) concatenated across all pages, and server totals passed through unchanged. It **rejects with a catchable error, never partial data**:
  - `result_too_large` before the concatenated result would exceed `max_call_result_mb`;
  - `script_limit` before the next page would exceed `max_calls`, or once the run's fetched bytes reach `max_fetch_mb`.
  `atlas.all` is a single `host.call`. The host pages internally, enforces these checks from its own counters, and commits each page as a `SCRIPT_CALL`, which counts against `max_calls`/`max_fetch_mb`.
- **Concurrency**: the shim keeps at most `max_concurrent_calls` host calls outstanding. Further calls wait locally as pending promises and are sent as earlier ones settle (§3.4).
- The effective limits (§9.4) are listed in `ops describe --instance X` (`script_limits`; built-in defaults without `--instance`, §2.3) and the script API reference (§12.4).
- `atlas` and `args` are deep-frozen.
- The worker runs with `TZ=UTC0` (§3.4): local-time `Date` methods and `toLocale*` behave as UTC. Documented in the script API reference (§12.4).

### 9.3 Engine configuration

- `rquickjs` pinned exact version; feature `macro`, plus only what the worker's single-threaded blocking I/O loop needs. Whether that includes `futures` is decided in the implementation plan together with the loop design (§15). Never `loader`, `dyn-load` or `parallel`.
- Context with minimal intrinsics: base objects, Eval (required to load source; harmless inside the sandbox), JSON, Promise, RegExp, MapSet, Date. **Excluded**: TypedArrays/ArrayBuffer, Proxy, WeakRef, Atomics/SharedArrayBuffer, Performance. No module loader (any `import` fails).
- One fresh Runtime per run, running on the **worker's main thread** with an 8 MiB native stack (Linux: `RLIMIT_STACK` = 8 MiB set by the parent before exec, §9.4; Windows: the worker binary's linker stack reserve `/STACK:8388608`; macOS: the 8 MiB main-thread default). The worker creates no other threads; `set_max_stack_size(1 MiB)`; `set_memory_limit(heap limit)`; `set_gc_threshold`.
- Interrupt handler checks deadline, cancel flag, and op budget (catches CPU-bound loops).
- Only JS source is accepted — never bytecode.

### 9.4 Limits and confinement

| `--limits` key | Default | Enforcement |
|---|---|---|
| `timeout_s` (wall clock incl. awaits) | 120 | interrupt handler + host-side kill of the process |
| `heap_mb` | 256 | `set_memory_limit`; OOM is terminal (host-decided) |
| `process_mb` | 512 | Windows job object / Linux `setrlimit(RLIMIT_AS)` / macOS host-side watchdog (polls `proc_pid_rusage` `ri_phys_footprint` every 100 ms, SIGKILL above the limit; `RLIMIT_AS` is not enforced on Darwin) |
| `max_calls` | 200 | host |
| `max_fetch_mb` (bytes fetched per run) | 50 | host |
| `max_call_result_mb` (per host-call response after normalization; also the cap on an `atlas.all` result) | 16 | host; over → the call rejects inside the script with `result_too_large` |
| `max_result_mb` (final result) | 16 | host |
| `max_concurrent_calls` | 4 | host counts outstanding calls; one beyond the limit = `protocol_violation` (§3.4); the shim queues locally (§9.2) |
| — concurrent real scripts | 2 (queued beyond; a run that waited is `queued`, §9.5) | host; saturation is never answered with `busy` |
| — concurrent dry runs and submit-time compile checks | 2 (queued beyond) | host; a separate pool that real runs never occupy (§9.1 steps 2, 7) |

Defaults configurable in Settings. Agents may request **lower** values via `--limits`; unknown keys or values above the configured default → exit 2, nothing queued.

**Memory invariants** (enforced in Settings and on agent `--limits`; violation → rejected in Settings, exit 2 for `--limits`). A JSON result expands several-fold when materialized as QuickJS objects, so:
- `heap_mb ≥ k × max_call_result_mb`, with `k = 8` provisionally; M8 measures the real factor on Jira `*all` search and Confluence storage-body fixtures and fixes `k` (§14, §15);
- `process_mb ≥ heap_mb + 24 MiB (max host→worker frame) + 64 MiB margin`.

**OS confinement of the worker** (best effort beyond a mandatory floor):
- **Linux** — applied by the worker to itself on its main thread, which is also the JS thread (§9.3), before it reads stdin. Landlock and seccomp filters apply only to the calling thread (and threads it creates later), so the worker is single-threaded when they are installed. Order: `tzset()` plus one `localtime_r` call (so libc's time-zone state is initialized from `TZ=UTC0`, §3.4, before files are blocked); `PR_SET_NO_NEW_PRIVS`; Landlock handling all filesystem rights the kernel's ABI supports with no rules (plus ABI ≥ 4 network rules and ABI ≥ 6 scopes when available); **seccomp-bpf in default-kill mode with an enumerated allowlist** kept in one reviewed file (read on fd 0, write on fds 1/2, memory management, futex, clocks, `getrandom`, signal return/mask, exit). `open`, `openat` and `openat2` return `SECCOMP_RET_ERRNO(EACCES)` (a libc path that lazily opens a file fails softly instead of killing the run); everything else not allowed is `KILL`, including, after setup, `clone` (`clone3` returns `ENOSYS`) and, among others, `execve(at)`, `socket(pair)`, `io_uring_*`, `ptrace`, `process_vm_*`, `bpf`, keyring calls, `unshare`/`setns`. If an implementation ever needs a separate JS thread, the order is `PR_SET_NO_NEW_PRIVS` → Landlock → spawn the thread → seccomp with `SECCOMP_FILTER_FLAG_TSYNC`; a `TSYNC` failure means the floor is not met. The parent sets `PR_SET_PDEATHSIG(SIGKILL)` (from its spawner thread, §3.4) and rlimits (`AS`, `NOFILE`, `STACK` = 8 MiB, `CORE=0`) before exec. Network blocking relies on seccomp, not Landlock.
- **macOS** — the worker calls `sandbox_init` with an embedded deny-by-default SBPL profile: no network, no file access after startup, no fork/exec, no `mach-lookup` (blocks securityd/keychain and pasteboard). This calling mode is deprecated and undocumented, so it is verified by probes (below) and listed in §15. Memory via the host-side watchdog.
- **Windows** — the worker runs in an **AppContainer** with zero capabilities (Less-Privileged AppContainer where all needed ACEs exist), so it has no network access and only explicitly granted file access. **Both NSIS install modes** (per-machine and per-user, §12.2) grant `ALL APPLICATION PACKAGES` (S-1-15-2-1) and `ALL RESTRICTED APPLICATION PACKAGES` (S-1-15-2-2) read+execute on the worker binary and every DLL it loads; a per-user install needs no elevation for this because the user owns the files. At each start, before the probe, the app checks these ACEs and re-applies missing ones if it holds `WRITE_DAC` on the files (normally only in a per-user install; in a per-machine install missing ACEs mean the installer failed and need a repair install). Job object: `ACTIVE_PROCESS=1`, `KILL_ON_JOB_CLOSE`, `DIE_ON_UNHANDLED_EXCEPTION`, process memory limit, `JOB_OBJECT_UILIMIT_ALL`. Only if the ACEs are still missing or AppContainer creation fails (e.g. AppContainer profile creation blocked by policy) does the degraded path apply: the only available configuration is then a lockdown token (restricting SID = NULL SID, untrusted integrity, applied after startup) + job object, in which file reads and network may not be blocked — this is **below the floor** (degraded).

**Mandatory floor and probes.** Per OS floor: Linux `no_new_privs` + seccomp; macOS seatbelt profile + watchdog; Windows AppContainer + job object. On each app start, and before the first script, the host runs a **probe worker** (and records the binary identity re-checked before every spawn, §3.4) that attempts: opening a file in the user profile, `socket()`/`connect()` to 127.0.0.1 and a public IP, spawning a process (incl. raw `clone`/`clone3` on Linux), reading the app's memory (Linux `process_vm_readv` and `/proc/<app pid>/mem`; macOS `task_for_pid`; Windows `OpenProcess(PROCESS_VM_READ)` on the app), and (Windows) `CredReadW`/`OpenClipboard`, (macOS) a securityd `mach-lookup`. On Linux it also asserts that **every** thread of the worker is confined (`Seccomp: 2` and `NoNewPrivs: 1` in each `/proc/self/task/*/status`). Results are recorded in `APP_START` and shown in Settings; the memory-read result is the app's only memory-protection self-test (§2.5) and, like every probe result, **never blocks app startup** (probe results affect only whether scripts are enabled, per the floor rule below). **If the floor cannot be applied and verified, scripts are disabled** (`failed`, exit 8, `error.code = sandbox_unavailable`). An explicit Settings toggle "Allow scripts with degraded confinement" re-enables them with a persistent warning and is audit-logged (`CONFIG_CHANGED`). Missing extra layers (e.g. Landlock on older kernels) are reported but do not disable scripts. Under degraded confinement, a worker compromise is equivalent to same-user code execution (§8.9).

### 9.5 Outcome classification and leak prevention

Classification is by **data exposure**, not by error type, and is decided **only by the host from its own state**: `script_syntax` only from the submit-time compile check (§9.1 step 2), which runs in the dry-run pool before the run joins the real-run queue, so it never waits on a real-run slot; `script_limit` only for limits the host itself measured (its timer and counters, the job-object/rlimit/watchdog kill reason, host-decided OOM); everything else is a runtime outcome. The worker's self-reported class and message are untrusted payload, stored only for the release preview.

- A run is **dispatched** once the host has committed `SCRIPT_CALL_SENT`, i.e. when it accepted the run's first validated host call, before any limiter wait and before the first HTTP request to Atlassian (§9.1 step 4), so a wait behind other requests in the per-instance limiter (§7.2) never makes a run data-free. Every dispatched host call ends in a committed `SCRIPT_CALL` with its outcome — successful response, upstream-error rejection, `result_too_large` or `max_fetch_mb`/`max_call_result_mb` overrun on a streaming body, network error, per-call timeout (§7.2), or `cancelled_in_flight` (§3.4) — with the request params and any bytes received, before anything is returned to the worker.
- **Direct data-free return** (the single rule): a run's failure is returned directly — `failed`, exit 8, `error.code = script_syntax | script_limit` (syntax errors include line/column/message) — only if it is a submit-time compile failure, or a host-measured limit of a run that is **not `queued` and not dispatched**. This rule is recorded as `SCRIPT_FAILED {direct: true}` (§8.3) and is the only one that decides terminality and release-gating; a failure that is data-free (not dispatched) but not direct, such as a user kill, worker crash or protocol violation before the first host call, is still a release item. A run is `queued` when it waited for a real-run slot held by another real run (§9.4; recorded in `SCRIPT_STARTED`); since its start time depends on how long other runs took, every outcome of a `queued` run, including a data-free `script_limit` (timeout, op budget, OOM), goes through `AwaitingRelease`, with the "keep error class only" preset pre-selected.
- **Every other termination** — success, runtime error (including a `SyntaxError` from `JSON.parse`/`eval` of fetched text), any limit once dispatched (timeout or kill while a call is in flight, OOM, budgets, size), user kill, worker crash, protocol violation, a caught network error or per-call budget rejection followed by any later termination — becomes a single `AwaitingRelease` item, except kills by the shutdown path (§2.5) and client cancels (below), which end in `CANCELLED` and never reach the release flow. **Exception**: an audit append failure always ends the run as `failed`, `audit_failure`, exit 1 (§5.1 inv. 1), with nothing released. The candidate is the result (`SCRIPT_FINISHED`), or the error details `{class, message, stack, elapsed, logs}` (with captured stderr) stored in `SCRIPT_FINISHED` or, for a host-decided termination, in the `SCRIPT_FAILED {direct: false}` payload (§8.3). Until the decision, the agent sees only `pending` (§4.5): no error class, no timing, no Running/AwaitingRelease distinction.
- **Client cancel** (`cancel`, MCP `request_cancel`) of a `Running` run: the host kills the worker as in §2.5 step 3 (`TerminateJobObject`/`SIGKILL`), logs the non-terminal `SCRIPT_FAILED {reason: cancelled_by_client}` and then `CANCELLED {by_client}` (a run still waiting for a slot gets only `CANCELLED {by_client}`), and answers with the same envelope as a cancel in `AwaitingRelease`, without waiting for the worker to be reaped (§4.4; commit latency is the §10.2 shared-resource residual). It never becomes a release item.
- On release of a result: `released`, exit 0. On release of error details: `released`, exit 8, `data.script_error`. On deny: `denied`, exit 3.
- `atlas.log` output and captured stderr never reach the agent unless the user includes them in a release.
- In-script rejections (`validation`, `result_too_large`, `needs_token`, upstream errors, and `atlas.all`'s `script_limit`) are catchable and do not by themselves end the run or change its classification. Only limits the host enforces by terminating the run count as limit outcomes.
- **Dry runs** (§9.1 step 7) are data-free by construction: every host call is answered from the registry's static examples, so a dry run's result, error details and logs derive only from the agent's own source and args. The outcome returns directly without release: `succeeded`, `meta.dry_run: true`, exit 0 with `{result, logs}` or exit 8 with `{script_error}` (§4.3); compile errors and host-measured limits give `script_syntax`/`script_limit` directly. Dry runs run in their own pool (§9.4) and never wait on a real-run slot, so their completion time does not depend on real-run slot occupancy (shared audit-writer latency is the §10.2 shared-resource residual). Logged as `SCRIPT_DRY_RUN` (terminal, §8.3). Onboarding tells agents to dry-run a new script first (§12.4), so shape errors (null assignees, wrong keys) are found without a release.
- **"Keep error class only"**: for a real run's error-details release item, a one-click redaction preset releases only `script_error.class` (message, stack and logs dropped), for approvers who cannot judge a stack trace. It is pre-selected for the data-free limit outcome of a `queued` run.
- **Host-computed preview warning**: the release preview states "N host calls returned truncated or lossy data". It counts calls whose internal `meta` reported `page.truncated` or `conversion.lossy`, which the script itself cannot see. The count comes from host state, never from the worker.

### 9.6 Running-scripts UI

Live list: agent, instance(s), started, elapsed, host calls, bytes fetched; per-script kill button (→ the run becomes an AwaitingRelease item per §9.5, logged `SCRIPT_FAILED {reason: killed_by_user, direct: false}` with its candidate payload, also before the first host call).

## 10. Security summary

### 10.1 Defense in depth

| Layer | Control |
|---|---|
| Credentials | PATs only in OS keychain (or KEK-wrapped vault), used only by the app's HTTP client; never in IPC, UI, logs, sandbox. In memory, PATs and passphrases are held in a non-`Serialize`, redacting secret type (e.g. `secrecy::SecretString`, `Debug` prints `[REDACTED]`), so no DTO, log line, Tauri response or audit payload can carry one; exposure is limited to building the `Authorization` header and keychain/vault I/O. Verified by the canary sweep (§13). |
| Local access | User-restricted pipe/socket; peer uid/SID checks; owner checks before the first byte (§3.2 (a)) and exact `build_id` match in `hello` (§3.3); detached app launch. |
| Capability | Fixed operation registry; field/expand rules; caps; method guard (GET + allowlisted POST outside approved writes); no passthrough. |
| Human control | Every write approved byte-for-byte (request-set hash); every read released; edits/redactions re-validated in Rust, target params and conflict baselines immutable in Rust (`DECISION_INVALID`); decision bound to `candidate_rev`; Rust-computed approvability (`not_approvable`); all-or-nothing batches; identity + stale check before writes (§5.4 step 5); no blind approvals (opened-flag, modifier chords, focus delay). |
| Opacity | Agent sees only agent-visible status changes (§4.5); upstream errors, read cap/budget outcomes and script outcomes after data exposure (or after waiting for a script slot) are release-gated, and post-send enrichment outcomes are approval-gated (§5.4 step 2); script-slot occupancy and the size of pending candidates are never observable through IPC/MCP responses (§9.5, §5.2); shared-resource latency and file/process observability by the same user are a documented residual (§10.2). |
| Script isolation | Separate process, no credentials, minimal JS intrinsics, resource limits, OS confinement, Read-only enforced host side. |
| Data exfil via UI | Sanitized previews, no remote loads, links as text, invisible-character marking, raw diffs. |
| Frontend | In the TCB (§2.4). Per-window capabilities and navigation lockdown (§10.3), explicit CSP and text-only rendering outside the sandboxed preview iframe (§6.4), `freezePrototype`, per-window grants via capability files, typed `deny_unknown_fields` arguments with Rust bounds checks, global isolation hook (known command names, payload size caps; no window context), decision binding and opened-state in Rust, devtools disabled, debug env vars scrubbed (§2.5). Against a compromised webview only the native confirmations for security-weakening settings (incl. instance base URLs, §7.1), Rust-chosen paths/certificates and the credential window hold; batch confirmation and the opened flag guard only against accidental or blind approvals, and a compromised approvals webview can approve every pending item individually (§2.4). |
| Process hardening | App memory unreadable by same-user processes on Linux (non-dumpable) and macOS (hardened runtime); on Windows unreadable only by lower-integrity/AppContainer subjects incl. the worker, while ordinary same-user processes are within the accepted §2.4 limits; checked by the §9.4 probe, never blocking startup (§2.5); CLI launches the app detached with a sanitized environment (§4.7); worker spawned with an explicit handle list and empty environment (§3.4). |
| Logs | Diagnostic logs metadata-only; payload-free panic hook, `panic = "abort"`, redacting `Debug` on request/response types, stderr to null, WER exclusion and cleared WebView2 crash reports (§2.5, §7.7); Atlassian content persisted only in the encrypted audit. |
| Audit | Encrypted payloads, AAD binding, hash chain from genesis, head/first-retained anchors, never-pruned `prune_log`, optional external anchor directory (unsigned lines), persistent integrity incidents, retention ≥ 92 days with clock guards. |
| Supply chain | `cargo-deny`, `cargo-audit`, `npm audit` in CI; pinned rquickjs; for a QuickJS-NG security advisory, a fixed atlas-duck release within 7 days, rolled out through the operator's software distribution (no auto-update, §1.3); `APP_START` records `engine_version` so the audit log shows which engine ran each script. |

### 10.2 Residual channels (accepted, documented)

- **Decision timing**: when the agent's call returns reveals when the human decided (and that a decision was approve/deny). This is chosen by the user, not by data.
- **Data-free failures**: validation errors (static), 401/needs-token state, connection-level network/TLS failures before the request was written (direct reads and enrichment, §5.2 step 6, §5.4 step 2), `upstream_unavailable` decided from status and headers alone (redirects, a 2xx with a non-JSON or missing `Content-Type`, a non-JSON 401, the identity-header states; body audit-only, §7.2; a JSON 2xx whose body fails to read or parse is release- or approval-gated instead), and directly returned script failures (`SCRIPT_FAILED {direct: true}`: a compile failure, or a host-measured limit of a run that was neither `queued` nor dispatched any HTTP request, §9.5) reveal no Atlassian content; nor do script dry runs (§9.5), which reveal only registry examples and validation results.
- **Deny hints**: `resolution_failed`, `missing_fields` and enrichment-error details reach the agent only when the user attaches them to a deny (§5.4 step 2); candidate names and allowed values only when the user ticks them. Enrichment size and timeout outcomes (per-call timeout or network error after send, 32 MiB per-response cap) likewise reach the agent only through a deny, as the outcome class with a fixed message and no size; until then it sees `pending`.
- **Busy/queue signals**: reveal only queue load, i.e. the count and kind of pending requests, which the agent already knows; `max_pending_bytes` (§5.2) is computed from fixed per-request reservations, never from fetched sizes. Script-slot occupancy is never observable through IPC/MCP: saturation is never answered with `busy`, and dry runs and data-free failures never wait on a real-run slot (§9.4, §9.5).
- **Content-size outcomes**: `result_too_large` (release cap or 50 MiB fetch cap) and read time-budget/timeout outcomes reach the agent only when the user releases the outcome item (§5.2 step 6): outcome class and a fixed hint, no size, no content.
- **OS-level process visibility**: a same-user process can observe sandbox worker process lifetimes at OS level (§2.4), so the "no timing" promise for scripts (§9.5) covers the IPC/MCP API only.
- **Shared-resource and filesystem observability** (same OS user, outside the IPC/MCP envelope): response latency from contention on the single audit writer (§8.1) with other requests' commits (e.g. a `READ_FETCHED` of up to 50 MiB or large `SCRIPT_CALL` payloads), including a request's own bounded local audit commits (e.g. `READ_FETCHED`/`PREVIEW_FETCH {cancelled_in_flight}` before `CANCELLED`, §4.4); the audit DB/WAL file size and mtime; the app's CPU, memory, I/O and network counters; and contention in the per-instance limiter (§7.2). These can reveal roughly when unreleased fetches finished and how large they were, never their content. The channel cannot be closed without agent authentication (§2.4), which is out of scope (§1.3).
- **Write receipts**: the op's static `result_projection` (Jira `id`, `key`; Confluence `id`, `type`, `status`, `version.number`, `_links.webui`) is released by approving the write (§4.2, §5.6); no other response field reaches the agent. For an edited write, approving also releases `edited_keys` (param names; `added` may name createmeta-derived field ids such as `fields.customfield_10200` the agent never sent, never their values).
- **Coarse version range via op availability**: `available: bool` per op (`ops list/describe --instance`, §2.3) and `op_unsupported_by_instance` with the static `min_version` (§7.1) reveal only which side of a registry version gate the instance is on, never its version string.
- **Write error text**: after an approved write fails with 4xx, the Atlassian `errorMessages`/`errors` (≤ 2 KiB) are returned without a separate release; they describe the approved payload but may quote server state.
- **Same-user processes** can list and `await` any request (including released data within the 1 h window); every delivery is logged with the recipient and highlighted in the Audit window.

### 10.3 Frontend lockdown

- **Per-window capabilities** (Tauri capability files, `app.security.capabilities` set explicitly; all custom commands declared in the app manifest; tested in §13 that commands outside a window's grant are rejected):

  | Window | Granted commands |
  |---|---|
  | Approvals | queue list/get, preview fetch for a rev, approve/deny/edit/redact, batch request (Rust confirms natively); header (§5.6): `open_window {settings\|audit\|running_scripts\|onboarding}` and `quit` triggers (no other arguments) and read-only `app_status` (the app-generated status lines) |
  | Audit | read-only queries and payload view; export/backup/verify **triggers** (no path arguments) |
  | Settings | settings, instance setup (adding an instance or changing its base URL is applied only after a Rust-drawn confirmation, §7.1), **credential-entry trigger** (opens the credential window), "Re-test stored token" trigger (§7.1), CLI install, retention/legal hold, confinement toggle, "Prepare for removal" trigger (Rust confirms natively, §12.5) |
  | Credential entry | `submit_secret` (PAT with an optional non-secret "token expires on" date (§7.1), recovery passphrase (entered twice, §8.6), unlock passphrase, recovery passphrase for "Recover this log" and "Finish restore", §8.7; for a PAT it returns the connection-test result, never the secret), read-only `credential_context` (the header below), a "Save recovery note" trigger (Rust save dialog, §8.6), plus an "Archive old DB and start fresh" trigger (Rust confirms natively) and the `quit` trigger (§2.5) |
  | Running scripts | list, kill |
  | Onboarding | read-only registry/onboarding text |

  No window gets shell, fs, http, opener, clipboard-read or remote-URL capabilities. Decision commands exist only in the Approvals window; credential commands only in Settings. The Approvals header triggers only ask Rust to open its own windows (each with its own capability file) or to run the §2.5 shutdown path; they add no command of the opened windows to the Approvals grant, and a `quit` from a compromised approvals webview is no worse than the deny-all it can already do (§2.4). Capability files are the only per-window control; argument validation is in Rust (typed, `deny_unknown_fields`, bounds checked) for every command. The isolation hook (§2.4) is global and sees no window label: it passes only known command names under a payload size cap. The isolation app's scripts are inlined in its HTML (Windows iframe limitation) and use no ES modules. The Audit window is a separate webview whose capability file grants no decision commands; it renders decrypted payloads through the same sanitized, sandboxed-iframe path as §6.4.
- **Navigation**: every webview registers an `on_navigation` handler that applies an origin allowlist to **main-frame** navigations: only the app's own origin (`tauri://localhost` / `http://tauri.localhost`). Where a platform also reports subframe navigations to the handler, `<isolation-origin>` (§6.4) and `about:srcdoc` (the preview iframe) are allowed for subframes as well. `window.open`/new-window requests are denied. No external-link opener in v1 — URLs are copyable text. No clipboard-read; copy is write-only on a user gesture.
- **Secrets** (PATs, recovery passphrase, unlock passphrase) are entered only in a dedicated, Rust-opened **credential-entry window**: a separate webview with a static bundled page, no untrusted content, and only the commands of its row above: `submit_secret` (write-only for the secret; for a PAT it returns only the connection-test outcome), the read-only `credential_context` and the recovery-note trigger (it is also used for first-run and unlock). Secrets are never sent to, displayed in, or returned to any webview after entry; other windows can only trigger the credential window. All other windows share one origin and one browser profile (localStorage, IndexedDB, BroadcastChannel, service workers), so the credential window is separated from them explicitly:
  - opened with `WebviewWindowBuilder::incognito(true)` (or, where a platform lacks it, its own `data_directory`), so it shares no storage or profile with the other windows;
  - built as its **own HTML entry point** that shares no JS/CSS chunks with the main bundle and uses no `localStorage`, `sessionStorage`, IndexedDB, `BroadcastChannel` or service workers;
  - its own CSP, delivered as the first `<head>` element (`<meta http-equiv>`) of that entry page and enforced together with the app-wide header policy (§6.4): `default-src 'none'; script-src 'self'; style-src 'self'; connect-src ipc: http://ipc.localhost; frame-src <isolation-origin>; worker-src 'none'; form-action 'none'; base-uri 'none'` (`<isolation-origin>` per platform, generated at build time, §6.4; `frame-ancestors 'none'` comes from the header policy, since a meta CSP cannot carry it). Its stylesheet hides the isolation iframe (§6.4).
  - **Context header**: Rust fixes the window's context when it opens it (never taken from the triggering window) and serves it through the read-only `credential_context` command; the page shows it as a read-only text header: purpose (add/replace PAT, recovery passphrase, unlock, "Recover this log", "Finish restore"), for a PAT the instance alias, product and normalized base URL, and for unlock the app-generated "Locked — N requests refused" count (§2.5). The window also has a Quit button (`quit` trigger, §2.5), so a locked app can be quit without a tray host.
  - **PAT connection test in the window**: on `submit_secret` for a PAT, Rust runs the §7.1 connection test (`SYSTEM_FETCH {purpose: connection_test}`) with the entered token before storing anything. The window shows "Connected as <atlassian_user>, Jira|Confluence <version>" or the failure class (§11.2 TLS/proxy hints, 401, version below the §7.1 floor, Jira `identity_header_missing`/`identity_header_mismatch`, §7.1) and stays open on failure. It cannot be opened for an `http://` instance (`insecure_scheme`) or an instance whose origin is not yet natively confirmed (§7.1). The PAT is stored (and `CREDENTIAL_CHANGED` logged, after the §7.1 identity comparison) only if the test passes; on failure nothing is stored and the old PAT, if any, stays.
- **Paths and certificates** for export, backup, restore, the recovery note (§8.6), external anchor directory and custom-CA import are chosen in a **native dialog opened by Rust**; no command accepts a filesystem path or certificate bytes from the webview. A custom CA shows its fingerprint and subject in the Rust-drawn dialog.
- **Security-weakening settings** (restore backup, archive old DB and start fresh (§8.7), "Prepare for removal" (§12.5), add custom CA, lift legal hold, lower retention, raise limits, enable degraded script confinement, passphrase mode without external anchor, change or remove the external anchor directory (§8.5), replace a PAT with one belonging to a different Atlassian user (§7.1), change an instance's base URL or add an instance (from Settings, the first-run wizard or `config.toml`; the dialog shows the alias and the old/new normalized origins, §7.1)) require a Rust-drawn native confirmation and are logged as `CONFIG_CHANGED` with old and new values (the PAT replacement as `CREDENTIAL_CHANGED` with old and new user keys). The attention mode (§5.6) is not security-weakening: a missed request fails closed (it waits or expires), so switching modes, including the tray's "Presentation mode", is a plain `CONFIG_CHANGED`.

## 11. Error handling

### 11.1 Fail-closed rules

- Audit append failure → no upstream call / release / execution; request `Failed`, `audit_failure`, exit 1; UI banner.
- Low audit storage → new requests refused (`audit_storage_low`, exit 1).
- Keychain unavailable / keychain entries lost / keyring on a network filesystem / passphrase mode locked → all requests rejected, exit 9 `locked` with `details.reason` `keychain_unavailable` / `keychain_lost` / `keyring_not_local` / `passphrase` (§8.6, §8.7). A lost keychain never triggers first-run setup or a new `GENESIS` (§2.5). Pending schema migrations wait until the KEK is available (§8.13), so an upgrade start while locked also answers `locked`, never `internal`.
- Validation failure → exit 2, nothing queued, logged `REQUEST_RECEIVED` (committed before validation) + `REQUEST_REJECTED`.
- Store written by a newer atlas-duck → nothing opened or written, requests exit 5 `store_newer` (§8.13).
- Shutting down → new requests refused, exit 5 `app_shutting_down` (§2.5).

### 11.2 Upstream errors

- **Reads / script calls / enrichment**: HTTP status ≥ 400 (except 401) is content — release-gated (§5.2 step 6, §9.5) or, for enrichment, approval-gated (deny with optional details, §5.4 step 2). For scripts, an upstream error is returned to the script as a rejected promise (it is fetched data; the run is no longer data-free).
- **401 and identity mismatch** → a JSON 401, or a Jira response whose `X-AUSERNAME` is missing, `anonymous` or another user (§7.2; its body audit-only), confirmed by the §7.1 re-test (a `token_recheck` that is not an identity match) → instance `needs_token` (logged `INSTANCE_STATE_CHANGED`; the stored PAT is kept). Direct reads (`READ_FAILED`) and enrichment (`REQUEST_FAILED`): `failed`, exit 9, directly. Script host calls: the call rejects inside the script with `needs_token` (run outcome per §9.5). Write execution: a JSON 401 → `WRITE_FAILED`, `failed`, exit 9 `needs_token`; a 2xx write response with an `X-AUSERNAME` mismatch → `WRITE_OUTCOME_UNKNOWN {identity_mismatch}`, exit 6 (§5.4 step 6). Stale checks: `WRITE_STALE {identity_mismatch}`, nothing sent (§5.4 step 5). If the re-test passes, a header mismatch is `upstream_unavailable` (except the rename and header-loss cases below); the mismatch alone never sets `needs_token`. A non-JSON 401 is `upstream_unavailable` (below).
- **Redirects and non-JSON responses** (any 3xx, a 2xx with a non-JSON or missing `Content-Type`, non-JSON 401; decided from status and headers alone, §7.2) → `upstream_unavailable`: direct reads and enrichment fail data-free (exit 6, body audit-only); script host calls reject inside the script; write execution: 3xx → `WRITE_FAILED`, a 2xx that is not the op's declared success → `outcome_unknown` (a declared empty 201/204 is `WRITE_EXECUTED`, §7.2).
- **Body-decided failures** (a 2xx with a JSON `Content-Type` whose body fails to read or parse, §7.2) → never data-free: direct reads → release-gated outcome item (§5.2 step 6); enrichment → the "enrichment failed" state (§5.4 step 2); stale checks → `recheck_failed`; script host calls → in-script rejection, release-gated (§9.5); writes → `outcome_unknown`.
- **Username rename** (`user_renamed`, §7.1): a Jira response whose `X-AUSERNAME` names the PAT's user under a new name is not a token failure and not generic `upstream_unavailable`: the key-matched re-check updates the stored name (`INSTANCE_STATE_CHANGED {user_renamed}`), the call is re-fetched once (writes: never; they stay `outcome_unknown`), pending writes are refreshed with the Caution "Atlassian username changed", and the instance heals without a new PAT.
- **Identity header lost** (`identity_header_missing`/`identity_header_mismatch`, §7.2): `X-AUSERNAME` absent (e.g. stripped by a reverse proxy) or not matching on both the data response and the key-matched re-check → instance state with the admin hint; reads and enrichment fail directly, exit 6, `retryable: false`; pending writes keep Approve disabled with that reason. Replacing the PAT does not help; "Re-test stored token" clears it once the header is back.
- **Stale-check / refresh failures** (anything but a parsed 2xx JSON response) → `WRITE_STALE {reason: recheck_failed, class}`, back to `AwaitingApproval` flagged "Could not re-check target"; nothing is sent (§5.4 step 5). During a maintenance window approved writes therefore return to the queue instead of landing as `outcome_unknown`.
- **429** → bounded retry (§7.2), then the same as other upstream errors.
- **Read cap and time-budget outcomes** (direct reads: `result_too_large`, read-budget expiry, per-call timeout or network error after the request was sent; §7.2) → release-gated outcome item (§5.2 step 6), never returned directly.
- **Enrichment post-send failures** (per-call timeout after send, network error or reset after send, 32 MiB per-response cap; §7.2) → the "enrichment failed" approval state with Approve disabled; the agent sees `pending` and learns the outcome class only through a deny hint (`denied`, exit 3, §5.4 step 2), never directly.
- **Connection-level network/TLS errors** (before the request was written: DNS, connect, connect timeout, TLS handshake, proxy CONNECT/407; for reads and enrichment alike) → direct reads and enrichment: exit 6 `upstream_network` with a message chosen by failure class: unknown issuer → "certificate not trusted — add a custom CA in Settings"; name mismatch, expired or not-yet-valid, or unsupported certificate → "server certificate problem (<class>) — contact the server administrator" (adding a CA does not help); proxy unreachable or 407 → "proxy error — see `doctor`"; script host calls: the call rejects inside the script; sent writes: `outcome_unknown` (§5.4 step 6).
- **Writes after approval**: 4xx (other than 401) → `WRITE_FAILED`, the Atlassian `errorMessages`/`errors` (capped 2 KiB) returned with exit 6 (the user approved this write; the error describes the agent's own payload — a listed residual channel, §10.2). Version conflicts → `WRITE_STALE` (§5.4). Timeout/reset after send/5xx → `outcome_unknown`.

### 11.3 Crash / restart reconciliation

- Pending requests' queue state is in memory (candidates are cached or rebuilt from committed audit records, §5.2) and is not resumed after a restart; on crash, CLI connections drop (waiting CLIs print `pending` with `error.code = unreachable`, `details.reason = connection_lost`, exit 4; the request id was already printed to stderr). A clean exit leaves no request to reconcile (§2.5 shutdown path); this section covers hard kills, crashes and power loss.
- On startup, the app scans request ids that have **no terminal event** (§8.3), not those whose last event is non-terminal, and reconciles by write state, using the same predicate as §5.1 inv. 3:
  1. A write whose latest `WRITE_APPROVED` is not followed by `WRITE_STALE`, `WRITE_EDITED` or `WRITE_DENIED` gets `WRITE_OUTCOME_UNKNOWN {request_index, reason: crash}` for its approved request (every v1 write is one request, §5.1 inv. 3), whatever non-terminal events trail the approval (`PREVIEW_FETCH {stale_check|refresh}`, `DECISION_STALE`, `DECISION_INVALID`, `PREVIEW_SHOWN`, `DELIVERED`). Its target is listed in the startup "check target" notice.
  2. Only then does every remaining non-terminal request get `ABANDONED`. This includes a script whose latest event is a non-direct `SCRIPT_FAILED` (a pending release item, §8.3).
  A crash during the stale-check GET itself, before the write was sent, is deliberately reported as `outcome_unknown`: this over-reports, in the safe direction (the agent is told to check the target, never to blindly resubmit).
- A `SYSTEM_FETCH` start record without a result record is left as is; it has no request id and needs no reconciliation.
- A read or enrichment GET in flight at a hard kill leaves no `READ_FETCHED`/`PREVIEW_FETCH` (the bytes received were only in memory); that request is covered only through its `REQUEST_RECEIVED` (full params) and its reconciliation event. The `cancelled_in_flight` records (§4.4) exist only for clean cancels, expiries and the shutdown path.
- `await` on such ids returns `abandoned` (exit 7, `retryable: true`) or `outcome_unknown` (exit 6, `retryable: false`), read from the audit log; `status` reports the same status with exit 0 (§4.4). An unknown id → exit 2 (`unknown_request`).

### 11.4 UI resilience

The Rust core is the single source of truth; reloading the webview loses no state.

## 12. Packaging, distribution, onboarding

### 12.1 Binaries

`atlas-duck-app` (main), `atlas-duck` (CLI + MCP), `atlas-duck-sandbox` are all `[[bin]]` targets of the Tauri package (thin `main`s calling into their crates), so the Tauri bundler ships them next to the app on every platform without target-triple renaming. `default-run = "atlas-duck-app"`.

**CLI mode of the app binary (AppImage dispatch)**: an AppImage's `AppRun` starts only `atlas-duck-app`, so `atlas-duck-app`'s `main` checks, before Tauri or any startup hardening initializes, whether its first argument is the reserved marker `__cli`; if so it strips the marker and hands the remaining argv to the `cli` crate's entry point (the same one the `atlas-duck` bin wraps), never touching keychain, DB or webview. An argv marker is used rather than an environment variable because §4.7 rebuilds the environment. The marker is only an entry-point switch, not an identity or security control (§3.2 (b)).

**Export verifier mode (`__verify-export`)**: a second reserved early-argv marker, checked at the same point as `__cli` — before the Tauri builder, the single-instance plugin, startup hardening and the §2.5 stderr redirect, the app-side data-dir check and `instance.lock`. It runs the `audit` crate's export verifier (§8.10) and exits. It is read-only: it reads only the export dir, the optional anchor dir and the given manifest hash; it never opens the keychain, the vault, the live DB or a webview, and it is never forwarded to a running instance. `atlas-duck-app --verify-export …` is accepted as an alias at the same early check (no console on Windows, so not the documented form).
- **User-facing entry**: `atlas-duck verify-export <dir> [--anchor-dir <dir>] [--manifest-sha256 <hex>]` (§4.1). The CLI locates the app as in §3.2 "App location" (a missing app binary is a usage/I/O error, exit 22, with the same reinstall hint, not exit 5) and runs `atlas-duck-app __verify-export …` as a child with **inherited stdio** (not the §4.7 detached launch), waits for it and passes its exit code through, so the §2.2 rule that `cli` depends only on `ipc` + `registry` holds. Under AppImage this is the same wrapper path as `__cli` (§12.3); the CLI runs `$APPIMAGE __verify-export …`.
- **Output and exit codes**: the report goes to stdout, diagnostics to stderr. `0` = verified against a supplied trust root (`--anchor-dir` and/or `--manifest-sha256`); `20` = internally consistent, trust root not verified; `21` = tamper or fork detected (§8.11); `22` = usage or I/O error. Every startup, argument or panic failure exits non-zero.

### 12.2 Per OS

- **Supported baselines** (v1): Windows 10 22H2+ and Windows 11 (x86_64); macOS 13+ (arm64 and x86_64); Ubuntu 22.04+ (`.deb`, AppImage); Fedora 40+ (`.rpm`, AppImage). Every shipped package is built and tested in CI (§13).
- **Windows**: NSIS installer, `installMode: both`; per-machine (Program Files) recommended for tamper resistance. Authenticode signing. WebView2 bootstrapper. In both modes the installer grants the (L)PAC read+execute ACEs on the sandbox worker and its DLLs (§9.4), so scripts work in per-user installs too. **Upgrade drain**: an `NSIS_HOOK_PREINSTALL` (and `NSIS_HOOK_PREUNINSTALL`) hook asks the running app to quit (shutdown path, §2.5, `APP_STOP {reason: installer}`), waits up to 90 s, then terminates remaining atlas-duck processes whose image is in the install dir (incl. long-lived `atlas-duck mcp` processes, which otherwise lock `atlas-duck.exe`). The finish page says: "Restart your MCP clients so they use the new version."
- **macOS**: `.dmg`, signed + notarized, hardened runtime; every binary in `Contents/MacOS` signed. Separate arm64 and x86_64 builds in v1 (universal builds need custom `lipo` for extra bins). Replacing the bundle while the app runs is handled like a Linux package upgrade (below).
- **Linux**: `.deb` and `.rpm` (binaries in `/usr/bin`, CLI on PATH; depends on WebKitGTK 4.1 and libayatana-appindicator3; install an `atlas-duck.desktop` launcher in `/usr/share/applications`), AppImage (CLI via in-app install; embeds the same `.desktop` entry, and "Install CLI to PATH" also writes it to `~/.local/share/applications` with `Exec` = `$APPIMAGE`, §12.3). The launcher starts the app with no arguments, so on a desktop without a tray host (§2.5) it opens the Approvals window. A package upgrade replaces files under a running app; the old app keeps serving until restarted, refuses script runs data-free (`app_upgraded`, §3.4) and shows "Updated — restart to apply"; the CLI reports `app_upgraded` from the `build_id` comparison (§3.3).
### 12.3 Install CLI to PATH (in-app, all OSes)

Writes `cli.toml` (`app_path`). Windows: append install dir to `HKCU\Environment\Path` (REG_EXPAND_SZ) + broadcast `WM_SETTINGCHANGE`. macOS: symlink `~/.local/bin/atlas-duck` (or `/usr/local/bin` with admin prompt). Linux AppImage: wrapper script `~/.local/bin/atlas-duck` with the AppImage's stable absolute path (`$APPIMAGE`, §3.2) baked in as `APPIMAGE_PATH`: if that file is missing or not executable, it prints the fixed §4.2 envelope for `failed`, exit 5, `unreachable`, `details.reason = not_running` with the hint "atlas-duck AppImage not found at <path>; re-run Install CLI to PATH" and exits 5; otherwise `exec "$APPIMAGE_PATH" __cli "$@"` (§12.1). It also writes the `.desktop` launcher to `~/.local/share/applications` (§12.2). `cli.toml` `app_path`, the launcher's `Exec` and the autostart entry (§2.5) record `$APPIMAGE`, never `current_exe` or a `/tmp/.mount_*` path. Moving the AppImage requires re-running the install; `doctor` reports a missing or moved file as `not_running` with that hint. deb/rpm: already on PATH.

### 12.4 Agent onboarding

A Settings page generates copy-paste instructions (for CLAUDE.md / AGENTS.md / MCP client config) from the registry:
- commands, the envelope, the status/exit matrix;
- "approvals take human time: set `--timeout` at least 10 s below your tool's kill timeout (e.g. `--timeout 100` under a 120 s tool; it counts from CLI start, including an app launch), or use `--timeout 0` and `await`; the request id and `params_sha256` are printed to stderr on submit; **never resubmit a pending request — if the id was lost, find it with `requests list --match-params-file <same params>` and `await` it**";
- "set `ATLAS_DUCK_AGENT=<tool>-<repo>` once per session (e.g. `claude-code-billing-api`) and always pass `--reason`, so the approver can tell sessions apart";
- "results may be redacted or edited — check `redacted`, `edited`, `meta`. A key missing from an item while named in `meta.redactions.fields_dropped` means withheld, not empty (a real `null` is the server's). If a write comes back `edited: true`, check `edited_keys` and re-read the target before any follow-up edit";
- "with several pending ids, use `requests list --agent <name>` to see which are decided, `await` only those, and do other work in between; `status` never blocks and never returns data";
- "for the next page, continue **only** from `meta.page.next_start` (never `start + returned`; redacted items would come back as new approvals); `total` is the server's total";
- "for writes, submit human names (project, issue type, transition, user, link type, parent page); the app resolves and validates them — do not pre-read createmeta, transitions or assignable users; if you need metadata, fetch it in one script";
- "batch many reads into one script instead of many parallel calls; on exit 11 back off";
- "run every new or changed script with `--dry-run=sparse` and `--dry-run=full` first (no approval needed; results come from documented examples, `meta.dry_run: true`), then run it for real once";
- "branch on `status` + `error.code` + `error.retryable`, never on the exit code alone. Resubmit only if `retryable` is true, with these exceptions: `denied` — resubmit (changed) only if the message asks for a change; `expired` — only if the user asks; `resolution_failed` — fix the named param. `pending` (exit 4, also after `connection_lost`) — `await` the id, never resubmit";
- "on `outcome_unknown`, check the target before retrying";
- "on exit 9 (`locked`, `needs_token`, `not_configured`), do not retry in a loop: tell the user what the app needs (unlock, recover, re-enter the token, configure), wait until they confirm, then retry once";
- "Confluence pages with macros: edit with `body_format=storage`. A Markdown body that still contains `page get` placeholders (`[macro: …]`, `confluence:` links or images, `@user:<key>`) is rejected with `markdown_placeholders`: fetch with `--format storage` and submit `body_format=storage`";
- "if `jira.issue.create` is denied with `error.details.missing_fields`, supply those fields via `--field id=<json>` / `fields` and reuse them for later creates in the same project and issue type";
- "page update requires `base_version` = the `version.number` you read; for issue edits pass `expected` with the values you read for each edited field. If someone changed the target since, the request is denied: re-read and resubmit";

### 12.5 Uninstall

- **Uninstallers never touch retained data or secrets**: NSIS uninstall, `apt remove`/`apt purge`, `dnf remove` and removing the macOS bundle leave the data dir (audit DB, `instance.lock`, `endpoint`, `anchor`, logs, `webview`), the config dir (`config.toml`; on macOS/Linux also the host-qualified `paths-<hostname>.toml` and `cli-<hostname>.toml`), (Windows) `paths.toml` and `cli.toml` in `%LOCALAPPDATA%\atlas-duck` (§7.7), the external anchor dir and all keychain entries in place. The Tauri NSIS "delete app data" option is disabled (and the bundle identifier differs from the data-dir folder name, so the uninstaller's app-data cleanup can never resolve to it); deb/rpm maintainer scripts contain no `purge` step for user data. A CI check inspects the built installers and package scripts for both rules.
- **Reinstall** onto an existing data dir continues the existing chain: §8.13 version gate, §8.7 verification (then migrations), or the keychain-loss path (§8.7) if the keychain entries are gone (§2.5).
- **"Prepare for removal"** (Settings; Rust-drawn native confirmation, §10.3; logged `CONFIG_CHANGED`):
  1. offers a compliance export and a full backup (§8.10; backups never contain tokens) and shows the remaining retention days of the newest record;
  2. deletes the stored PATs (`CREDENTIAL_CHANGED` per instance, instances `needs_token`), then shows, per instance, the step "Revoke this token in Jira/Confluence (Profile → Personal Access Tokens)" with the instance alias and token identity, which the user must tick as done (or explicitly mark as skipped) before the procedure completes; the choice is recorded in the `CONFIG_CHANGED` record (DC PATs stay valid server-side until revoked);
  3. removes autostart, the HKCU `Path` entry (Windows), the `~/.local/bin` symlink or AppImage wrapper and its `~/.local/share/applications` launcher (§12.3), and `cli.toml`;
  4. keeps the KEK, anchors and audit DB, so the log stays verifiable and recoverable with the recovery passphrase until retention has passed.
- **Documentation** lists the remaining paths and keychain entries per OS (data dir, config dir, `paths.toml`, runtime socket dir, keychain service `atlas-duck/<install_id>/*`) for manual deletion after the retention period (§8.12). On macOS/Linux it names the host-qualified pinned files (`paths-<hostname>.toml`, `cli-<hostname>.toml`, §7.7) and states that on an NFS-shared home each host has its own pair and its own `install_id`-scoped keychain entries, to be removed per host.
