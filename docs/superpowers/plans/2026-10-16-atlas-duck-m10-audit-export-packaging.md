## Global Constraints

The master plan's Global Constraints and the M6 plan's Global Constraints (TCB rules, rendering, text, opacity, secrets, threads, lints, logs, test-only code, tests, commits) apply verbatim. In addition:

- **Export is decrypted data (§8.10, L41):** only `Store::export` writes it, only into a directory Rust chose in a native dialog (`RustChosenPath`, L54 grep check T1), only into a new empty subdirectory it creates itself, manifest last. On macOS/Linux the subdirectory is created `0700` and every file `0600` with create-new; on Windows the files inherit the user-profile ACL of the chosen folder (stated in the dialog text's docs, T32). If the final `EXPORT` append fails, the directory is removed and the failure is reported, so no unlogged export is left behind (a crash between the manifest and the append is the one residual, L186). The export dialog warns that the files are decrypted and readable by any same-user process (§8.10 states the content, not the sentence; the UI sentence is plan text, PD-161).
- **The export directory is adversarial input** to `verify_export` (a recipient verifies files someone else made) and to a `panic = "abort"` release binary: the verifier streams the files once (no whole-file buffer, no in-memory copy of the export), every read is bounded per item (line length, base64 length, decoded payload ≤ `MAX_PAYLOAD_LEN`, JSON depth, anchor-dir sizes), no recursion on input structure, no allocation proportional to a claimed length before the bytes are read; the working set is one row plus a bounded map of in-range anchor lines, never proportional to the export; a proptest/fuzz corpus asserts no panic, no hang and a measured peak-memory bound (T8, PD-162).
- **Anchor-dir lines are append-only and fsynced** (§8.5); the writer never rewrites, truncates or deletes a byte of an anchor file; it writes nothing before startup verification has completed (§8.7 "No anchor writes before verification").
- **Native dialogs only from Rust:** every path (export dir, backup dir, restore source, anchor dir) is chosen in a Rust-opened dialog; every security-weakening action (restore, anchor-dir change/removal, archive, "Prepare for removal", re-anchor, forget install) and the incident acknowledgement (PD-180) asks `NativeConfirmer` first and builds `Confirmed` only from its `Ok` (L54; T1 checker).
- **Secrets:** the backup's recovery passphrase (restore) and the new recovery passphrase (change) enter only through `submit_secret` in the credential window (§10.3); no command response, event, capture record, log line, export or backup file holds a PAT or a passphrase (S-16, T29).
- **Release vs non-release builds:** unsigned or ad-hoc output only on non-release runs; every `v*` tag run is a release run (`release.yml`; `bundle.yml` loses its tag trigger), and a release run without signing secrets fails (T26, PD-182). `ci/check-release-build.sh` stays green: no `--debug`, `--features`, `--profile` or feature-bearing `--config` in any `cargo tauri build` line of `bundle.yml`; a `--config` value or file may hold only the signing keys and `build.beforeBundleCommand`, and the guard reads a generated config file, not only the command line (signing goes through the Tauri config's signing keys, environment variables or a pre-bundle signing step, never through features).
- **CI secrets** live only in a protected GitHub environment that only the signing build jobs and the release-verify/upload jobs declare themselves (a job that `uses:` a reusable workflow cannot declare one, PD-182); `install-probes.yml`, `e2e-bundle.yml` and every `workflow_run`/`pull_request` workflow stay secret-free (its header rule), also when `release.yml` calls `install-probes.yml`.
- **Commits:** one commit per task (more where stated), message `<type>(<scope>): <summary>`, trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` (Opus tasks `Claude Opus 5.5`, Haiku tasks `Claude Haiku 5.5`); explicit pathspecs, never `git add -A`.

- **PD-162 Verifier design (spec silent; redesigned after plan review B-1).** `verify_export` is a **streaming, decrypt-free verifier with its own walk**; it does not reuse `verify::run_full`, `VerifyCtx` or `anchor_dir::check`, which decrypt with the KEK, judge keychain anchors and assume the DB holds everything from the first retained record to the head (a partial range export would read as `FirstRetainedMismatch` and as "anchored record is missing"/"beyond the store's head", exit 21). It never opens the keychain, a vault, the live DB or a webview (§12.1).
  1. **Manifest** (≤ 1 MiB, JSON depth ≤ 64): parsed first; with `--manifest-sha256` its SHA-256 must match (else 21). Its `first_seq`, `last_seq`, `rows`, `boundary_prev_hash`, `head`, `chain_ids`, `restore_records`, `key_recovered_records`, `events_sha256`, `prune_log_sha256` are the claims the walk checks.
  2. **`prune_log.jsonl`** (≤ 64 MiB, ≤ 1 000 000 rows): rows rebuilt as `PruneLogRow`; `prune_row_hash` and the `check_prune_log` rule (`verify.rs:776`, made `pub(crate)`, no logic change); its file hash compared with `prune_log_sha256`.
  3. **`events.jsonl`**, one pass, one line at a time (≤ `MAX_EXPORT_LINE_BYTES`, PD-159), file hash fed as it is read. Per row: rebuild `RowFields` (strict column set, `deny_unknown_fields` except `payload`/`unanchored`) and recompute `RowFields::record_hash` (`encoding.rs:214`); `seq` = previous + 1; `prev_hash` = previous `record_hash` (the first row's = `boundary_prev_hash`); decode `payload_b64` (≤ `MAX_PAYLOAD_LEN`) and check `payload_len` and `payload_sha256`; parse the plaintext only for the event types whose checks read it (`WRITE_APPROVED` → `request_set_hash` over its `requests` (`request_set.rs:40`); `RESTORE` → the §8.11 segment-boundary rule (`source_head_seq`/`source_head_hash` equal the previous row, chain id switch to `new_chain_id`, `records_lost`); `PRUNE` → its settings snapshot parsed with the store's own settings parser, which accepts the M8 Δ7 optional `allow_degraded_scripts` key; `KEY_RECOVERED`, `GENESIS` → the manifest's lists); every parse depth ≤ 64. State carried between rows: O(1) (previous seq/hash/chain, counters, the open `RESTORE` segment) plus the in-range anchor map of step 4. At EOF: row count = `rows`, last row = `head`, file hash = `events_sha256`. Peak working set: one line buffer plus its decoded `payload_ct` and plaintext (and the parse of a plaintext the row's check needs), documented in the module as ≤ 2 × `MAX_EXPORT_LINE_BYTES` + the anchor map, and measured by the counting-allocator tests of Task 8; no time cap (work is linear in the bytes read).
  4. **Anchor dir** (`--anchor-dir`), read with `anchor_dir::parse_line` and the existing bounds (`MAX_LINE_BYTES` 4096, `MAX_FILE_BYTES` 64 MiB, `MAX_LINES` 1 000 000 per file; `anchor_dir::load`'s torn-line rule, PD-165), before the events pass, for the files `<chain_id>.jsonl` of the manifest's `chain_ids`, plus every other `*.jsonl` whose header line names the manifest's `install` triple (fork candidates, PD-163 (b)); of the remaining files only the header line is read (≤ 256 `*.jsonl` files in all; more → 22 with "anchor dir has too many files"). Kept: a `BTreeMap<seq, (record_hash, kind)>` of lines naming seqs in `[first_seq − 1, last_seq]` per chain, and the `Prune` lines. **Range-aware comparison:** a line naming a seq in `[first_seq, last_seq]` must match that row (`record_hash`, `epoch`, `clock_behind`, immediate `event_type`) → else 21; lines naming seqs outside the range are skipped (never "missing" or "beyond head"); a line at `first_seq − 1` must equal `boundary_prev_hash`; `Prune` lines are matched against `prune_log.jsonl` rows; anchored lines of a `RESTORE` source chain beyond its `source_head_seq` must be covered by `records_lost` (the `LostSpan` rule, `anchor_dir.rs:626-645`, reused as a pure function).
  5. **Trust-root verdicts:**
     - `--manifest-sha256` matches and the walk is consistent → the whole range is bound (exit 0).
     - `--anchor-dir` only: rows up to the last in-range anchored seq `L` are bound through the chain (any change to a row at or before `L` changes `L`'s `record_hash`; `boundary_prev_hash` is bound once any in-range line exists). Exit 0 only if `L` = `last_seq`; otherwise exit 20 with the report line `anchor dir: ok up to seq <L>; rows <L+1>..<last_seq> unanchored, not covered by a trust root; give --manifest-sha256` (a truncated unanchored tail cannot be detected without the manifest hash). No in-range line at all → 20. **[lead to confirm]** (review B-1 primary option; the alternative is exit 0 with that report line).
     - Neither → internal consistency only: inconsistent → 21, consistent → 20 with "internally consistent; trust root NOT verified" (§8.10).
     - Both given → both must pass (either failing → 21).
  6. Usage, I/O and bound violations (missing file, unreadable file, line over its cap, JSON depth) → 22 when the input cannot be read as an export at all, 21 when a well-formed export contradicts itself or a trust root (a claimed length that does not match the bytes, a row count beyond `rows`).

## Review Focus

Five failure modes most likely to bite users of M10's code; each has named tests the reviewer must see pass.

1. **(Tasks 7, 8, 11, 28) A forged or broken export never verifies, an honest partial export always does, and a hostile export never crashes the verifier.** Any change a trust root covers gives exit 21 (with `--manifest-sha256`: every byte of the export; with `--anchor-dir`: every row up to the last in-range anchored line, `prune_log` rows matched by `Prune` lines); no trust root (or an unanchored tail without the manifest hash) gives exit 20, never 0; an honest export of any contiguous range, incl. a 96 MiB payload, gives exit 0 with its trust root; the verifier never decrypts, never opens the keychain, the live DB or a webview; garbage input ends with exit 21/22, no panic, measured peak memory. Tests `s03_verify_pass_tamper_no_trust_root` (lib), `verify_export_tamper_matrix` (per trust root), `partial_range_export_verifies`, `anchor_lines_outside_range_ignored`, `max_size_payload_round_trips`, `verify_export_fork_reported_as_fork`, `verify_export_garbage_never_panics` (proptest), `verify_export_never_opens_keychain_or_live_db`, CI `s03_cli_verify_export_with_tray_app_running`.

3. **(Tasks 12, 13, 14, 15, 22) Recovery-tier actions keep the boundary.** Restore, passphrase change, anchor-dir change, re-anchor, forget install and incident acknowledgement each need their native confirmation (where §10.3, PD-170 or PD-180 says so) before any effect; paths come only from Rust dialogs; secrets only through `submit_secret`; the rollback confirmation is re-asked when the head moved; closing or quitting mid-flow leaves no half-done effect (PD-181).
