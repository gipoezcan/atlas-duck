## Global Constraints

The master plan's Global Constraints apply verbatim. The subset M9 touches most:

- **Opacity (§4.5, §10.2):** the MCP server adds nothing to an envelope; `structuredContent` is the envelope exactly as the app (or the CLI-side rules shared with the CLI) produced it. Progress notifications carry only `{request_id, status}` (status changes) or nothing (heartbeats on a fixed timer started at tool-call receipt, never driven by app events). Nothing internal (queued, slots, sizes, timing) is derivable from MCP messages beyond what the CLI already shows.
- **stdout is JSON-RPC only (§4.6, §4.7, §13 S-02):** in `mcp` mode nothing but `rmcp`'s transport writes to stdout; `crates/cli/src/mcp/` carries `#![deny(clippy::print_stdout, clippy::print_stderr)]`; the launched app's stdio is the null device (existing §4.7 rule, T10 audits the intermediate processes).
- **Never cancel by accident (§4.4, §4.6):** a dropped tool call, a client `notifications/cancelled`, stdin EOF, a signal or a lost connection never sends `request.cancel`; only the `request_cancel` tool does.
- **Never exit because of the app (§4.6):** `atlas-duck mcp` ends only on stdin EOF, a transport error on stdin/stdout, or a signal; an app restart, upgrade, mismatch or crash makes the next tool call reconnect.
- **Deadline (§4.6, L04):** `ATLAS_DUCK_MCP_TIMEOUT` (default 50 s) is wall-clock from receipt of the tool call; discover, launch poll, the pipe-busy wait, connect, `hello` and the wait for a `SharedClient` slot are each capped by the remaining time; a deadline that expires before the submit frame was taken by the writer is `unreachable {launch_timeout}` with nothing queued; one that expires after it is `pending` with `request_id: null` (PD-16, L63), never `launch_timeout`. Every IPC call is bounded through `SharedClient`'s own `at` argument (Δ1), never by dropping its future.
- **Same rules as the CLI:** `params_sha256`, `build_id` exact match (L16), L63 `connection_lost` with an unknown id, L131 (a `pending` submit reply without `request_id` is `protocol_error`; an await reply naming another request is `protocol_error`), L66 (the `request_list` agent filter comes only from the tool's own `agent` argument), status exit-0 rule for known ids (§4.4). M9 reuses the CLI code for each (T4), never a copy.
- **Lints:** `clippy -D warnings`; `unwrap_used`/`expect_used` denied in `crates/cli/src/mcp/` (module-level `#![deny]`, tests excepted).
- **Tests:** each Rust test file starts with `type TestResult = Result<(), Box<dyn std::error::Error>>;`; async tests `#[tokio::test(flavor = "multi_thread", worker_threads = 4)]`; OS-only tests are `#[cfg]` modules; `#[ignore]` reasons name the CI step. **Paused clock only without real IO:** `#[tokio::test(start_paused = true)]` is used only for the `progress.rs` timer tests over a fake waiting future and a fake peer (Task 9). No paused-clock test wraps the rig, a pipe, a socket or a `duplex` transport (tokio auto-advances while real IO is in flight, which fires `HELLO_TIMEOUT`/`FRAME_BODY_TIMEOUT` and the hello deadline spuriously, and `Deadline` is `std::time::Instant`, which a paused clock does not move). Rig tests run on the real clock with short real periods (the test-only heartbeat period of PD-125).
- **Commits:** one commit per task unless stated, `<type>(<scope>): <summary>`, trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` (Opus tasks `Claude Opus 5.5`, Haiku `Claude Haiku 5.5`); explicit pathspecs; `--locked` on every cargo command after Task 1's one unlocked build.

## Plan decisions and contract deltas

**Contract deltas (applied before Task 1):**
- **Δ1 C.2 `ipc::client::SharedClient`** (PD-115). Additive; `IpcClient` and its `&mut self` API stay for the CLI.
  ```rust
  impl IpcClient { pub fn into_shared(self) -> SharedClient; }          // after connect + hello
  #[derive(Clone)] pub struct SharedClient { /* Arc<inner>: writer task (mpsc of queued frames, each with a FrameState), routes HashMap<u64, Route /* oneshot or tombstone + the slot permit */>, progress HashMap<String /* request_id */, Vec<mpsc::Sender>>, closed: Option<Closed>, in-flight semaphore */ }
  pub struct Sent<R> { pub result: Result<R, ClientError>, pub written: bool }   // `written`: the writer took this call's frame (Queued -> Writing), so the server may have it (PD-16 per call)
  impl SharedClient {
      /// `at`: the caller's bound (`None` = unbounded). On expiry the call returns
      /// `Sent { result: Err(ClientError::DeadlineExceeded), written }` itself.
      pub async fn call<R: DeserializeOwned>(&self, method: &str, params: impl Serialize, at: Option<Instant>) -> Sent<R>;
      pub async fn call_with_progress<R: DeserializeOwned>(&self, method: &str, params: impl Serialize, at: Option<Instant>,
          on_progress: &mut (dyn FnMut(ProgressNotification) + Send)) -> Sent<R>;   // only notifications whose request_id = params.request_id
      pub fn is_closed(&self) -> bool;                                     // the reader saw EOF, an error or a protocol violation
  }
  pub const SHARED_IN_FLIGHT: usize = 48;   // < server MAX_IN_FLIGHT_PER_CONNECTION (64); counts what the server holds (see "Slots")
  ```
  `at` is a `std::time::Instant` (the `ipc` crate does not know the CLI's `Deadline`; callers pass `Deadline::at()`). Rules:
  - **Deadline, not drop (PD-16 per call).** Callers bound a call through `at` and never drop a call future to time it out. Each queued frame carries a `FrameState` (an atomic: `Queued → Writing | Abandoned`). The writer task does the compare-and-swap `Queued → Writing` before the frame's first byte and skips a frame it finds `Abandoned`. When `at` passes, the call tries `Queued → Abandoned`: success means the frame is never written (`written: false`, the server never sees it); failure means the writer already took it (`written: true`; the request may exist). A call whose `at` passes while it waits for a slot queued nothing (`written: false`). So "nothing queued" (exit 5, `launch_timeout`) is answered only when it is true.
  - **Dropped futures.** A future is dropped only when the MCP client cancels a tool call (PD-126: an await whose `written` nobody reads, or a submit if rmcp aborts handlers, Task 1). Its drop guard does the same compare-and-swap: a still-queued frame is abandoned (never written); a taken frame is written whole by the writer task, so the stream is never torn.
  - **Slots (plan review I-1).** A call acquires one of `SHARED_IN_FLIGHT` permits before its frame is queued (the wait is bounded by `at`). The permit travels with the route, not with the call future: it is released when the server's answer for that id arrives (a late answer for a call that already returned or was dropped included), when the frame is abandoned, or when the client closes. A call that returned or was dropped after its frame was taken leaves a tombstone route that discards the late answer and then releases the permit. So 48 counts what the server still holds (the server holds its own permit per request until the request's task ends, `server.rs:1066`).
  - A `null`-id error answer is delivered to no call and closes the client (`Closed::Protocol`), since with several calls in flight it cannot be attributed (the sequential client's rule, "goes to the waiting call", has no equivalent).
- **Δ2 C.1 `GENERIC_COMMANDS`** gains `{path: ["mcp"], usage: "atlas-duck mcp [--tools full|generic] [--instance ALIAS] [--agent NAME]", summary: "Serve the operations as MCP tools on stdio"}` (registry data, additive). ## Ledger entries the lead adds (L155–L164, the M9 allocation)

- **L155** (PD-115, §3.3, §4.6; R1) One long-lived IPC connection per `atlas-duck mcp` process, shared by all concurrent tool calls through `ipc::client::SharedClient` (≤ 48 calls in flight); a new connection only after it closed (never on a per-call error). Keeps one approval session and one agent key per MCP server; accepted cost: every reconnect starts a new approval session for the same MCP server. Calls are bounded by their deadline inside `SharedClient` (a frame still queued at the deadline is never written; `written` tells the caller whether the request may exist, PD-16), and the 48 slots count what the server still holds (a slot is released by the server's answer, an abandoned frame or the close). Residual: cancelled waiting tool calls keep their server-side awaits, and slots, until each await's `timeout_ms`; with a large `ATLAS_DUCK_MCP_TIMEOUT`, 48 such cancels make later calls end `launch_timeout` (nothing queued) until the app answers them; no cap on `timeout_ms` in M9.
- **L156** (PD-117, §4.2, §4.6, §13 S-02; R5) `atlas-duck mcp` prints nothing on stdout before serving: a usage error goes to stderr as one envelope line, exit 2; `--help` prints on stdout as every `--help`. After serving starts stdout carries only JSON-RPC; exit 0 on stdin EOF. `ATLAS_DUCK_MCP_TIMEOUT=0` returns `pending` at once.
- **L157** (PD-121, PD-123, §4.6; R3) `isError` = the CLI exit code of the equivalent command is neither 0 nor 4 (so also `cancelled`, `abandoned`, `outcome_unknown`, `result_evicted`, script error exit 8), or the envelope is `pending` + `connection_lost`; `content` = the fixed §4.6 sentence when one applies, then the envelope as one JSON line; `structuredContent` = the envelope unchanged. The restart text accompanies `protocol_mismatch`, **every** `unreachable` reason (incl. `launch_timeout`, `no_gui_session`) and `pending` + `connection_lost`; not `server_identity` (exit 5, not an `unreachable` reason) and not `store_unavailable` (the reason Task 12a adds by the §4.3 amendment; restarting the MCP server cannot help a failed store; still `isError`).
- **L158** (PD-122, §4.6; R2) MCP agent name precedence: `--agent` > `ATLAS_DUCK_AGENT` > `clientInfo.name` > none; `--agent ""` is no agent at all (no env, no `clientInfo.name` fallback); an empty `ATLAS_DUCK_AGENT` or `clientInfo.name` counts as absent; read once at the first connect.
- **L159** (PD-125, §4.5, §4.6; R11) Progress only with a `progressToken`: a per-call counter (first notification `progress: 1`), "submitted request_id=<id> status=pending", "request_id=<id> status=<status>" (each change once per tool call), heartbeats without a message every 5 s on a timer that starts at tool-call receipt and first fires one period later; no notification after the tool call's response.
- **L160** (PD-126, §4.6) A cancelled tool call drops its wait, sends no `request.cancel` and no result; an interrupted submit completes and its answer is discarded (spawned when rmcp aborts handler futures).
- **L161** (PD-127, §4.1, §4.6; R7) No stderr submission notice in MCP mode.
- **L162** (PD-130, L81) The launch-stub wait is capped by the caller's deadline; a wait cut short by the deadline is `launch_timeout`, a stub that exceeds its own 5 s stays `not_running`; L81 closed in M9.
- **L163** (PD-129; R9) Test-only seams: approver directives `release-redacted <path>`, `expire`; `ATLAS_DUCK_TEST_SERVER_BUILD_ID` under `scripted-approver`/`core/testing` only.
- **L164** (PD-124, §4.4, §4.6; R6) **CLI discrepancy, open for a later milestone:** §4.4 says a script's `instance_id` is null, and MCP `script_run` follows it (no default instance applied), but the CLI sends its global `--instance` with `script run` (`crates/cli/src/connected.rs`). M9 leaves the CLI unchanged. Aligning the CLI would change the `params_sha256` of scripts submitted with `--instance` (a `request_list {match_params}` computed one way would not match a submit made the other way); the lead decides the owner milestone and whether the spec or the CLI moves.
