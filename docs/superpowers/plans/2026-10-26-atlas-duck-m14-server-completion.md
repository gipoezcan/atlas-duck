> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. One implementer subagent per task, one reviewer after each task. Each task names every file it touches, the interfaces it consumes and produces, the spec clauses it implements, its tests with the assertions that matter, and which tests run locally and which only in CI.
>
> **Model policy (memory `subagent-model-preference`; never Fable):** **Sonnet 5.5 (effort medium)** for normal tasks; **Opus 5.5 (effort medium)** for security-critical tasks, each marked `Model: Opus` (OAuth authorization server, token endpoint, anchor chain v2, auditor access, export job, `verify_export` extension, server script runner, container sandbox proof, isolation/redaction extension, final review). Reviewers have the task's tier. Haiku 5.5 only for the docs edits of Task 24.
>
> **Hard execution limits (memory `agent-execution-limits`):** no agent downloads or runs executables, toolchains or installers, runs `cargo install`, `npm install`/`npm ci`, `docker`/`podman`, `kubectl`, `helm`, `helmfile`, or starts `atlas-duck-server`, `atlas-duck-app`, `atlas-duck` or `atlas-duck-sandbox` (not even as a smoke test). Building the image, running the container, running the e2e suite against a container or a review environment, and every test that spawns a sandbox worker run only in GitHub CI (Linux) or GitLab CI (review environment). Locally: `cargo check|clippy|test -p <crate> --locked -j 4` for in-process tests (server tests bind `127.0.0.1:0` inside the test process; sandbox-spawning tests are `#[cfg(target_os = "linux")]` and compile on the Windows laptop with `--no-run` only), `cargo tree`, `cargo metadata`, `node ci/*.mjs`, `node --test`, `npx vitest run` / `npx tsc --noEmit` / `npx eslint` from the existing `node_modules` (worktrees: junction per memory `ui-gates-in-worktree`). Shell scripts are checked by reading and by the CI `bash -n`/`sh -n` steps.
>
> **Cargo on the laptop (memory `disk-usage-target-dir`):** at most one cargo process at a time, `-j 4`, `--locked` (Task 2 changes `Cargo.lock` once with a plain `cargo check` and is reviewed as a lock diff; it must add **no** `[[package]]` entry), `CARGO_TARGET_DIR` = the one shared scratchpad target dir the lead names; deleted at milestone end.
>
> **Shell (memory `powershell-utf8-rewrite`, `powershell-net-paths-and-commit-quoting`):** agents use PowerShell; edit files with the Edit tool, never `Get-Content | Set-Content`; commit with `git commit -F <file>`.
>
> **Outward-facing gate (M13):** pushing a branch that matches M13's review-deploy rules deploys to the shared cluster. The lead gets the user's go-ahead before the first M14 push that triggers `deploy:review`. No agent triggers a GitLab job.

**Goal:** Complete server mode (SM-10 M14): an OAuth 2.1 authorization server for remote MCP per the MCP authorization specification (protected-resource metadata, authorization-server metadata, dynamic client registration, authorization code + PKCE S256, resource indicators, short-lived access tokens with rotating refresh tokens and reuse detection, consent through the domain-login session, revocation from the web UI, audit records); scripts in server mode on the M8 sandbox inside the hardened server container with per-user and server-wide concurrency limits, proven in CI; an own-chain audit view for every user and a role-gated auditor UI with exports, each auditor read recorded as `AUDITOR_READ`; `verify-export` that verifies a server export together with an anchor-chain excerpt; an end-to-end server test suite that runs in GitHub CI against the built container and in GitLab CI against the M13 review environment.

**Exit criterion (master plan "### M14"):** an MCP client completes the OAuth flow and runs a script; an auditor exports another user's chain and `verify-export` passes on it; the server e2e suite is green in CI. Proven by: `crates/server/tests/exit_flow_m14.rs` (in-process, GitHub `server` job; the script leg runs the real worker on Linux), `crates/server-e2e` against the built container (GitHub `server-e2e` job, all three clauses), the same suite against the review environment (GitLab `verify:review-e2e`), and `atlas-duck verify-export` (desktop CLI) plus `atlas-duck-server verify-export` exiting 0 on the downloaded auditor export in both e2e runs.

**Architecture:** One new library crate, one new test-only crate, no new process model.

- `crates/script-glue` (`atlas-duck-script-glue`): the Tauri-free `ScriptRunner` implementation and the startup probe holder, moved out of `app/src-tauri/src/script_glue/` and `app/src-tauri/src/sandbox_probe.rs` unchanged in behaviour (PD-247). The app's diagnostic allowlist (`crate::diag::fields`) stays in the app and is passed in as a small trait object. `app` and `server` both depend on it.
- `crates/server` (from M12/M13) gains: `oauth/` (metadata, registration, authorize/consent, token, revocation, grants), `scripts.rs` (the server `ScriptRunner` wrapper with the server-wide cap), `auditor/` (cross-user read views, `AUDITOR_READ`), `export_job.rs` (server-side export, anchor excerpt, tar download), schema v3 of the server store (on M13's migration path), the anchor-now hook and excerpt builder (v2 rows themselves are M12's).
- `crates/audit` gains, additively: in `server_anchor` (created by M12 with the v2 row hash and leaf hashing) the excerpt format and its bounded parser (pure functions used by the server writer and by the verifier), `verify_export` support for an anchor-chain excerpt, `RustChosenPath::from_server_export_dir`, and an export range bounded by a sequence number. `EventType` gains `OAUTH_GRANT_CREATED` and `OAUTH_GRANT_REVOKED` at the end.
- `crates/cli`: `verify-export` gains `--anchor-chain <file>` and `--anchor-chain-head <seq>:<hex>`.
- `crates/server-e2e` (`atlas-duck-server-e2e`, `publish = false`, test-only, `harness = false`): a black-box client suite run against a base URL given by environment; never part of `cargo test --workspace`.
- `app/ui/src/server/`: OAuth consent page, connected-apps page, own-chain audit page (reusing `app/ui/src/audit/*` through the M12 transport seam), auditor pages.

**Tech stack:** existing pins (Rust 1.95.0, `tokio =1.53.3`, `axum =0.8.9` from M12, `rmcp =3.5.0`, `rusqlite =0.40.2`, `sha2`, `hmac`, `getrandom`, `subtle =2.6.1` (M12), `base64`, `url =2.5.8`, `serde_jcs =0.2.0`, `flate2 =1.1.10` (not used, see PD-256), `landlock =0.4.7`, `seccompiler =0.5.0`, `reqwest =0.13.5` (dev/e2e only), React 19.3.0, Vite 8.3.3, Vitest 5.0.3). **No new crate enters `Cargo.lock`** (PD-232): the token endpoint parses forms through axum's `form` feature, whose only dependency `serde_urlencoded` is already in the lock through the `query` feature M12 enables (`axum-0.8.9/Cargo.toml`: `form = ["dep:serde_urlencoded"]`, `query = ["dep:serde_urlencoded"]`); tokens are opaque random strings hashed with SHA-256 (no JWT crate); the export download is a hand-written ustar stream (no `tar`/`zip` crate). No new npm package.

**Spec:** `docs/superpowers/specs/2026-10-26-atlas-duck-server-mode.md` SM-3.1, SM-3.3, SM-3.4, SM-5.3 (approval_url for scripts), SM-6.3 (`AUDITOR_READ`, anchor chain, `verify-export` with anchor-chain excerpt), SM-6.4, SM-6.5 (auditor access to deactivated users' chains), SM-7.1, SM-8.2/8.3 (readiness and logs for the new parts), SM-9.1/9.2, SM-10 M14. Glossary `CONTEXT.md` (terms verbatim: Server mode, User, Agent, Approval, Domain login, Role, Auditor, Admin, Session, API key, Audit chain, Server anchor chain, Master key). ## Global Constraints

M12's Global Constraints (desktop untouched, secrets, master key only from a file, TLS never disabled, agents never approve, per-user scoping is structural, error shape, hermetic tests with `tokio::time::timeout`, lints, `panic = "abort"`, commits) apply verbatim. In addition:

- **OAuth secrets:** authorization codes, access tokens, refresh tokens, PKCE verifiers and challenges are `SecretString`/`Zeroizing` from parsing; the server stores only `SHA-256(token)` (tokens carry 256 random bits, so a fast hash suffices, PD-235); none appears in logs, audit payloads, metrics, SSE, error bodies or redirect URLs other than the one `code` redirect. The redaction sweep (T21) gains canaries for each.
- **Agents never approve (SM-3.4):** an OAuth access token is a bearer credential like an API key: M12's `auth/bearer_not_accepted` on `/api/cmd/*` and `/api/me/*` applies unchanged, and consent (`POST /api/oauth/consent`) needs session + CSRF + Origin, so an agent holding a token can neither approve a write nor grant itself another client's consent.
- **One audience:** every access token is bound to the resource `<ATLAS_DUCK_PUBLIC_URL>/mcp` and accepted only at `/mcp` (RFC 8707). No token is passed through to Jira/Confluence (PATs stay the only upstream credential, ADR 0001).
- **Scripts fail closed:** server mode never runs a degraded script (no `allow_degraded` in server mode, PD-248); a server whose probe floor is `NotMet` refuses every script with the base-spec `sandbox_unavailable` envelope and reports it in `/readyz` and `/metrics`; nothing else is affected.
- **Auditor reads are recorded before data leaves:** each auditor request appends `AUDITOR_READ` to the auditor's chain and an operational row to the anchor chain, both committed **before** the response body is produced; an append failure answers 503 `audit/read_not_recorded` with no target data (PD-258).
- **Decrypted exports on the volume** live only under `<data>/exports/<job_id>/` (created `0700`, files `0600`), are removed after download completion or the TTL (default 24 h) and at startup for expired jobs; the job id is random (128 bits) and bound to the requesting user/auditor.
- **E2E tests never hang:** every test body in `crates/server-e2e` and every new in-process test is wrapped in `tokio::time::timeout` (default 60 s e2e, 30 s in-process); HTTP clients have per-request timeouts (10 s; 120 s for the script `request_await`); CI jobs have `timeout-minutes`; shell scripts use `timeout`, `curl --max-time`, `set -euo pipefail`.

## Plan decisions

- **PD-231 Numbering.** See header; Δ-M14-n are local.
- **PD-232 No new crate in the lock.** The OAuth AS is built on axum (M12 pin) with feature `form` added to the workspace line (its dependency `serde_urlencoded` is already in the lock via `query`), `sha2`, `getrandom`, `subtle`, `base64`, `url`, `serde_json`, `rusqlite`. Rejected: `oauth2` (a client library), `oxide-auth` (unmaintained relative to our pins, drags `rouille`/`actix` adapters), `jsonwebtoken` (JWT access tokens are unnecessary when AS and RS are one process and add key management). Task 2 proves `Cargo.lock` gains no `[[package]]` entry; `cargo deny` (CI supply-chain job, 0.20.2) runs unchanged.
- **PD-233 Which MCP authorization spec.** The 2025-06-18 revision (RFC 9728 discovery via `WWW-Authenticate resource_metadata`, RFC 8414 AS metadata, RFC 7591 DCR, RFC 8707 `resource` mandatory, PKCE S256) is implemented in full. From the 2025-11-25 revision M14 takes what is compatible with it: the protected-resource metadata is also served at the path-suffixed well-known URI, `scopes_supported` in both documents, `scope` in the 401/403 challenge. **Client ID Metadata Documents** (2025-11-25, server fetches a client's HTTPS metadata URL) are **not** implemented in M14: the server would make outbound requests to agent-chosen URLs from inside the cluster (SSRF surface, NetworkPolicy egress M13 allows 443). Advertised as unsupported (field absent); ledger L241 (handoff).
- **PD-234 Public clients only, PKCE S256 only.** DCR accepts only `token_endpoint_auth_method: "none"`, `grant_types ⊆ {"authorization_code","refresh_token"}` (must include `authorization_code`), `response_types = ["code"]`; any other value → `invalid_client_metadata`. No client secrets are issued (nothing to store or leak). `/oauth/authorize` requires `code_challenge` (43 chars base64url, i.e. S256 output) and `code_challenge_method=S256`; `plain` or absent → error redirect `invalid_request`. `/oauth/token` requires `code_verifier` 43..=128 chars of `[A-Za-z0-9-._~]`; compared in constant time against the stored challenge.
- **PD-235 Opaque tokens.** Formats: code `ado_ac_<43 base64url>`, access `ado_at_<43>`, refresh `ado_rt_<43>` (32 random bytes each from `getrandom`). Stored as `SHA-256("atlas-duck/oauth/v1\0" ‖ kind ‖ token)`; lookup by hash (indexed, constant-time compare of the hash on the found row). No argon2: unlike API keys (user-visible, long-lived, M12 PD-213) these are high-entropy and short-lived; a stolen DB copy yields hashes of 256-bit secrets. Access TTL default 900 s (`ATLAS_DUCK_OAUTH_ACCESS_TTL_SECS`); code TTL 60 s, single use.
- **PD-236 Grants and refresh rotation.** A **grant** = (user, client, scopes, resource, created_at, absolute expiry = created + `OAUTH_GRANT_MAX_DAYS`, revoked_at, revoke_reason). Every refresh-token use issues a new access token and a new refresh token in the same **family** (`grant_id`), marks the used one `rotated_at`, and keeps at most one live refresh token per grant. **Reuse detection:** presenting a refresh token whose `rotated_at` is set (or a code already redeemed) revokes the whole grant and every access token of it at once (`revoke_reason = "refresh_reuse"` / `"code_reuse"`), appends `OAUTH_GRANT_REVOKED {by: "reuse_detected"}` to the user's chain and `OAUTH_REUSE {client_id, grant_id}` to the anchor operational log, and answers `invalid_grant`. A 5-second grace window for the *same* refresh token from the same client (network retry) is **not** granted: rotation is strict (OAuth 2.1 §4.3.1 permits either; strict is simpler to reason about; L242). Refresh idle expiry `OAUTH_REFRESH_IDLE_DAYS`. Re-consent for an already granted (client, user) creates a new grant and revokes the old one (`by: "replaced"`).
- **PD-237 Resource indicators (RFC 8707).** `resource` is required at `/oauth/authorize` and at `/oauth/token` (both grants) and must equal the canonical resource URI `<ATLAS_DUCK_PUBLIC_URL>/mcp` byte for byte after `url` normalisation (lowercase scheme/host, no default port, no trailing slash, no fragment); else `invalid_target`. The access-token row stores the resource; `/mcp` refuses a token whose resource differs (`invalid_token`). There is exactly one resource.
- **PD-238 Redirect URIs.** Registered: 1..=5 URIs, each ≤ 512 bytes, absolute, no fragment, no userinfo; scheme `https` (any host), or `http` with host `127.0.0.1`, `[::1]` or `localhost` (RFC 8252 §7.3; at authorize time a loopback URI matches a registered one ignoring the port only, everything else exact string match). Custom URI schemes are refused (L243: native MCP clients use loopback). The authorize request's `redirect_uri` is required (even with one registered URI). Consent "allow"/"deny" answers JSON `{redirect}` that the page assigns to `window.location`; the server never issues a cross-origin form post (CSP `form-action 'self'` unchanged). Authorization responses carry `iss` = issuer (RFC 9207, advertised by `authorization_response_iss_parameter_supported: true`).
- **PD-239 Error formats.** Protocol endpoints use RFC error JSON (above), never M12's shape, so standard MCP clients understand them; web APIs keep M12's shape.
- **PD-240 Dynamic client registration limits.** Per client IP (M12 `X-Forwarded-For` rule, PD-201) at most `OAUTH_REGISTER_PER_IP_HOUR` registrations per hour (in-memory sliding window, as M12's limiter); total cap `OAUTH_MAX_CLIENTS`; a client with no grant 24 h after registration and a client whose last grant ended 30 days ago are purged by a daily M13 scheduler job (`oauth_purge`). `client_name` 1..=64 printable chars (control chars, bidi overrides refused); `client_uri`, `logo_uri`, `tos_uri`, `policy_uri`, `contacts`, `jwks*`, `software_statement` are refused or ignored (ignored: `client_uri`, `software_id`, `software_version`; everything else `invalid_client_metadata`). Response: `client_id` (`adc_<22 base64url>`), `client_id_issued_at`, the accepted metadata; no `registration_access_token` (no RFC 7592 management). Registration writes `OAUTH_CLIENT_REGISTERED {client_id, client_name, redirect_hosts, source_ip}` to the anchor operational log (no user exists yet).
- **PD-241 Consent.** `/oauth/authorize` without a session redirects to `/login?next=/oauth/authorize?...` (M12's `next` sanitising already accepts same-origin relative paths). With a session it validates client, redirect URI, PKCE, `resource`, `scope` (space-separated subset of `read propose_write scripts`; absent → `read`), stores a **consent request** (id 128 bits, 10 min TTL, bound to the session id hash) and redirects to `/oauth/consent?req=<id>`. The consent page shows: client name **marked "unverified, chosen by the app"**, the redirect host in bold, each requested scope with its plain-English effect (fixed texts) and a checkbox (the user may drop scopes, never add), "Allow" and "Deny". The consent POST (session + CSRF + Origin) checks the request belongs to that session. No "remember this decision": every authorization asks (L244).
- **PD-242 Scopes.** OAuth scopes are the API-key scopes verbatim (`read`, `propose_write`, `scripts`); `read` is implied by any grant (a grant without `read` gets it added and shown). `/mcp` treats a token's scopes exactly like an API key's (A-9): `tools/list` filtered, `scope_missing` envelope for tool calls; `WWW-Authenticate: Bearer error="insufficient_scope", scope="…"` only for transport-level refusals.
- **PD-243 Bearer dispatch.** M12's `BearerUser` dispatches on prefix: `adk_` → API-key path unchanged; `ado_at_` → OAuth path (hash lookup, not expired, grant not revoked, resource matches, user not deactivated); anything else → 401 `invalid_token`. Both produce the same `UserCtx` + scope set + a `credential` tag (`api_key:<id>` / `oauth:<grant_id>`) used in `ConnectionMeta.agent` and in the MCP session binding (M12: session id bound to the user; M14: also to the credential, so a session created with token A cannot be continued with API key B of the same user → 404). 401 header: `Bearer realm="atlas-duck", resource_metadata="<public>/.well-known/oauth-protected-resource/mcp"` (+ `error="invalid_token"` when a token was presented). A refused OAuth token is audited as `LOGIN {method: "oauth", outcome: "refused", reason: "expired"|"revoked"|"wrong_resource", grant_id}` in the owner's chain when the owner is known (unknown hash → no record, like an unknown API-key prefix).
- **PD-244 OAuth audit kinds (SM-6.3 lists four kinds; ledger L245).** Appended to `EventType` after M12's four: `OAUTH_GRANT_CREATED {grant_id, client_id, client_name, redirect_host, scopes, expires_at}` and `OAUTH_GRANT_REVOKED {grant_id, client_id, by: "user"|"revocation_endpoint"|"reuse_detected"|"replaced"|"deactivation"|"expired_purge"}`. Token issuance and refresh are **not** audited per event (volume; the grant record and `LOGIN refused` cover the trust decisions); first use of a grant at `/mcp` per MCP session appears through the existing `hello`/agent connection records (M12 PD-194). Consent denial is not audited (no state change).
- **PD-245 Revocation.** RFC 7009 `/oauth/revoke` (public client: `client_id` + `token` in the form; refresh or access token) revokes the **grant** (both token kinds), answers 200 for unknown tokens too (RFC 7009 §2.2), and is listed in the AS metadata. The web UI "Connected apps" page lists grants and revokes them (`by: "user"`). Revocation takes effect at once: the access-token check reads the grant's `revoked_at` on every request (no cache longer than the request), unlike API keys' 60 s cache (M12 PD-213, which also invalidates on revoke).
- **PD-246 Script concurrency (SM-7.1).** Per user: core's `SCRIPT_SLOTS = 2` and `DRY_SLOTS = 2` per `Core` (`crates/core/src/engine/queue.rs`) already give "2 concurrent runs per user", because M12 runs one `Core` per user; M14 adds no per-user knob (a value above 2 would need a core change; below 2 is not asked for). Server-wide: `ServerScriptRunner` wraps the shared `ScriptGlue` and takes a permit from a `tokio::sync::Semaphore` (`SCRIPT_RUNS_MAX` real, `SCRIPT_DRY_RUNS_MAX` dry/compile) before delegating `start_run`/`compile_run`; waiting is bounded by `SCRIPT_WAIT_SECS`, after which the run is refused through the existing busy path (`RunnerError` → `envelope::busy`; if `RunnerError` has no variant that maps to `busy`, T12 adds `RunnerError::Busy` to core additively, desktop never constructs it). Per-run CPU/memory: the base-spec per-run limits the M8 host already applies (`RLIMIT_AS` from the run's limits, wall-clock and CPU watchdog, `[scripts]` limits); server mode uses the base-spec defaults for every user (no per-user `[scripts]` overrides; the admin can lower them through new keys later, L246). Pod sizing: memory limit ≥ server baseline + `(SCRIPT_RUNS_MAX + SCRIPT_DRY_RUNS_MAX) × per-run address-space limit`; T15 computes the default chart values from the constants and documents the formula.
- **PD-247 Glue extraction.** `app/src-tauri/src/script_glue/{mod,map,policy,tests}.rs` and `app/src-tauri/src/sandbox_probe.rs` move to `crates/script-glue/src/{lib,map,policy,tests,probe}.rs` verbatim except: `crate::diag::fields::{SCRIPT_DIAG_UNLISTED, SCRIPT_GLUE_EVENTS}` and `allowlist_layer` stay in the app; the glue takes a `GlueDiag` trait object (`fn event(&self, name: &'static str, request_id: &str)`) whose app impl is the existing allowlisted logger and whose server impl is a `tracing` event with the same constant names. `canonical_worker` resolution becomes a constructor argument (`WorkerLocation::BesideExe` for the app = today's behaviour, `WorkerLocation::Fixed(PathBuf)` for the server from `ATLAS_DUCK_SANDBOX_BIN`). The app re-exports under the old module paths so its call sites change only `use` lines; tests move with their code under the same names (count before/after in the commit body).
- **PD-248 No degraded scripts in server mode.** M8's degraded policy (`allow_degraded`, run when the floor is `NotMet`, M8 plan lines 321–343) is a desktop user's informed choice on their own machine; on a shared server no single user can accept it for the pod. `ServerScriptRunner` always passes a strict `RunPolicy` (`ConfinementMode` strict), refuses any degraded path, and the config refuses `*ALLOW_DEGRADED*` keys. A `NotMet` probe → every script `sandbox_unavailable` (`UnavailableReason` as M8 maps it), `/readyz` field `scripts: "not_met"` (degraded field, not a 503, consistent with PD-M13-13), metric `atlas_duck_scripts_floor{state="not_met"} 1`.
- **PD-249 Probe and runtime pins.** The startup probe runs once per process (shared `ProbeHolder` from `script-glue`), not per user; identity re-checks before every spawn stay (PD-133 of M8: the image's read-only root filesystem makes a mismatch an image defect, logged as `sandbox_identity_mismatch` and refused). A running script pins its user's runtime against eviction (already in M12 PD-209, Δ-M14-3 applied; inert there until this milestone sets `CoreDeps.scripts`). Runtime close during shutdown kills running workers through the bridge's non-blocking kill before `APP_STOP`.
- **PD-250 Container sandbox proof.** Claim to prove: the M8 Linux layers need **no capability and no user namespace**: `PR_SET_NO_NEW_PRIVS` and `seccomp(SECCOMP_SET_MODE_FILTER)` with NNP are unprivileged; Landlock `landlock_create_ruleset`/`landlock_restrict_self` are unprivileged; `setrlimit` lowering is unprivileged; `PR_SET_PDEATHSIG`, `fork`, `execve`, `pidfd_open`, `close_range` are unprivileged. What can differ in a container is whether the runtime's default seccomp profile **allows** `seccomp`, `landlock_*`, `pidfd_open`, `close_range`, `clone3`. The plan does **not** assume the answer; CI measures it: (1) GitHub `server-image` job runs `atlas-duck-server sandbox-probe --json` inside the image under `docker run --read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges --user 65532:65532` with Docker's default seccomp profile, and the `confined_scripts` corpus (M8) compiled as a test binary run in a container from the same base image with the same flags; (2) GitLab `verify:review-sandbox` runs `admin sandbox probe` through `kubectl exec` in the review pod (Kubernetes `RuntimeDefault`, M13 securityContext) and a script through MCP in `verify:review-e2e`. Pass: floor `Met`, every worker task `Seccomp: 2` and `NoNewPrivs: 1` (the host's `/proc/<pid>/task/*/status` check), a script returns its result. `landlock_abi` `Some(n)` or `None` both pass and are recorded as evidence in the job log (Landlock is an extra layer, `probe.rs:744-751`). If `pidfd_open`/`close_range` are blocked, the M8 fallbacks apply and the evidence line records `pidfd=false`. If the floor is `NotMet` under `RuntimeDefault`, M14 is blocked and the lead decides between a `Localhost` seccomp profile shipped with the chart (allowing exactly the missing syscalls, reviewed) and leaving scripts disabled in production (L247).
- **PD-251 Own-chain view (SM-6.4, first sentence).** M12 ships no audit read; M14 adds the four read-only desktop commands `audit_query`, `audit_trail`, `audit_payload`, `audit_status` to `SERVER_COMMANDS` (they never call `NativeConfirmer`; T16 adds them to M12's checked list) with the same DTOs, so `app/ui/src/audit/{Audit,EventList,Filters,PayloadView,Trail}.tsx` render unchanged through the HTTP transport. Desktop-only parts of the Audit window (Verify now, incidents acknowledgement, backup/restore, anchor dir) are hidden in server mode by an optional `mode` prop (`'desktop'` default) on `Audit.tsx` (one prop, like M12 PD-219's `header` slot). Export is the server export job (T18), not the desktop dialog.
- **PD-252 Anchor chain v2 (spec SM-6.3 "verify-export accepts a server export together with the matching anchor-chain excerpt").** M12's v1 row hashes `body_jcs` in clear, so an excerpt that lets the verifier recompute hashes must contain every body in the span, including other users' heads and `LOGIN_FAILED` usernames (SM-6.4: users see only their own chain). v2: `hash = SHA-256("atlas-duck/anchor/v2\0" ‖ seq_be ‖ ts_utc ‖ kind ‖ SHA-256(body_jcs) ‖ prev_hash)`; `HEADS` v2 body = `{"leaves": [hex(leaf)…]}` sorted, `leaf = SHA-256("atlas-duck/anchor-leaf/v1\0" ‖ user_id ‖ "\0" ‖ chain_id ‖ "\0" ‖ seq_be ‖ record_hash)`, plus a non-chained side table `anchor_heads(anchor_seq, user_id, chain_id, head_seq, record_hash)` the server uses to build excerpts and that `anchor verify` recomputes against the leaves; `RUNTIME_CLOSED` and `USER_DEACTIVATED` v2 bodies carry `{"leaf": …}` the same way. Rows carry `hash_version` (1 or 2); verification accepts v1 rows before the first v2 row and only v2 after it (the switch row is `ANCHOR_V2 {}` written by the migration). The pure functions (`row_hash_v2`, `leaf_hash`, excerpt parse/verify) live in `crates/audit/src/server_anchor.rs` so `verify-export` (desktop CLI, no server dependency) and the server share one implementation. **Applied in M12 (Δ-M14-2, M12 PD-217):** M12 writes v2 rows from the start, so no v1 rows, `hash_version` column or `ANCHOR_V2` row ever exist and the dual-version verification above is not built; M14 keeps from this decision only the excerpt (PD-253) and its verification (PD-259).
- **PD-253 Excerpt format.** File `anchor-chain.jsonl` in the export: one JSON line per anchor row in the contiguous span `[s0, s1]`, where `s1` is the `HEADS` row the export job forces right before exporting (PD-254) and `s0` is the earliest `HEADS`/`RUNTIME_CLOSED`/`USER_DEACTIVATED` row whose leaf names this chain at or before the export's `first_seq` (or the chain's first anchoring), capped at 100 000 rows (beyond the cap: `s0` is moved forward and the verifier binds only what the span covers; reported). Each line is either **full** `{"v":2,"seq","ts_utc","kind","body_sha256","prev_hash","hash","leaf_entry"?}` where `leaf_entry = {user_id, chain_id, head_seq, record_hash, leaf_index}` is present only on rows whose leaf names the exported chain (the verifier recomputes the leaf, checks it is in `body` — so those rows also carry `body` = the leaves array, which reveals only other users' leaf hashes and their count, L248) or **opaque** (same fields without `body`/`leaf_entry`; its hash is still recomputable from `body_sha256`). A manifest `anchor-chain.manifest.json` `{format: "atlas-duck-anchor-excerpt/1", issuer: <public URL>, first_seq, last_seq, last_hash, chain_id}` is written beside it; both files are listed with SHA-256 in the export's top-level `README.txt` together with the exact `verify-export` command line.
- **PD-254 Export job.** `ExportJob::start(requester, target, range)`: (1) concurrency check; (2) `AnchorWriter::anchor_user_now(target)` appends a `HEADS` row naming the target's current head `h` (forces anchoring of everything exported); (3) `Store::export` with the additive range `TimeRange::through_seq(from, h)` (new audit API, Step in T18) into `RustChosenPath::from_server_export_dir(<data>/exports/<job_id>)` (additive constructor; the L54 checker allows it only in `crates/server/src/export_job.rs`, PD-255); the store-owned `EXPORT` record lands in the **target** chain as on desktop (an auditor export is therefore visible to the target in their own view); (4) excerpt from the anchor chain; (5) tar stream on download. Runs on `spawn_blocking`; progress via the existing `ExportControl`; cancel on shutdown (PD-181 of M10: wait for return). The job row (`export_jobs(job_id, requester_user_id, target_user_id, state, created_at, expires_at, manifest_sha256, size)`) is in the server store; only the requester can poll/download it.
- **PD-255 `RustChosenPath::from_server_export_dir`.** The path is computed by the server from `ATLAS_DUCK_DATA_DIR` and a random job id, never from a request. The M10 L54 check (`ci/` grep for `RustChosenPath::from_` outside native-dialog sites) gets one allow-listed call site; ledger L249.
- **PD-256 Download format.** One uncompressed POSIX ustar stream (`Content-Type: application/x-tar`, `Content-Disposition: attachment; filename="atlas-duck-export-<user>-<from>-<to>.tar"`), written by ~150 lines of own code (`crates/server/src/tar.rs`: 512-byte headers, regular files only, fixed mode 0600, mtime = export time, names ≤ 100 bytes, checksum; property-tested against a hand-parsed reader in the test). No compression (exports are mostly base64 ciphertext and JSON; `flate2` is in the lock but adding it buys little and adds a parser-facing format). Archive layout `atlas-duck-export-…/{manifest.json, events.jsonl, prune_log.jsonl, anchor-chain.jsonl, anchor-chain.manifest.json, README.txt}`. The response also exposes `X-Atlas-Duck-Manifest-Sha256` and the job page shows it: the out-of-band trust root a recipient copies from the page (§8.10's `--manifest-sha256`).
- **PD-257 Auditor access path.** `/api/auditor/*` routes sit behind a router layer that requires a session whose roles contain `auditor` (403 `auth/role_required` otherwise) **before** path extraction; the target `user_id` must exist in `users` (404 `audit/user_unknown`). The handler gets an `AuditView` from `Registry::audit_view(target)`: when the target's runtime is open, its `audit::Store` handle; otherwise the target's store opened by `audit::open` with the target's `ServerKeyStore` **without starting a `Core`** (no `APP_START` is appended to the target's chain by an audit read, and no agent-facing runtime exists), held under the per-user instance lock, closed after 5 min idle; a runtime open for that user while a view is held adopts the view's store. Admins have no route (SM-2.5; M12 T23's admin route scan stays green).
- **PD-258 `AUDITOR_READ` granularity.** One record per auditor API request that returns target data: `list_users` (once per request, no target), `query` (filter + page cursor summarised: `range`, kinds count, not the filter text), `trail` (`request_id`), `payload` (`seq`, `page`), `export` (range, job id). Each request appends to the auditor's chain via the auditor's runtime **and** `AUDITOR_READ {auditor_user_id, target_user_id, action}` to the anchor operational log, both before the body is built; failure → 503 `audit/read_not_recorded`. An auditor reading **their own** chain through `/api/auditor/…` is recorded the same way (no special case). Users reading their own chain via `/api/cmd/audit_*` write nothing (desktop behaviour).
- **PD-259 `verify-export` with an excerpt.** New optional inputs `anchor_chain: Option<&Path>` (the `anchor-chain.jsonl`; its manifest is read from beside it) and `anchor_chain_head: Option<(u64, [u8;32])>`. Checks, streaming and bounded (`Limits` gains `anchor_chain_file` = 256 MiB, `anchor_chain_line` = 64 KiB, `anchor_chain_rows` = 100 000): row hashes recompute; `prev_hash` links contiguous; each `leaf_entry` recomputes to a leaf contained in its `body`; every `leaf_entry` whose `chain_id` is the export's and `head_seq ∈ [first_seq, last_seq]` must match that row's `record_hash` (else 21, a contradiction like an anchor-dir mismatch); `head_seq` outside the range is skipped; the excerpt manifest's `chain_id` must be one of the export manifest's `chain_ids`. Trust: with `--anchor-chain-head <seq>:<hex>` the excerpt row at `seq` must exist and have that hash (else 21); then the excerpt binds the export rows up to the highest in-range `head_seq` `L`: 0 when `L` is the export's last row, else 20 — exactly the M10 anchor-dir rule; without a pinned head the excerpt contributes only internal consistency (20 unless `--manifest-sha256` binds). New report lines `"verified against the anchor chain"` and both-roots combinations, mirroring `ANCHOR_OK`/`BOTH_OK`. `--anchor-dir` and `--anchor-chain` together → usage error (exit 2): one export comes from one mode. The pin comes from the auditor page (`GET /api/anchor/head`), from the server's JSON log line `anchor_head {seq, hash}` written at every tick (the cluster's log store is the out-of-band witness), or from the admin CLI `anchor head` (M13 socket).
- **PD-260 E2E suite shape.** `crates/server-e2e` is a `harness = false` test binary (`tests/e2e.rs` with its own `main`) that requires `ATLAS_DUCK_E2E_BASE_URL`, `ATLAS_DUCK_E2E_USERS_FILE` (stub users: alice, bob, carol-admin, dave-auditor with test passwords), optional `ATLAS_DUCK_E2E_CA_FILE`, optional `ATLAS_DUCK_E2E_JIRA=mock|none`, and exits 2 with a usage line when they are missing (so `cargo test --workspace` never runs it: the crate is excluded there and in clippy-only jobs it compiles). Against the review environment Jira is `none` and Jira-dependent cases are skipped by name (listed in the summary as `skip`, never silently).

- **PD-262 Running-scripts window not in server mode.** M8's Running-scripts window (S-09) is a desktop window; in server mode a running script is visible as a pending item on the approvals page (its final result is approved there) and an agent cancels with `request_cancel`; a user-side kill button in the web UI is a handoff (L250).
