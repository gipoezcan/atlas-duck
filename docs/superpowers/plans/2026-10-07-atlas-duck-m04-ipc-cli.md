# atlas-duck M4 (IPC + CLI) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. One implementer subagent per task, one reviewer after each task. Each task below is self-contained: it names every file it touches, the interfaces it consumes from earlier tasks and the ones it must produce, and the tests with the assertions that matter.
>
> **Model policy for the executing agents:** implementers use **Sonnet (effort medium)**; every reviewer uses **Opus**; the security-critical tasks are implemented by **Opus** as well (marked `Model: Opus` in the task header: pipe/socket ACLs and owner checks, peer identity, the server's hello/limits, the launch environment and detachment, the test-only feature locks, the security test task). >
> **Hard execution limits (corporate AV, memory `agent-execution-limits`):** no subagent downloads or runs executables or installers, no `cargo install`, `pip install`, `npm install -g`; no `icacls`, registry or ACL changes on the developer machine; no `taskkill`; nothing outside the repo and the session scratchpad. **Goal:** Serve `core` over a same-user local IPC endpoint and give agents the real `atlas-duck` CLI: per-OS transports with owner checks and peer identity, the JSON-RPC server with `hello`, limits and progress, the client, registry-generated argv parsing with local `--help`/`ops`, the §4.3 envelope/exit contract, wall-clock `--timeout`, detached app auto-launch, `doctor`, and the app's startup orchestration that serves either `Core::handler()` or the gate handler on one swappable endpoint, all tested end to end with the real `atlas-duck-app --background` and `atlas-duck` binaries and a headless scripted approver.

**Architecture:** `ipc` gains `rpc` (JSON-RPC 2.0 messages, method names, async framing), `paths::endpoint` (the one shared endpoint-location function, the `<data>/endpoint` file), `transport` (Unix socket / Windows named pipe, both sides' owner checks), `peer` (pid → exe, start time, ancestor walk) and `server` / `client` (`HandlerCell`, `ShutdownSignal`, `IpcServer`, `IpcClient`). `cli` (deps `ipc` + `registry` only) gains the argv parser driven by `registry::CliBinding`, the input rules, the output layer, app discovery, the per-OS launcher and the connected commands. `app/src-tauri` gains the `core` edge and a composition root (`app::compose`), the startup orchestration (`app::serve`), the quit wiring, the app-side `doctor` fields and a test-only `scripted-approver` feature. `core` changes only additively (submit reply with `params_sha256`, `disconnected`, `set_utc_offset`) plus the M3 carry-overs.

## Global Constraints

The master plan's "Global Constraints" apply verbatim; read them once before Task 1. The subset M4 touches most:

- **Dependency rule (§2.2, `node ci/check-workspace.mjs`):** `cli` depends only on `ipc` + `registry` (normal edges); its normal closure must not contain any `BANNED_IN_CLI_AND_WORKER` crate (`reqwest`, `hyper`, `rusqlite`, keyring crates, `tauri`, `wry`, …). `ipc` depends on no workspace crate. `sandbox-worker` depends on `ipc` with `default-features = false`: everything tokio-based in `ipc` (rpc framing, transport, server, client) sits behind the existing `async` feature, so the worker stays tokio-free. `core` keeps its exact six edges. `app` gains the normal edge `app → core` (allowed: only `cli`, `registry` and `sandbox-worker` are restricted).
- **Binaries (§2.1, §12.1):** the `atlas-duck` bin (thin main over `atlas_duck_cli::run`) links no webview, TLS, DB, keyring or tray library (`ci/check-bin-linkage.{sh,ps1}`, existing CI steps); the `__cli` early-argv mode keeps working (`atlas-duck-app __cli …` → `atlas_duck_cli::run`).
- **Wire (§3.3):** `u32` big-endian length-delimited frames, max 24 MiB (`ipc::sandbox::MAX_FRAME_BYTES`; the first frame on a connection, the `hello`, max 64 KiB: `server::HELLO_MAX_BYTES`, L65); JSON-RPC 2.0; methods exactly `hello`, `ops.list`, `ops.describe`, `instances.list`, `request.submit`, `request.await`, `request.status`, `request.cancel`, `requests.list`, `script.submit`, `doctor`; notification `request.progress`; `hello` first and within 5 s; exact `build_id` match; frame/JSON/ordering errors → `protocol_error` (exit 1), never a silent drop.
- **Transport security (§3.1, §3.2):** Windows pipe `\\.\pipe\atlas-duck-<first 16 hex of SHA-256(user SID)>-<128-bit random hex>`, protected DACL with one ACE (user SID, `FILE_GENERIC_READ | FILE_GENERIC_WRITE`), `reject_remote_clients(true)`, first instance `first_pipe_instance(true)` and never retried without it, one listening instance kept, client `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, server SID check by impersonation after the `hello` read (one synchronous block or `spawn_blocking`, abort if `RevertToSelf` fails); Unix dir `0700`, `lstat` owner == euid, mode 0700, not a symlink, `peer_cred().uid() == geteuid()`; the CLI's owner check runs **before the first byte** (mismatch → exit 5 `server_identity`, nothing sent).
- **Limits (§3.3, L44):** 64 connections, 16 per `peer_origin_exe` (CLI with null origin: `peer_exe`) → `busy` with `retry_after_s: 5`; CLI-local exit 11 after a 5 s `WaitNamedPipeW` carries `retry_after_s: 5`; `busy` never triggers a launch.
- **Timing (§4.1, §4.7, L04):** `--timeout` default 100 s, wall-clock from CLI process start; `WaitNamedPipeW` ≤ 5 s, post-launch poll ≤ 20 s, `hello` round trip, each `min(own limit, remaining)`; a deadline expiry before submission → exit 5 `unreachable {launch_timeout}`, never 11; `--timeout 0` skips only the wait after submission.
- **Envelope (§4.2, §4.3):** exactly one envelope line on stdout per invocation in `--output json` (default); submission notice on stderr `{"event":"submitted","request_id":"…","params_sha256":"…","status":"pending"}` printed only from the server's accepted reply; SIGINT/SIGTERM/SIGHUP/CTRL_CLOSE_EVENT/broken pipe never cancel (pending envelope, exit 4); `status` exits 0 for any known id.
- **Launch (§4.7, L28):** only `--background`, no agent argv; environment rebuilt from the allowlist `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `HOME`/`USERPROFILE`, `LANG`/`LC_*`, `TMP`/`TEMP`/`TMPDIR`, `SystemRoot`, a system `PATH`; proxy variables in every case variant never forwarded; no inherited handles; stdio on the null device; cwd install dir (Windows) or `/`; detached from the caller's tree and job; Windows shell-parent first, breakaway stub only if granted, else exit 5 `launch_blocked_by_job`.
- **Lints and panics:** `clippy -D warnings` on the workspace; `unwrap_used`/`expect_used` stay errors in `core` and `atlassian` (incl. tests) and `node ci/check-no-panic-macros.mjs` keeps scanning `core`, `atlassian`, `audit`. New code in `ipc` and `cli` follows the same rule by convention (tests return `TestResult`), because the CLI runs in agents' processes and `panic = "abort"` turns a panic into a missing envelope.
- **Secrets and logs:** no PAT, URL, username, params, JQL/CQL or Atlassian text in any IPC diagnostic line (`tracing` fields allowlisted by the app's diag layer; ipc emits only constants, connection ids, pids and static reasons).
- **Fixed strings** (hints, gate messages) are copied verbatim from the spec section that defines them, each constant with a `/// §x.y (verbatim)` doc comment.
- **Commits:** one commit per task (more where a task says so), message `<type>(<crate>): <summary>` with trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; explicit pathspecs (never `git add -A` outside the task's directories); every cargo command uses `--locked` after the task that changes `Cargo.lock` has run its one unlocked build.

## Plan decisions and contract deltas

Tagged **(spec silent)** where the spec does not say; **(spec gap → ledger)** where the lead must add a ledger entry and a spec line (the master plan's rule: "A milestone plan never resolves a gap silently"); **Δ C.x** = master-plan contract change the lead applies before Task 1.

**Contract deltas (applied before Task 1):**
- **Δ1 C.2 `SubmitReply`.** The submission notice needs `params_sha256` after instance resolution, which only the server knows, and the pending envelope may carry nothing but `{request_id, op_id, instance, status}` (§4.5). So `RequestHandler::submit` and `submit_script` return `SubmitReply { pub envelope: Envelope, pub params_sha256: Option<String> }` (`Some(lowercase hex)` exactly when `envelope.request_id` is `Some`; serde `deny_unknown_fields`). `params_sha256` never appears inside an envelope. The JSON-RPC result of `request.submit` / `script.submit` is the serialized `SubmitReply`.
- **Δ2 C.2 `disconnected`.** `RequestHandler` gains `async fn disconnected(&self, conn: &ConnectionMeta) {}` (default body: no-op, so `GateHandler` compiles unchanged). `IpcServer` calls it once per connection whose `hello` succeeded, after the connection closed **and** every `submit`/`submit_script`/`cancel` task it spawned for that connection has finished (await tasks are dropped). Core removes the session; core also caps its session map at 1 024 entries (oldest evicted) as a backstop (M3 Task 19 handoff).
- **Δ3 C.2 transport surface.** As C.2 "M4 adds" plus: `pub mod rpc` (Task 2), `paths::{endpoint_location, EndpointLocation, write_endpoint_file, read_endpoint_file, ENDPOINT_FILE, socket_dir}` (Task 4), `transport::{Listener, Conn, connect_checked, OwnerCheck}` (Tasks 5/6), `peer::{peer_info, PeerSource}` (Task 7). `IpcServer::bind(data: &LocalDataDir, host: &str) -> io::Result<IpcServer>` and `serve(self, handler: Arc<HandlerCell>, shutdown: ShutdownSignal)` as C.2; `ShutdownSignal` derives `Clone`. `IpcClient::connect(ctx: &ClientContext, deadline: Instant)` as C.2 with `ClientContext { data_dir: LocalDataDir, host: String, hello: Hello }`; `IpcClient::call` as C.2 plus `call_with_progress<R>(&mut self, method, params, on_progress: &mut dyn FnMut(ProgressNotification)) -> Result<R, ClientError>`. `ConnectError` as C.2 plus `Busy { retry_after_s: u64 }` (server-side connection limit, PD-27) — `PipeBusy` stays the CLI-local `WaitNamedPipeW` timeout.
- **Δ4 C.3 / C.2 keyring locality moves to `ipc`.** `audit::keystore::locality::{DirsOs, keyring_dirs, keyring_dirs_for, Probe, probe_fs, keyring_locality, keyring_locality_with}` and `audit::KeyringLocality` move to `atlas_duck_ipc::paths::keyring` (pure path + `statfs` logic, already built only on `ipc::paths`); `audit` re-exports them under the old paths (`pub use atlas_duck_ipc::paths::keyring::…`), so no `audit` caller changes. Reason: §4.7 says the CLI computes `keyring_local` itself, and `cli` may depend on neither `audit` nor a keyring crate (PD-11).
- **Δ5 C.1 `registry::ops_list_json`.** `pub fn ops_list_json(env: &DescribeEnv) -> serde_json::Value` returns `{"ops": [{op_id, class, approval, description}, …]}` in `all()` order (the shape `core::gate::ops_list_local` builds today); `core::ops_list_local` and the CLI's local `ops list` both call it, so they cannot drift (PD-10).
- **Δ6 C.7 `Core::set_utc_offset(&self, minutes: Option<i32>)`** forwards to `SimilarityIndex::set_utc_offset` (the "similar to req_… executed HH:MM" text is UTC until a caller sets it; M3 progress line 73). The app calls it at start and hourly (PD-32).
- **Δ7 C.7 composition visibility.** The app's composition root uses `core::audit_port::DateBridge`, `core::proxy::SystemProxySource::new`, `core::http_factory::HttpFactory::new`, `core::credentials::KeychainCredentials::new` — all already `pub` and not feature-gated on `master` (checked); no change, recorded so nobody gates them later.
- **Δ8 C.7 `GateState` unchanged.** The app never serves `GateState::NotConfigured(data_dir_*)`: those states bind no IPC (§7.7 "at a later start the app opens no store, binds no IPC"); the CLI answers them itself (§7.7 CLI-side check). `NotConfigured(config_unreadable)` is not a gate state in practice either: `Core::start` runs with `ConfigState::Unreadable` and answers per request (M3). The variant stays for completeness.
- **Δ9 master plan M-11/M-12 (doc drift, M3 final review).** C.4 `WriteOutcome::OutcomeUnknown` gains `status: Option<u16>`; C.7 `ScriptRunner::start` returns `Arc<dyn RunHandle>`; the M3 plan's traceability renames listed in M-12. Doc-only.

**Plan decisions:**
- **PD-01 Test home override (spec silent; never in release).** `paths::base_dirs()` reads no environment by design (§7.7) and `ci/pinned-fixture.*` overwrites the host's real pinned file, so the real binaries cannot be tested end to end on a developer machine without an override. Feature `atlas-duck-ipc/test-paths`: when `ATLAS_DUCK_TEST_HOME` is set to an absolute existing dir `H`, `base_dirs()` returns `home = H`, `local_app_data = H/AppData/Local`, `roaming_app_data = H/AppData/Roaming` (all OSes, so the Windows layout is testable everywhere), and the socket dir is `H/s/` (Unix, created 0700, same lstat checks; short so the macOS 104-byte `sun_path` limit holds when the test picks a short root such as `/tmp/adt-XXXXXX`). Without the variable the feature changes nothing. `host_name()` is unchanged. Lock: `compile_error!` above + the CI forwarding rule.
- **PD-02 Test keystore (spec silent; never in release).** Under `scripted-approver` the app uses `app::testing::FileKeyStore` (implements `audit::KeyStore`; one file per `EntryName::full_name` under `ATLAS_DUCK_TEST_KEYSTORE`, values hex; a `mode` file `ok|unavailable|locked|not_local` maps to `KeyStoreError::{Unavailable, Locked}` on every call / `KeyringLocality::NotLocal{dir}`) instead of `OsKeyStore`, so `cli_flows` needs no OS keychain or Secret Service and can provoke each `locked` reason. The real `OsKeyStore` composition is covered by one `#[ignore]`d test `os_keychain_smoke` run in the existing Windows and macOS keychain CI steps (Task 26).
- **PD-03 Scripted approver control (spec silent; never in release).** Under `scripted-approver` the app runs `app::testing::ScriptedApp`: it tees the `UiSink`, and on every `QueueChanged` (and every 50 ms) reads `DecisionApi::queue_list()`; for each item whose `reason_excerpt` starts with `atlas-test:` it acts once per revision: `release` (open + release), `release-status-only`, `deny` (reason "denied by test"), `deny-details` (deny with `DenyDetails::UpstreamHttp { include_messages: true }` where applicable), `approve` (open + approve), `hold` (nothing; also the default without a directive). It uses `core::testing::ScriptedApprover` over the real `DecisionApi` (C.7: "the scripted approver calls this"). A control dir `<data>/test-control/` is watched every 100 ms: a file `quit` runs the §2.5 shutdown path with `ShutdownReason::Quit`; the app writes `env-names.json` (the **names** of its own environment variables at start, I-20) and `refused` (the gate handler's refused count after each `CredentialContextChanged`, PD-35) there.
- **PD-04 Before first run (spec gap → ledger).** With no pinned file for this host the app has no data dir and no `instance.lock`, so it binds no endpoint (§3.1: the lock precedes the bind; §7.7: `<data>/endpoint`). §7.7 says the CLI then "launches the app as before and the wizard enforces locality", and §2.5 G1 wants a `first_run` answer. Decision: the CLI applies every launch rule (app location, GUI session, launch lock, environment) and launches; the post-launch poll re-reads this host's pinned file on every tick; if no pinned file appears within `min(20 s, remaining)` the CLI prints `failed`, `not_configured`, `details.reason = first_run`, `retryable: true`, the §2.5 fixed message ("atlas-duck is not set up yet: finish the setup window on the desktop"), exit 9, `request_id: null`; if a pinned file appears it continues with the normal path. Local commands (`--help`, `ops` without `--instance`, `verify-export`) are unaffected. Ledger line: "§7.7 CLI-side check: before first run the CLI's answer after launching is `not_configured {first_run}` when no pinned file appears within the poll".
- **PD-05 App startup order (§2.5, §3.1, §8.7 steps 1–5).** GUI/`--background`: crash settings → diag → Tauri builder → `setup`: M1 gate (pinned → data-dir check → `instance.lock`) → in `Ready`: delete a stale `<data>/endpoint` → **first** `audit::open` (blocking, off the main thread) → map the outcome: `Ready{store, pats_deleted}` → `Core::start` (with `pats_deleted`) → handler = `AppHandler(Core::handler())`; `FirstRun` → `gate_handler(FirstRun)`; `Locked(r)` → `gate_handler(Locked(r))`; `StoreNewer` → `gate_handler(StoreNewer)` → `IpcServer::bind` (writes `<data>/endpoint`) → `serve(cell)`. While `Locked(KeychainUnavailable)`, the M2 retry loop (`keychain_retry_schedule()`, 90 s total) re-runs `open` and on `Ready` starts `Core` and **swaps** the cell (no rebind); after the schedule the state stays locked (manual retry is M6). The endpoint exists only after the first `open` returned, so no agent ever sees a half-started app; the CLI's post-launch poll covers the wait. FirstRun → Ready swapping (the wizard's `GENESIS`) is M6.
- **PD-06 Store errors bind no IPC (spec silent).** `audit::open` returning `Err` (tampered newest key row, `audit.db-wal` without `audit.db`, `MigrationFailed`; M2 handoff) and `Core::start` returning `StartError` are startup errors: the app keeps the lock, binds no endpoint, shows the tray status text "audit store could not be opened" (constant, no path, no error text) and logs `event=store_open_failed` with a static class (`integrity|io|migration|core_start`). - **PD-13 Argv grammar (spec examples + `CliBinding`).** Tokenized by `lexopt`. Global flags (`--agent NAME`, `--reason TEXT`, `--timeout SECONDS`, `--instance ALIAS`, `--output json|text`, `--help`) are accepted anywhere before a `--`. Op commands: the longest `noun_path` match selects the op; the `positional` param is the next free argument **or** the flag `--<param>` (param name with `_` → `-`; e.g. `jira search --jql …` per §4.1's example, while `CliBinding.positional = Some("jql")`), never both (usage). `FlagKind`: `Str` → string; `Int` → `i64` (`--max 50`; a non-integer → usage); `Bool` → presence (`--comments`; `--comments=false` → usage); `Json` → parsed JSON (parse error → usage with the parser's message, no input echo beyond 80 chars); `CsvList` → split on `,`, trimmed, empty items dropped → JSON array of strings; `KeyJsonPairs` → repeatable `--field id=<json>` into an object (duplicate id → usage). `file_variant: true` adds `--<flag>-file <path|->` whose content is the value (Str: the text; Json/KeyJsonPairs: parsed JSON; one of the two forms only). - **PD-15 `--output text` rendering (§4.1 "a human rendering of `data`").** stdout: `data.help` raw; else `data.result` pretty JSON (2 spaces); else `data` pretty JSON; nothing when `data` is null. stderr: the submission notice (if any), then one JSON line = the envelope with `data` set to null. Exit codes identical to json mode.
- **PD-16 Interrupts (§4.1; partly spec gap → ledger).** Handlers (tokio `signal`) are installed for the whole connected phase. Interrupt **after** the server's submit reply: print the pending envelope `{request_id, op_id, instance, status: pending}` if stdout is writable, exit 4, never cancel. Interrupt during `await <id>`: the same with that id. Interrupt **before** the submit frame was written: nothing was queued → `failed`, `unreachable`, `details.reason = launch_timeout`, exit 5 (the §4.3 "deadline expired before submission" row; no new reason). Interrupt after the submit frame was written but before its reply (spec gap): `pending`, `request_id: null`, `error {code: unreachable, retryable: false, details: {reason: connection_lost}}`, message "the request may have been queued; recover it with requests list --match-params-file", exit 4 (§4.3's `connection_lost` row with an unknown id; ledger line). Broken pipe: any failed stdout write ends the process with exit 4 and never cancels (Unix: SIGPIPE is ignored by the Rust runtime, so writes return `EPIPE`; Windows `ERROR_NO_DATA`); additionally on Unix the wait loop polls fd 1 for `POLLERR|POLLHUP` every 500 ms and treats a hang-up like an interrupt. `status`, `cancel`, `requests list`, `instances`, `doctor` keep the default signal behaviour (short calls).
- **PD-17 Deadline (§4.1).** `Deadline::new(start: Instant, timeout: Option<Duration>)` is created as the first statement of `run` (process-start approximation). `remaining()` caps `WaitNamedPipeW` (5 s), the post-launch poll (20 s), `connect`, `hello` and the submit round trip. With `--timeout 0` the pre-submission steps use their own limits only; the wait after submission is skipped (`await` not called; the pending reply is printed). Expiry before the submit frame is written → exit 5 `launch_timeout`. After submission the CLI calls `request.await {timeout_ms: remaining}`; an `await <id>` command does the same.

- **PD-22 Launch lock (§4.7 "serialized via a launch lock file in the data dir").** `<data>/launch.lock`, exclusive `std::fs::File::lock` (stable since Rust 1.89) held from the endpoint check through the post-launch poll; a second CLI waits on it (bounded by the deadline) and re-checks the endpoint after acquiring it. Before first run (no data dir) the lock is `<pinned dir>/launch-<host>.lock` (`ipc::paths::pinned_dir`, host-qualified like the pinned files); the pinned dir may not exist yet on a fresh machine, so the CLI creates it (and only it, mode 0700 on Unix; default ACL on Windows, where it lives under `%LOCALAPPDATA%`) before opening the lock file. It writes nothing else there.
- **PD-23 Unix launch.** Linux: `/usr/bin/systemd-run` (only that absolute path) exists and `systemctl --user` is reachable (`systemd-run --user --scope --quiet --collect` returns within 2 s on a probe `/bin/true`, cached per process) → `systemd-run --user --scope --quiet --collect -- <app> --background` started through the same double-fork; else plain double-fork. Double-fork: `fork` → child `setsid` → `fork` → grandchild: `dup2(/dev/null)` onto 0/1/2, `close_range(3, ~0, 0)` (fallback: close 3..`RLIMIT_NOFILE`), `chdir("/")`, `execve(app, ["--background"], allowlisted envp)`; only async-signal-safe calls between `fork` and `execve`, every string prepared before `fork`; the first child `_exit(0)`s; the parent `waitpid`s it. macOS: when the app path is inside a `*.app` bundle, `/usr/bin/open -n -g -a <bundle> --args --background` with the allowlisted environment (LaunchServices does not pass the caller's environment, V13 note), else (dev builds) the double-fork. The CLI never uses `std::process::Command` for the app itself except `open`/`systemd-run` probes, each with `env_clear()` + allowlist and null stdio.
- **PD-24 GUI session detection (§4.7).** Linux: `DISPLAY` or `WAYLAND_DISPLAY` non-empty. - **PD-25 Socket upkeep (§3.1 "touched periodically / sticky bit").** The server `chmod`s the socket to `0600 | S_ISVTX` after bind and every 6 h `utimensat`s the socket file and its dir (systemd-tmpfiles skips sticky files and recent mtimes).
- **PD-26 `<data>/endpoint` content.** One line: Windows the full pipe name; Unix the absolute socket path. Written atomically (temp file in the data dir + rename), Unix mode 0600, Windows created with the owner-only security descriptor of Task 6 (protected DACL, user SID full control). - **PD-27 Connection-limit busy.** At 64 connections, or 16 for the connecting peer's limit key (`peer_origin_exe`, else `peer_exe`, else the constant bucket `"?"`), the server still accepts, reads the `hello` frame within 5 s, answers it with the JSON-RPC error `-32000` whose `data` is `busy_envelope(BUSY_RETRY_CONNECTION_S)` and closes. The client maps it to `ConnectError::Busy { retry_after_s: 5 }` → exit 11, never a launch.
- **PD-28 JSON-RPC mapping.** Request `{"jsonrpc":"2.0","id":<u64>,"method":…,"params":{…}}`; success `{"jsonrpc":"2.0","id":…,"result":…}`; error `{"jsonrpc":"2.0","id":…|null,"error":{"code":…,"message":…,"data":<Envelope>}}`. Codes: `-32700` parse error, `-32600` invalid request (incl. a non-`hello` first frame, a second `hello`, oversize frame), `-32601` unknown method, `-32602` invalid params — each with `data` = `protocol_error` envelope (`failed`, exit 1, `retryable: false`, `details.reason` ∈ `parse|invalid_request|hello_required|hello_repeated|frame_too_large|unknown_method|invalid_params|hello_timeout`); `-32000` = an application refusal carried as an envelope (`hello` build mismatch, connection-limit `busy`). Every other handler answer, including `failed` envelopes, is a `result`. Params: `hello` = `Hello`; `ops.list` `{instance?}`; `ops.describe` `{op_id, instance?}`; `instances.list` `{}`; `request.submit`/`script.submit` = `SubmitParams`; `request.await` = `AwaitParams`; `request.status`/`request.cancel` `{request_id}`; `requests.list` `{agent?, state?, match_params?}`; `doctor` `{}`; notification `request.progress` params = `ProgressNotification`.
