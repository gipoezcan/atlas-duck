# Server data on NFS with a rollback journal, and daily backups

The cluster offers no ReadWriteOnce block storage class, and `local-path` is not provisioned on its nodes (the first review deploy's claim never bound: "no local path available on node"). Every class the team can use is NFS (`team-dux-storage`). So the live stores go on a `team-dux-storage` claim, ReadWriteOnce, with one replica and the `Recreate` strategy (ADR 0003), and SQLite runs in the mode NFS can carry: `ATLAS_DUCK_SQLITE_JOURNAL=delete`, the server's default. Every server-side database (`server.db` and each user's `audit.db`) uses the rollback journal (`journal_mode=DELETE`) with `synchronous=FULL`, never WAL, whose shared-memory index does not work over NFS. `server.db`, which only the server's single connection opens, also takes `locking_mode=EXCLUSIVE`, so no second process can open it while the server runs. A user store keeps normal locking, because its own read connections run beside its writer. The desktop refuses a data folder on a network filesystem. The server accepts one only with `delete`: with `wal`, its data directory must be local. A second claim on the same class holds the daily backup bundles the server writes itself, keeping the newest 14 (`ATLAS_DUCK_BACKUP_DIR`, `ATLAS_DUCK_BACKUP_KEEP`).

## Consequences

SQLite on NFS is safe only with exactly one writing host. That depends on the single replica, `Recreate`, the instance lock in the data directory and the exclusive lock on `server.db`. It still relies on the NFS server's locks and fsync behaving correctly. That includes the instance lock, a `flock`, which the Linux NFS client maps to NFS byte-range locks. Nobody has verified this on this cluster's NFS server yet. A stale lock or lost write on the NFS side could corrupt a store, and the anchor chain and `admin anchor verify` detect that afterwards rather than preventing it. The rollback journal is slower than WAL, and readers wait while a write commits. That is acceptable at this load.

The backup claim is on the same NFS server as the data, so it protects against a damaged or deleted claim, not against losing that server. Streaming a bundle off the cluster (`admin backup --stdout`) covers that case (docs/server/backup-restore.md). The backup claim holds wrapped data keys and every chain of the last 14 days. That widens the exposure of ADR 0002 to anyone who can read that share. Retention-deleted chains disappear from it within 14 days.

Ask the cluster admins for `local-path` provisioning or a ReadWriteOnce block class. Once either exists, the data claim moves there with `ATLAS_DUCK_SQLITE_JOURNAL=wal` (chart value `persistence.sqliteJournal`) and a restore from a bundle, with no code change. The desktop app is unaffected: it always uses WAL.
